## Checklist gaps (from the risk reviewers, verbatim)
destructive-operations (SQ-025):
- Changes that only add access (raising an Allow, or Deny to Allow) on high-impact roots and protected folders: "Inheritable Add and Copy" should also cover in-place Change and any Allow raise, and "adds access only" must not bypass the high-impact checks.
- In-place ACE edits: the user-facing text must not promise "only this entry changes" when the API used (AddAccessRule) can merge entries, and the old-value read should be the one the exact-match decision used.
- A `-WhatIf` dry run should apply the same re-read and refusal checks (entry still there, canonical order) as the real run, so it does not promise a change the real run will refuse.
- The self-lockout warning should cover lowered Allows as well as Deny, and say when group membership on a remote server could not be checked.

destructive-operations (SQ-029):
- A "dry run / smoke / nothing changes" mode must be enforced at the change chokepoint (`Start-ChangeTask` / the write layer), not only at the UI action wrapper. Every direct UI handler that writes (settings, export, folder creation) must also check the mode.
- Pre-flag startup paths (code that runs before a mode switch is captured, such as missing-dependency message boxes) must honour the mode, or be listed as exceptions.
- A process runner that launches tools in a special mode must verify the target declares that mode (AST check) before starting it. Otherwise an unknown switch can be silently ignored and the tool starts normally.
- Integration tests that launch a real tool in a no-write mode must redirect LOCALAPPDATA/TEMP for the child, even when they aren't testing for leftover files.

destructive-operations (SQ-022):
- An acknowledgement switch passed from a UI to a core (-AllowDeny style) must carry what the user actually saw (the ACE set, the target list), not a boolean. Otherwise anything that changed after the confirm goes out under it.
- A late re-check before a path-based write should say whether the window between the check and the write is acceptable, or require a handle-based write. It should also note that Set-Acl rewrites the whole DACL it read earlier, not only the added entries.
- When a new guard is added to an existing work function, the existing suites start reaching its real P/Invoke or disk reads. They need the same UNC-$TestDrive guard and must not depend on where %TEMP% lives (for example a runner whose TEMP is under C:\Windows\Temp).
- Docs and README claims of the form "whatever calls it" or "refuses X" must match every caller and every case: a front end that never passes the override, DFS, and the boolean-acknowledgement case above.

destructive-operations (SQ-024):
- "Typed `.` and `..` segments are refused" should also cover segments made only of dots and spaces (`.. `, `. .`). It should state that the dot rule is enforced in the core guard as well as in each front end.
- The CLI's "is this a full path" test should cover PowerShell provider-qualified (`FileSystem::`) and PSDrive paths. PowerShell's own `..` collapsing is not the Windows rule.
- Refusal text for a rule that also matches real on-disk names (for example `...`) must not give a next step the tech cannot take.

personal-data (SQ-027):
- The ticket-notes section covers what is removed from the note (IPs, paths, SIDs, third-party data). It does not cover how sensitive the verdict text itself is. "This user is flagged as possibly compromised", lockout investigations, and similar security findings leave the machine in a PSA note. That note may be visible in the client portal or emailed to the contact, who may be the compromised user. Add a rule that tools whose notes state a security or compromise finding tell the tech, in the note or the README, to paste it as an internal-only note with contact notification off.

read-only-advisory (SQ-027):
- Under "A failed or partial check ... could not check": every non-Available state of a safety-relevant gate (including NotAllowed/403, not only NotLicensed/Failed) must trigger the cautious path. Tests must loop over all states the gate classifier can return.
- Changing or excluding a user from a Conditional Access policy (including risk-based policies) is a reversal of a deliberate block. Add "exclude from policy / change the policy" to the reversal verb list.
- A deliberate cloud-side block on a synced account (AD enabled, no marker) must not be framed only as a sync fault. The step escalates before any sync troubleshooting.
- For risky or compromised users, the checklist should also cover MFA/security-info registration steps, not only unblock, re-enable and password reset.
- Ordering: when an escalation applies to the account, it is the first next step in the ticket note, not appended after plain steps.
- (re-review) The checklist could require that when a code path branches on gate states, every state Get-M365GateFromError can produce for that source (Available / NotLicensed / NotAllowed / Failed / NotChecked) is handled explicitly and tested.
