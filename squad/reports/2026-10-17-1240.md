## Checklist gaps (verbatim from the risk reviewers)

**personal-data**
- CHECKLIST GAPS: (1) The clipboard as an output channel: clipboard history, cloud clipboard sync, and RDP redirection off client servers. Also, tests must never touch the real clipboard, including child-process tests that mocks cannot reach. (2) A rule that paste-safe or redacted outputs are applied end to end, so aggregators/joiners re-apply redaction rather than trusting their inputs. (3) Loose output files (not only output folders) in `.gitignore` when `-OutputPath` can point anywhere. (4) Over-collection through "ambiguous match" candidate lists that pull in unrelated users. (5) Tests whose "skip when RSAT is installed" branch still runs the tool against the real domain.
- Clipboard as an output channel. The checklist has nothing on it. Add: client data copied to the clipboard by default must opt out of clipboard history and the cloud clipboard (CanIncludeInClipboardHistory / CanUploadToCloudClipboard, https://learn.microsoft.com/windows/win32/dataxchg/clipboard-formats) on every PowerShell version, or be opt-in. The README must mention RDP clipboard redirection.
- Tests must not reach real user-facing state (clipboard, %USERPROFILE%, Documents), with a static guard for both child-process and in-process script runs.
- Redaction ("paste-safe") rules: what is removed (IPs, share paths), what is deliberately kept (headline, DC/host names, user names), and that any re-processing step (joiners, combiners) applies the same redaction again.
- Default output roots must not be cloud-synced folders (OneDrive Known Folder Move).
- CSV formula injection: Graph or AD values starting with `=`, `+`, `-` or `@` (display names, app names, error text) written by `Export-Csv` run as formulas when a tech opens the CSV in Excel. Prefix these with `'` or neutralise them.
- Security-relevant connection options silently dropped by compatibility fallbacks (`ContextScope`, `-DisableWam`-style options). The checklist should require a warning, or a refusal to run, when a protective option cannot be applied.
- `-PassThru` / result objects as a leak path: raw Graph rows with IPs, phones and devices kept in returned objects.
- Console and transcript output should get the same redaction as CSV and ticket notes.
- Consent hygiene in client tenants: delegated consent to Microsoft Graph Command Line Tools persists after the run. The narrowest scope matters beyond the session.
- Reports that hold personal data (the HTML with IPs and locations) carry no visible "contains personal data, do not attach or forward" marking, while the product description says reports get attached to tickets and the note's Evidence line lists the HTML file name.
- `.gitignore` patterns should be repo-wide (`**/`), not limited to the tool folder.
- "Trim Graph or API responses as they arrive when the endpoint does not support $select" is not covered. Today only "collect only what the diagnosis needs" applies, and it is easy to read as covering only the request.
- Token lifetime after sign-in (Connect-MgGraph -ContextScope Process, and refusing to sign in with modules that lack it) is not covered. Only "disconnect when done" is, and that does not help when the run is killed before the finally block.
- Tests must never trigger PowerShell module autoloading of a real RSAT module or connect to a real DC. This includes `Get-Command`/`Import-Module ActiveDirectory` in child processes (set `ADPS_LoadDefaultDrive=0`), and a file-level throwing stub for every AD cmdlet the code under test calls.
- The read-only static guard must cover every write verb of every module the tool imports (AD, not only Graph), not one hand-picked list.
- Values the tech supplies (`-Server`, typed names) that get repeated in error text should go through the same IP/path redaction as tenant data on every surface, including banners.
- A credential passed in must have a test proving it never shows up in the result object, the CSV, the HTML or the ticket note, not only a code-reading check.
- Matching another user's records: when a tool filters host-wide logs or events to one user, require matching on SID or `DOMAIN\sam` with proper delimiters, not a bare-name `\b` regex, plus a test with a similar name (`jdoe` vs `jdoe.smith`).
- What paste-safe/redacted ticket notes must remove (SIDs including `S-1-12-`, paths with spaces, IPs in headlines and parameters), with a test for each.
- Secret patterns in log or event text that is quoted into output (`AccountKey=`, `SharedAccessSignature=`, `sig=`). This applies to tools that quote FSLogix, Cloud Cache or Azure log lines word for word; this change has no scrub for them.
- Data minimisation across remote calls: filter on the remote side so other users' data is not shipped back to the tech's PC.
- Permissions on output folders: client-data and audit folders created on shared servers (RDS hosts, file servers) inherit read access for Users. The checklist should require a restricted ACL, or at least documenting it.
- Tool location versus "stays local": a default output folder next to the script ends up on a share when the tool runs from UNC. The checklist assumes the script directory is local.
- Audit records from tools that change things (change logs and restore backups): the checklist only names diagnostic exports. It should say that backups used for restore are integrity-sensitive (tampering changes what a restore applies) and that they are kept indefinitely.
- Fallback and resolved output locations: every location the tool may write client data to (default, fallback, explicit, relative) must be resolved to a full local path or warned about, not only the default.
- Backups and logs that hold client paths should record absolute, fully resolved paths. A relative path in a backup cannot be trusted at restore time.
- The checklist doesn't say that browser GUIs over HttpListener must insert client-derived values with textContent or encoding, not innerHTML. It only names "HTML reports".
- Change-log and backup files under a tool's Logs folder hold account names, SIDs and paths, but the checklist only mentions "case or evidence folders". It should list them explicitly.
- The checklist should say that secrets embedded in configuration values (Azure storage connection strings, account keys, SAS tokens in registry, GPO or config settings) must never be echoed into findings, error text or "invalid value" messages, including when the value is malformed. Validation messages should use fixed wording. It should also require a regression test for malformed input that runs on into the secret.
- Redaction done after the fact (regex over rendered text) instead of building text from safe fields. The checklist should prefer building from known-safe fields and treat post-hoc regex stripping as fragile.
- The checklist should cover -PassThru RawOutput: raw event-message text and other free text handed to calling scripts should get the same secret filtering as the reports.
- Output file names built from client data (sam, display name) should be sanitized against path traversal and reserved characters.
- When `-Credential` (or the tech's own logon) is used to connect to a host named in user-supplied input, the credentials are offered to whatever machine that name resolves to. An NTLM fallback against a spoofed name is the exposure. The checklist doesn't mention this.
- The README should say what client data a saved report holds and how to handle it (ticket only, delete the local copy).

**destructive-operations**
- CHECKLIST GAPS: A change made by more than one step (takeown, then `Set-Acl`) can fail partway. The log must record the real state after a failure, never just "nothing changed".
- Backups must be checked by reading them back (row count and content) before acting, not just written without an error.
- "Could not read" or otherwise unusable backup entries must stop the change unless an owner decision explicitly allows it for that action.
- The change log should be written per item, or be safe if the run is interrupted, so a cancelled batch still has a log.
- Plain-English `Detail` must describe what the API actually does (`RemoveAccessRuleAll` removes all rights, not just the ones named).
- Restore instructions should include a check step that confirms the owner and DACL really came back.
- Time between the safety check and the change: the checklist does not ask that the old value logged and backed up be the same read the safety decision used.
- Log file locked by another program (Excel): the checklist should require a fallback or keeping the rows, not just a warning.
- Items with no restorable backup (allowed for take ownership): the checklist should require that every message telling the user to restore from the backup also says which items it cannot restore.
- Out of scope here, but the profile should name it: before this branch, the recursive "Copy permissions (all subfolders and files)" path in the GUI runs `icacls /reset /T` with no confirm and no backup (D-031 / SQ-015). The "show scope before confirming" line does not currently catch actions that have no confirmation at all.
- Incomplete backup must not show as success: a backup that is known to be incomplete (unlisted folders, unreadable items) must never produce a green/PASS result.
- Verify the result by read-back: success of a native tool (icacls, takeown, robocopy) must be confirmed by reading the result back, not inferred from exit codes or English output text that Learn doesn't document; localized Windows has to be considered.
- Reparse points: junctions, symlinks and mount points inside a recursive target may make the change reach outside the folder shown to the user, or make the snapshot and the change cover different sets of items.
- High-blast-radius targets: recursive destructive actions need a guard for drive roots, OS folders and profile folders.
- The restore procedure itself: documented undo steps should be verified (privileges, per-item error handling) and preferably tested, not just written.
- Tests that mock native tools: must mock the wrapper that actually runs the tool. A mock of the bare exe name can be bypassed when the code calls the exe by full path.
- Exit codes: console scripts should exit non-zero when a change failed, for unattended runs.
- Native tools whose side effects go beyond the stated action: for example `takeown /D Y` replaces permissions, not just owners. The checklist should require that every side effect of a native command is backed up or warned about before confirming, and is reflected in the undo docs.
- Read-back verification: a result must not be reported as Done when nothing could be verified (no vacuous success).
- Long-running bulk actions should log a "started" record before the irreversible step, so an interrupted run is auditable.
- Undo instructions should keep "applying the restore" and "verifying the restore" separate, so a failed check is not reported as a failed restore.
- GUI and CLI should show the same scope before confirming. When one entry point has a preview, the other should too.
- Recursive tools: things the pre-snapshot can't see (content under folders that can't be opened) should be listed as possibly changed and not backed up, not only as "not in the snapshot".
- Add-only copies can still be security-harmful: duplicating rules that are already inherited (or copying explicit rules onto descendants of the source) silently breaks later access removal. The checklist should require tests where the target already inherits the same rule from the source.
- A Deny rule that spreads by inheritance has a wide blast radius. Copy/add operations that include Deny rules should be called out in the confirmation.
- Status and log text should describe what was actually written (re-read after the change), not what was planned, including races between Plan and Change.
- Writes that propagate automatically (one Set-Acl re-propagating a whole subtree) count as bulk operations. They need scope shown before confirming and a note on how long they run.
- A result or status message produced by a shared function must be true for every entry point that calls it (GUI vs CLI scope differs). Above all, a message must never say sensitive items were left alone when they were written.
- Changing permissions on folders that block inheritance (SE_DACL_PROTECTED) should be named in the confirmation and counted, because those folders are usually locked down on purpose.
- Warnings in confirmation dialogs that come from client-side state must be tied to the item being changed, never stale.
- The checklist has no item for "a copy or propagate operation does not widen a rule's intended scope" ("this folder only", OI-only, NoPropagateInherit must be respected for descendants; protected descendants skipped or explicitly opted into).
- No item says to fail closed when a safety check cannot run (for example, an unreadable ACL must not be treated as "not protected").
- No item covers scalability of the pre-confirm scope calculation on large trees.
- Read-only diagnostic tools: the "never changes anything" static guard should also cover .NET method calls (Delete/Kill/Move), Invoke-Expression and dynamic scriptblocks, not just cmdlet names.
- Wording of recommended destructive or lossy actions (logoffs, session resets): the next step should check the state first (Disconnected vs Active) and say to save work or ask the user first.
- Reading live log or lock files on production hosts should use a non-exclusive share mode (FileShare.ReadWrite|Delete).
- Tests should prove that calls without -OutputPath or -TicketNumber never fall back to a real default folder (for example Documents\TicketNotes) on the dev machine.
- Tests that replace a script's own functions with global aliases or functions must remove every one in AfterEach/AfterAll by fixed name, and point the default output root at $TestDrive before any run that can write without -OutputPath.
- The checklist has no section for tools that claim to be read-only. It should require a static allowlist (AST) test of every command and .NET method the script calls, so the "Changes anything? No" label is enforced.
- CIM/PSSession/remote-session cleanup: sessions opened against client servers must be closed in `finally`, with a test that proves cleanup on the failure path.
- Read-only remote method calls: list `Invoke-CimMethod` / `Invoke-WmiMethod` with any non-getter method, `Set-/New-/Remove-CimInstance`, and `.SetAccessControl()` / `[IO.File]::Delete` as write operations to mock and assert against.

**system-configuration**
- Static read-only guards should cover every file a tool dot-sources or runs (companions and the shared kit), not just the entry script, and check .NET method calls (RegistryKey.SetValue/CreateSubKey/OpenSubKey writable, ServiceController.Stop, File.Delete).
- Read-only tools that open live files on a production host (logs, VHDs) should open them with FileShare.ReadWrite.
- Remote sessions (CIM sessions, PSSessions) must be closed in `finally` on every return path.
- Script blocks sent to a remote host (Invoke-Command, including ones built with [scriptblock]::Create from local function text) should be included in the read-only scan.
