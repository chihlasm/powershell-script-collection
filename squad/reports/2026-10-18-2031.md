## Checklist gaps (verbatim from the risk reviewers)
### SQ-011 CHECKLIST GAPS (personal-data)
- Error messages from remote systems (AD/ADWS exceptions, Graph error bodies) that end up in report or note text, together with operator-supplied values such as `-Server`. The checklist covers credentials but says nothing about redacting a DC address or hostname in console banners, or about testing that credentials stay out on the failure path as well as the success path.
- Whether directory identifiers (DistinguishedName/OU path, SIDs) may appear in paste-safe ticket notes that leave the machine. The checklist only names IPs and share paths implicitly, through D-009.
- Whole AD objects returned in a `-PassThru` result: whether the result object should carry the full AdUser (`proxyAddresses`, `pwdLastSet`, SID) or only the fields the verdict uses.

### SQ-011 CHECKLIST GAPS (destructive-operations)
- The checklist covers mocking write cmdlets but says nothing about tools that must stay read-only. It should require such tools to enforce this with a case-insensitive allowlist of the cmdlets allowed per module (AD, Mg, Exo, Az), not a case-sensitive deny-list regex. The check should also cover module-qualified names, dynamic invocation (`&`, `Invoke-Expression`, `[scriptblock]::Create`), ADSI/DirectoryServices writes, AD: provider writes, and raw REST calls (`Invoke-RestMethod`/`Invoke-WebRequest`).
- Delegated Graph tokens carry every scope already consented, not only the ones requested. "Read-only scopes" must not count as a write control. GET-only plus the static guard is the actual control.
- Diagnostic tools whose "What to do" lines tell helpdesk techs to delete objects (users, groups, contacts, AD markers) should send those steps to a senior engineer and note when the object cannot be restored. Advice is a destructive path too, even when the code writes nothing.
- The checklist covers tools that change things, but not read-only verdict tools that advise a destructive action (remove an address, delete an object, remove a block marker). It should require that such advice either escalates (D-017) or names the tool that records the old value, with a test over all Action strings.
- For tools labelled read-only, the checklist should require a construction guard that: is case-insensitive and module-prefix-aware, using an allowlist rather than a denylist; covers dynamic invocation and the other directory modules (AzureAD, MSOnline, Microsoft.Entra, ExchangeOnlineManagement); does not allowlist commands that persist client-side settings (`Set-MgGraphOption`).
- The checklist covers tools that change things. It says nothing about read-only verdict tools whose next-step text tells tier 1 to make a destructive or reversing change: removing markers, deleting objects, re-enabling disabled accounts. Add an item: every next step that undoes a deliberate block or disable, or removes or deletes anything, must escalate (D-017). It must stay consistent across the branches with and without AD data, with a test that lists every reason code and every branch, using a wider set of verbs than remove/delete.
- Nothing requires a static "read-only by construction" guard for tools labelled "Changes anything? No". The rules that guard should follow are not written down either: module-qualified names, case-insensitive matching, GET-only checks for Graph and REST wrappers, child-process and Start-Process escapes, and dynamic invocation.

### SQ-014 CHECKLIST GAPS (personal-data)
- Retention and handling guidance for client-data output (backups and change logs that keep growing on client servers). Nothing in the profile asks a README to say what the files contain or when to delete them.
- No limit on client identifiers inside log cells (whole lists of user and folder names in one CSV field), or the Excel 32,767-character cell limit silently cutting off evidence.
- Logs written next to the script when it is run from a shared or toolkit copy. This tool handles it with the %LOCALAPPDATA% fallback, but the profile does not require it, so other tools could write client data back onto a share or into the toolkit bundle.

### SQ-014 CHECKLIST GAPS (destructive-operations)
- Path canonicalisation before any protected-path or scope check: UNC admin shares (`ADMIN$`, `X$`), `\\?\` and `\\.\` prefixes, 8.3 short names, trailing dots and spaces, and links or mounted volumes at the top of the target.
- WOW64 environment differences when a guard relies on env vars (`ProgramFiles` vs `ProgramW6432`).
- Remote targets: a guard built from the local machine's env vars does not describe the remote server.
- Native tools run after a "skip" step (takeown /D N followed by icacls /T): the result text must come from reading back, not from what the first tool was meant to do.
- Leftover dangerous switches in sibling code paths (here `/D Y` in the single-item call) should be grepped for and pinned by a test across all calls.
- Server-side enforcement of "one change at a time" for GUIs over HttpListener.
- Path canonicalisation for destructive targets: refusals and "protected path" guards must be checked against the path the OS will actually reach. That means junctions, symbolic links, subst and mapped drives, 8.3 names, `\\?\` and `\\.\`, trailing dots, admin shares, and server-side junctions on SMB, and the guard must not fail open when the path cannot be resolved.
- Links inside a recursive change: any recursive native tool (takeown /R, icacls /T, robocopy, Remove-Item -Recurse) must have the targets of links inside the tree checked before it runs, not just reported afterwards.
- Well-known system shares (SYSVOL, NETLOGON, print$, ADMIN$, X$) are system folders reached through UNC paths and should be treated as protected.
- Cleanup code inside a failure path (removing folders or files the tool created) should use a primitive that cannot recurse or prompt, and must never be able to delete another run's backup.
- The protected-folder list could cover other high-impact roots: C:\Users (every profile), System Volume Information and $Recycle.Bin on data volumes.
- The checklist does not say that a recursive change must define what counts as a link or redirect as an allowlist of known-safe types, never a denylist. A bit-test denylist such as name-surrogate is exactly what lets DFS links and other filter-driven redirects through. It also does not ask whether a recursive operation can leave the selected tree, through links, DFS referrals or links nested inside link targets. Add: "recursive changes stay inside the selected root; any redirect leading outside it is refused or listed in the confirmation."

### SQ-013 CHECKLIST GAPS (personal-data)
- Paste-safe redaction (D-009) is not on the checklist. It should require the redaction tests to cover paths with apostrophes, spaces, parentheses and commas, unquoted and single- or double-quoted, plus IP literals inside host names. It should also prefer leaving client paths out of the note over relying on regex redaction afterwards.
- Clipboard handling: history and cloud-clipboard opt-out, an explicit warning when it cannot be applied, and RDP clipboard redirection.
- Tests must never touch the real clipboard or `%USERPROFILE%` default folders, and must assert that their test doubles are in effect.
- Run-as credential user names (privileged admin account names) in client-facing notes.
- Personal data about third parties in notes (ambiguous-match candidate lists).
- Per-user activity data such as lastLogon and group-join dates in exported notes: keep it to the precision the diagnosis needs (date-only here, which is fine).
- The checklist has nothing on paste-safe or redaction filters for ticket notes (D-009). Suggested items: (1) Redaction must be tested against legal-but-awkward names: an apostrophe followed by a space or punctuation, spaces in the last segment, uppercase or alternative forms of IP literals. (2) Tools should keep client paths out of note text they build themselves rather than rely on the filter. (3) Exception messages copied into notes count as client data that can carry paths. (4) A shared filter used by several tools needs behaviour tests in the canonical suite plus at least one end-to-end paste-safe test in each tool that uses it.
- The checklist has no item for redacting text a tech pastes into a ticket. Suggested wording: "Any output marked paste-safe or for the ticket removes client share paths, IPs (including *.ipv6-literal.net names) and folder names that appear inside error messages. Prefer a literal scrub of paths the tool already knows over pattern guessing, and add a regression test with an apostrophe/space folder name."
- It does not cover clipboard handling: notes should stay out of clipboard history and the cloud clipboard, and there should be a way to skip the clipboard (-NoClipboard).
- It does not say which identifiers are allowed in the note's stamp line (server name, run-as user name, domain) versus which must be removed. That is currently decided only in D-009.

### SQ-013 CHECKLIST GAPS (destructive-operations)
- **Advice that tells someone else to change things.** The checklist only covers tools that write. It should also cover read-only verdict tools whose next step tells tier 1 to make a change: group membership, ACL changes via FolderPermissionManager, privilege-granting steps. That means D-017 wording, an approval condition placed in or before the action, never recommending well-known privileged or computer groups, and failing closed when privilege can't be determined.
- **Read-only guards.** When a read-only tool dot-sources or loads a shared file (CaseKit), the guard must scan that file too, and allowlisting writer functions by name is not enough.
- **Parity-copied shared files.** A destructive change to a shared kit spreads to every tool through the parity copy. The checklist should require a per-copy write-surface check.
- **Clipboard writes.** The clipboard is never mentioned. It is overwritten by default and travels over RDP redirection. -NoClipboard and -Quiet handle it here, but the checklist should say so.
- **Folder-ACL step (spec text, not a finding).** The AC29 step tells tier 1 to add a group to the folder ACL with FolderPermissionManager after the owner agrees. On a parent folder with inheritance this widens access to the whole subtree. Consider whether that step should also say "Escalate" under D-017.
- **Advisory tools:** the checklist covers tools that change things, not read-only tools that tell a tech to make a privileged change (add a user to group X). It should require that such advice can never name a privileged group without escalation, and that the privilege check fails closed, including cross-domain, cross-forest (FSP) and non-GC `memberOf` gaps.
- **Shared kit files:** a change to one copied kit file reaches every tool that ships a copy. The checklist should require the read-only/writer guard to run against the kit itself, not just the tool that uses it.
- **Privileged-group lists:** they should be kept in one canonical list, tested for parity, and checked against Learn (498/ERODC, Exchange groups).
- The checklist only covers tools that change things. It says nothing about read-only tools that recommend a change for a human to make, such as "add X to group Y". It should require that: a recommendation never names a privileged group; any uncertainty in the privilege check (unreadable parents, depth limit, multi-domain forest or trusts, lookup failure) makes the recommendation carry an approval gate rather than dropping it silently; name-based detection of privileged groups with non-well-known RIDs is listed as a known limitation.

### SQ-006 CHECKLIST GAPS (personal-data)
- CSV formula injection is not on the checklist. Neutralising leading `= + - @` (and tab/CR) in any CSV cell taken from AD, event logs or Graph should be listed next to the HTML-encoding item, with a pointer to the existing helper in FolderAccess-Check/M365-UserQuickCheck.
- The checklist covers new tools' output folders in .gitignore, but not default output folders that sit inside the repo tree (`<scriptRoot>\Reports`) for existing tools that start writing more client data. Add: "if a change adds client data to an output, confirm that output's default location is gitignored."
- HTML encoding should state the context. Values placed in attributes (title=, href=, data-*) need quote escaping, and a `& < >`-only encoder like Convert-Esc is safe only in element content.

### SQ-007 CHECKLIST GAPS (personal-data)
- (1) Ticket notes and clipboard text are a paste channel just like HTML. The checklist should require free-text from tenants and error messages to be mapped to fixed wording or redacted in notes, and should say explicitly that CaseKit's paste-safe mode does not cover the headline. (2) "Encode every value" should also cover plain-text sinks (console, note): strip control characters, CR/LF and ANSI escape sequences from attacker-controlled strings such as rule names, display names and subjects. (3) "Disconnect when done" should say to disconnect only the session the tool opened (by ConnectionId), never every session in the window. (4) Raw exception text (MSAL/Graph/EXO) should be treated as possibly containing personal data whenever it leaves the console. (5) The wrong-tenant check when several sessions are open (D-002) is not covered.
- The checklist does not list the ticket note or clipboard as an output channel. Its rules should say what may go there (checked identity, sign kinds, outside domains) and what never does (raw error text, delegate, forwarding or trace addresses, rule conditions).
- Exception and error text should be treated as client data: it can carry addresses and tenant details. It should stay in console and local reports and never go into paste-bound output.
- Text written by whoever controls the mailbox (rule names, folder names, addresses) should be sanitised for control characters before it reaches the console, the note or the clipboard. Today the checklist covers only HTML encoding.

### SQ-016 CHECKLIST GAPS (personal-data)
- Data minimisation for server-side queries. The checklist covers what is stored, not what is fetched. This item asks Microsoft for every rule, permission and forwarding change in the whole tenant (up to 50,000 records with other users' UPNs and IPs) and filters on the workstation. The spec accepts this on purpose, to avoid false all-clears. The checklist should say that bulk fetches of other users' data must not be persisted, logged or returned through -PassThru, and that this has to be checked.
- Attacker-chosen free text (rule names, display names) that goes into the ticket note can carry PII or addresses. The checklist covers HTML encoding of such values but says nothing about masking them in paste-safe outputs (notes and clipboard).
- Raw error text shown on the console or written to HTML can carry addresses and IPs. The checklist does not say whether that is acceptable. Today only the convention "not in the note" exists.

### SQ-009 CHECKLIST GAPS (personal-data)
- Log location when a tool runs from a UNC share, mapped drive or synced SharePoint folder. The checklist says "output stays on the machine it ran on" but does not require a fallback to a local folder for `$PSScriptRoot`-relative defaults. FolderPermissionManager and M365-SyncedUserFixes each handle this differently.
- Spreadsheet formula injection in CSV exports. The checklist covers HTML encoding but not the CSV guard (= + - @ tab CR) or a regression test for it.
- File permissions and retention of client-data logs: inherited ACLs, no automatic deletion, and a required README note on both.
- Change-log writes that fail after the change: the audit row is lost even though fail-closed was checked up front.
- Add a rule for client-data logs and fallback copies written to a share/UNC path, a removable drive or %TEMP%: default to local fixed storage and warn otherwise, and the README covers cleanup and retention.
- Add CSV formula-injection guarding for exported client values (the checklist covers HTML encoding but not CSV).

### SQ-009 CHECKLIST GAPS (destructive-operations)
- Wrong-target resolution: how a target name is normalised (FQDN vs short name, empty/null target, IP) must never silently fall back to the machine the tool runs on.
- Identity matching for removals: "already absent / no change" on a Remove or revoke must be proven by SID, not a string compare, and an unresolvable principal must fail, not pass.
- Fail-closed probes must test the exact file that will be written (Excel and share locks), and when a post-change log write fails, the before-state must still be saved to a fallback location.
- Prompt behaviour in non-interactive hosts (`-NonInteractive`, scheduled tasks, RMM) and under an explicit `-Confirm`; log writes must use `-Confirm:$false -WhatIf:$false`.
- Dry-run output must not claim a log was written.
- Post-change verification: the re-read state must agree with the intended outcome before reporting Done/PASS.
- Test suites for destructive tools need a backstop mock of the transport/ADSI/write layer so one missed mock cannot touch the dev machine. Tests should not use `$env:COMPUTERNAME` as the target for write wrappers.
- Agents running real reads against this machine's configuration during a build (process rule, not a code check).
- When the check-by-name and the act-by-path can resolve differently, the change should act on the same identifier it matched (SID).
- Tests that pass only under pwsh 7 when the tool runs on Windows PowerShell 5.1: for example `Export-Csv -Append` behaviour, especially into a 0-byte file created by a probe.
- Result reconciliation when a write call throws after it has committed (remote timeouts): the logged Result should match the re-read state.
- When the scope preview fails, the tool should not go ahead silently under -Force.
