# SQ-022 · FolderPermissionManager: enforce the D-044 Copy refusals inside the core's Copy-FolderPermission

- status: done
- size: M
- risk: high
- touches: FolderPermissions.Core.ps1 (Copy-FolderPermission, moved refusal helpers), FolderPermissionManager-GUI.ps1 (WPF app: drop its copies of the helpers, pass the Deny acknowledgement), core and app test suites, README
- depends-on: SQ-018 (the code lives on `squad/SQ-018-fpm-wpf-changes`; build from main after SQ-018 merges)
- related: SQ-023 (same kind of move for whole-tree take ownership), SQ-024 (`..` segments, shares ConvertTo-ComparablePath), SQ-021

## Summary (plain English)
The WPF app refuses to copy permissions onto Windows folders, admin shares, SYSVOL/NETLOGON and
similar places, but that check lives only in the window. The function that really does the copy
accepts any folder. This item moves the check into that function, so the copy itself refuses a
protected folder and checks again just before it writes. Whatever calls it, a protected folder
can't receive copied permissions. It also makes the copy refuse Deny entries the technician was
never warned about (Q2).

## What users will be able to do
Nothing new to click. In the WPF app, Copy Permissions To... behaves as it does after SQ-018:
protected targets are still refused before anything starts. Two things change:
- **A late check.** A target swapped for a junction into a protected folder after the check, but
  before the write, is refused at write time. Its result row says why, and nothing is changed.
- **Unwarned Deny entries (if Q2 = A).** Say a Deny entry is added to the source after the window
  loaded its permissions. The copy is refused, and nothing goes out without the Deny warning.

The old command-line script is not affected. It has no copy step (D-035, pinned by
`AC15_CliHasNoCopyStep_ScriptHasNoCopyCallsStatically`). The browser GUI picks up the refusals
automatically because it calls the same core function. It gets no acceptance criteria, because
it is removed after the SQ-018 lab test (owner, 2026-10-19).

## Acceptance criteria
Tests go in a new `FolderPermissionManager/Tests/CopyPermissions.Refusal.Tests.ps1`, except AC1
and AC10. AC1 is a static check over both scripts. AC10 goes in the WPF app's changes suite
(`FolderPermissionManager-AppChanges.Tests.ps1` on the SQ-018 branch).

1. AC1_CopyRefusalHelpersLiveInTheCore: `FolderPermissions.Core.ps1` defines
   `Get-CopyTargetRefusal` and `Get-CopyTargetResolvedRefusal`. `FolderPermissionManager-GUI.ps1`
   no longer defines either one and still calls both. The test parses each file's AST (FunctionDefinitionAst /
   CommandAst).
2. AC2_CopyRefusesProtectedTargetsByText: Given an ordinary source with explicit Allow rules and
   each of these targets: `\\fs01\ADMIN$\x`, `\\fs01\SYSVOL\corp.local\scripts`,
   `\\fs01\netlogon`, `\\fs01\PRINT$\x64`, `\\fs01\IPC$`, `\\fs01\D$`, `C:\Windows\Temp`,
   `C:\Windows\`, `C:\\Windows`, `\\?\C:\Windows.`, `C:\Program Files\App`,
   `C:\ProgramData\Vendor`, `D:\` and `C:\Users`. `Get-AclItemType` is mocked to 'Folder' and the
   final/long path reads are mocked to return the typed path. When `Copy-FolderPermission` runs,
   then each target gets one row with Result `Failed` and an ErrorText that holds the refusal
   reason and ends with "Nothing was changed.". `Set-Acl` and `Save-AclBackup` are called 0 times.
   This is one data-driven `It` with `-ForEach`.
3. AC3_CopyRefusesATargetThatReallyLeadsIntoAProtectedFolder: Given a target folder in
   `$TestDrive` whose final path (`Get-Win32PathName -Kind Final`, mocked) is
   `C:\Windows\System32`, then its row is `Failed` and names the real location. Run the same test
   case with only the long-name read (`-Kind Long`, an 8.3 name) returning `C:\Program Files`. In
   both cases `Set-Acl` is not called.
4. AC4_CopyFailsClosedWhenTheRealLocationCannotBeRead: Given an existing target whose final path
   read throws, then its row is `Failed` with the "could not tell where it really is" wording
   from `Get-CopyTargetResolvedRefusal` plus "Nothing was changed.", and `Set-Acl` is not
   called.
5. AC5_CopyMixedTargets_OnlyAllowedTargetsAreBackedUpAndWritten: Given the targets
   `[<TestDrive>\ok, C:\Windows\Temp]`, then the first row is `Done` and the second is `Failed`.
   `Set-Acl` runs once, on the first target only, and the backup file lists only the first.
6. AC6_CopyRefusalStandsUnderWhatIf: Given `-WhatIf` and the targets
   `[<TestDrive>\ok, C:\Windows\Temp]`, then the rows are `Skipped (WhatIf)` and `Failed` (the
   refusal is shown, as for whole-tree take ownership). There is no `Set-Acl`, no backup and no
   change-log write.
7. AC7_CopyChecksTheRealLocationAgainJustBeforeTheWrite: Given a target whose final path read
   returns the ordinary folder at the plan step and `C:\Windows` on the next read, with the
   underlying `Get-Win32PathName` mocked rather than the guard, then the row is `Failed` with the
   refusal and "Nothing was changed.", and `Set-Acl` is called 0 times.
8. AC8_CopyLeavesOrdinaryTargetsAlone: `Get-CopyTargetRefusal` and
   `Get-CopyTargetResolvedRefusal` (with resolution mocked to the same path) return `$null` for
   these four targets:
   - a folder under a user profile (`C:\Users\alice\Documents\Proj`)
   - a `$TestDrive` folder
   - `\\fs01\Data\Dept`
   - `\\fs01\D$\Shares\Data`, a folder inside an `X$` share. SQ-018 allows this; only the bare
     `X$` root is refused.

   With these four targets, `Copy-FolderPermission` returns `Done` for each.
9. AC9_CopyRefusesDenyEntriesTheCallerDidNotAcknowledge *(only if Q2 = A)*: Given a source with
   an explicit Deny entry and no `-AllowDeny`, then every target row is `Failed`. Its ErrorText
   names the source and each Deny entry (`Format-PermissionRule`) and ends with "Nothing was
   changed.". `Set-Acl` is not called. Given the same call with `-AllowDeny`, the rows are
   `Done`. The Deny decision uses the same `Get-Acl` read whose rules are copied.
10. AC10_AppPassesAllowDenyOnlyAfterTheDenyConfirm *(only if Q2 = A)*: In the WPF app, a copy
    whose destructive Deny confirm was accepted calls `Copy-FolderPermission -AllowDeny`. This
    covers both the AC48 case and the "could not be checked" `-DenyUnchecked` case. A plain copy
    (no Deny confirm shown) calls it without `-AllowDeny`. `Copy-FolderPermission` is mocked,
    and the test asserts its bound parameters.

## Out of scope
- **The old CLI** (`FolderPermissionManager.ps1`). It has no copy path (D-035), and this item
  does not add one.
- **The browser GUI** (`FolderPermissionManager-WebGUI.ps1`). There are no ACs and no UI changes
  (owner, 2026-10-19). It inherits the core refusals as `Failed` rows. If Q2 = A, it can no longer
  copy a source that has Deny entries, because it never passes `-AllowDeny`. Its existing tests
  must still pass.
- **D-044 confirms in the core.** The confirms for Deny sources, drive/share roots and "resolves
  somewhere other than typed" stay in the WPF app, because the core cannot ask. Only refusals
  move, plus the Deny acknowledgement in Q2.
- **Server-side checks for Copy targets**: the share's server folder (NetShareGetInfo), and
  junctions on the server (D-045). See Q3. The functions sit in the WPF app until SQ-023 moves
  them.
- **`.` / `..` segments in typed paths.** That is SQ-024. This item reuses
  `ConvertTo-ComparablePath` unchanged.
- **Wording changes to the refusal texts.** The text moves as it is, so the WPF app's existing
  tests keep passing.

## Approach
- **Precondition.** SQ-018 is merged to main. The spec was drafted without branch access. The
  helper names and behaviour come from `squad/specs/SQ-017.md`: "Revision notes, SQ-018", AC50,
  lead ruling 3, fix round 1 and the "Assumed by the squad" list. Before writing tests, the
  builder confirms against the merged code:
  - the exact names and signatures of `Get-CopyTargetRefusal` and
    `Get-CopyTargetResolvedRefusal`;
  - which helpers they call (`Get-TreeOwnershipRefusal`, `Get-HighImpactRootRefusal`,
    `Get-AppProfilesDirectory`, `Get-Win32PathName`, `ConvertTo-ComparablePath`);
  - the copy work call in the app.
- **Move.** Move both helpers, unchanged, from `FolderPermissionManager-GUI.ps1` into
  `FolderPermissions.Core.ps1`, in the copy region next to `Copy-FolderPermission`. Then delete
  the app's copies. Other helpers they need move too, unless they are already in the core
  (`Get-HighImpactRootRefusal` and `Get-AppProfilesDirectory` moved in SQ-018 AC53a).
  - The app's background pool copies core functions automatically
    (`Initialize-BackgroundPool`).
  - A moved helper might use a script-scope variable. If so, it must be one that
    `Get-CoreScriptVariableNames` copies into the pool, or AC8d (SQ-017 AC-R2) fails.
- **Enforce, early.** In `Copy-FolderPermission`'s `-Plan` block, after the existing "is a file"
  check, call the text refusal and then the resolved refusal. A refusal returns
  `[PSCustomObject]@{ Result = 'Failed'; ErrorText = "$refusal Nothing was changed." }`, so the
  item is never backed up or passed to ShouldProcess. This is the pattern already in
  `Invoke-SingleItemAclChange`'s Plan contract and `Invoke-TreeOwnershipChange` (refusal before
  ShouldProcess, `Result 'Failed'`).
- **Enforce, late.** In the `-Change` block, run the resolved refusal again just before `Set-Acl`.
  If it refuses, throw `"$refusal Nothing was changed."`. `Invoke-SingleItemAclChange`'s catch
  writes the `Failed` row, and the SDDL before and after are equal, so no "partly changed" text is
  added. This mirrors the late re-check in `Invoke-TreeOwnershipChange`, and closes the SQ-018
  open minor: "Copy checks a target's real location ... only in the background lookup".
- **Deny acknowledgement (Q2 = A).**
  - Add `[switch]$AllowDeny` to `Copy-FolderPermission`.
  - After `$sourceRules` is built, any rule with `AccessControlType -eq 'Deny'` and no
    `-AllowDeny` gives one `Failed` row per target, then a return. No target is read or written.
  - Existing core tests that copy the four-rule source (which has a Deny rule) add `-AllowDeny`
    to their call. This is a contract change that the spec asks for; nothing is asserted less.
  - The WPF app passes `-AllowDeny:$denyConfirmed` from the confirm it already shows.
- **Help.** Update `Copy-FolderPermission`'s `.DESCRIPTION`: name D-044, the early and late
  refusal, and `-AllowDeny`. Add a `.PARAMETER AllowDeny`. The README's "Copy Permissions To..."
  paragraph adds that the copy itself re-checks every target just before it writes. Follow
  SQ-018's README wording, where the refusal list already appears.
- **No new Microsoft facts.** This item adds none. The moved helpers carry their Learn citations
  with them.

## Test plan
- Pester 5 under `pwsh`. Load the core by dot-sourcing `FolderPermissions.Core.ps1
  -LoadFunctionsOnly` (as `CopyPermissions.Tests.ps1` does). Folders live in `$TestDrive` only.
- **Mocks:**
  - `Set-Acl` (backstop that records calls), and `Get-Acl` seeded with SDDL (the
    `CopyPermissions.Tests.ps1` pattern).
  - `Get-AclItemType` for paths that do not exist in the test.
  - `Get-Win32PathName` for final and long paths.
  - `Get-AppProfilesDirectory`, returning the literal `C:\Users`, so the real
    GetProfilesDirectoryW P/Invoke never runs.
  - A throwing `Invoke-AclTool` stub, and `Save-AclBackup` / `Write-PermissionChangeLog` where
    counted.
- **Expected values are literals**, never built from `$env:SystemRoot`. This was a minor review
  finding in SQ-018. Under WOW64 or a non-C: system drive, the text check still compares with this
  machine's variables. Tests use `C:\Windows`, but they must not rely on `%SystemRoot%` being
  `C:\Windows`. Where that matters, mock `[Environment]` reads through a seam the helper already
  has, or pick UNC rows.
- **Edge cases covered:**
  - odd spellings (AC2 rows: trailing `\`, doubled `\`, `\\?\` prefix, trailing dot, lower-case

  - mixed lists (AC5)
  - WhatIf (AC6)
  - a time-of-check/time-of-use swap driven through the path read, not by flipping the guard
    (AC7)
  - fail closed (AC4)
  - ordinary profile and share folders not refused (AC8)
- **Existing suites must pass unchanged:** `CopyPermissions.Tests.ps1` (core and WebGUI parts),
  `FolderPermissions.Core.Tests.ps1`, the App and AppChanges suites, and
  `FolderPermissionManager.CliNoCopy.Tests.ps1`. Only two additions are allowed: a
  `Get-AppProfilesDirectory` mock, and `-AllowDeny` on Deny-source calls if Q2 = A.
- **Gates:** `Tests\Test-ScriptParse.ps1` (under `powershell.exe`) and the full
  `Tests\Invoke-AllTests.ps1`. Also run `Tests\ScriptEncoding.Tests.ps1` if a moved helper carries
  non-ASCII text, and `Tests\PSVersionFloor.Tests.ps1`, because the core's version floor must not
  rise.

## Decisions

- D-052 (2026-10-19 plan, Q2 = A): Copy-FolderPermission refuses a source with explicit Deny entries unless the caller passes -AllowDeny; the WPF app passes it only after its Deny confirm. AC9 and AC10 are in scope.
- D-053 (2026-10-19 plan, Q3 = A): server-side checks for remote Copy targets (the share's real folder against D-036, D-045 junctions) are a separate item, SQ-026, after SQ-023. Not in SQ-022.
- D-031: Copy is add only, with one `Set-Acl` on the target.
- D-035: the CLI has no copy step.
- D-036: protected folders and drive roots.
- D-044: protected Copy targets are refused. Deny sources, roots, and targets that resolve
  elsewhere get confirms.
- 2026-10-19: the browser GUI is removed after the SQ-018 lab test; no ACs for it.

### Assumed by the squad
- **The CLI needs no change.** The backlog text says "the CLI still needs it", but
  `FolderPermissionManager.ps1` never calls `Copy-FolderPermission` (D-035; static test
  `AC15_CliHasNoCopyStep_ScriptHasNoCopyCallsStatically`). The core enforcement protects the WPF
  app's write (the late re-check) and any future caller.
- **No `-AllowSystemFolder`-style override for Copy.** D-044 says "refused", the WPF app has no
  override, and the CLI has no copy.
- **A refused target is `Result 'Failed'`** with "Nothing was changed.", not a new Result value.
  This is the same as whole-tree take ownership refusals and the "is a file" copy refusal, and
  `Get-ChangeResultMessage` already groups `Failed` rows.
- **The refusal is shown under `-WhatIf` too.** A dry run then shows what the real run would do.
  The Plan block runs before ShouldProcess, as in `Invoke-TreeOwnershipChange`.
- **A missing target stays `Skipped (not found)` in the core.** The WPF app refuses it earlier
  (SQ-018 fix round 1). Either way nothing is written, and changing the core's row would break
  `CopyPermissions.Tests.ps1`.
- **A source with no explicit rules returns before any target check.** Nothing is written, so
  there is nothing to refuse.
- **The refusal texts move unchanged.** The WPF app's tests assert them.
- **A Copy onto a drive root is refused (lead ruling 3), and a Copy onto a non-admin share root is
  allowed in the core.** The share-root confirm stays in the window, because the core cannot ask.
- **Kept as a separate item, not merged with SQ-023.** The two touch different work functions
  (`Copy-FolderPermission` vs `Invoke-TreeOwnershipChange`) and different helpers. Together they
  would be L, touching three areas: core copy, core tree and app. Build them one after the other,
  because both edit the core and the GUI.

- **Added during the build (2026-10-20 run):**
  - `Get-TargetRootKind` moved to the core with the two refusal helpers (they need it); the three
    names left `$script:WorkHelperFunctions`, the pool loads them as core functions.
  - `[bool]$AllowDeny` is the last parameter of `$script:CopyPermissionsWork`, after `$CorePath`
    (a `[bool]` can't take the `$null` five-argument callers pass); five-argument callers get the
    safe refusal.
  - New helper `Get-CopyDenyRefusal` builds the Deny refusal text (squad-drafted wording); it accepts
    and skips null rules (in the pwsh test pool `Get-Acl().Access` can come back null).
  - The late check re-runs only the resolved (disk) refusal; the text check can't change.
  - `Get-Win32PathName` reads in `Get-CopyTargetResolvedRefusal` are wrapped in try/catch (fail closed).
  - Test edits: AC10's mock body read `$PSBoundParameters` (empty in Pester 5.7 mocks) and was
    changed to `$PesterBoundParameters`; `-AllowDeny` added to a third Deny-source row
    (CopyPermissions.Tests.ps1 ~339). Code and spec reviewers confirmed no assertion weakened.

## Risk and safety notes
- **Destructive-operations profile applies in full.** Copy writes inheritable ACEs. On a root,
  they reach the whole tree.
- **Canonicalise before the check, and fail closed.** AC2 covers odd spellings and AC4 covers an
  unreadable real location.
- **Re-check just before the write** (AC7). This answers the checklist gap "every target check
  that reads the disk runs again just before the write, for every write path (Copy as well as take
  ownership)".
- **Same read for the decision and the write.** The Deny decision uses the `Get-Acl` read whose
  rules are copied (AC9). This follows "The old value logged and backed up is the same read the
  safety decision used".
- **Safety rules live in the core work function**, so no front end can bypass them. This answers
  the checklist gap "Safety rules enforced only in one UI must also be enforced in the shared core
  work functions".
- **Every write cmdlet is mocked.**
  - `Set-Acl` has a recording backstop, and `Invoke-AclTool` a throwing stub.
  - GetProfilesDirectoryW and the final-path read are mocked; there are no reads outside
    `$TestDrive`.
  - No test targets `$env:COMPUTERNAME` or a real share.
- **Lab test by hand after merge:**
  - a copy in the WPF app onto `\\server\SYSVOL\...` and onto a junction that points into
    `C:\Windows`. Both should be refused, with nothing changed.
  - With Q2 = A: add a Deny on the source after the window loaded it, then copy. The copy should
    be refused.

## Open questions for the owner
- **Q1. Build this at all, now that the CLI has no copy?** (scope) The backlog's main reason, "the
  CLI still needs it", is not true (D-035). What is left is the late re-check before the write,
  and protection for any future caller.
  - **A) Build it as specified (recommended).** It closes the SQ-018 open minor (the real location
    is checked only at lookup time, not at the write), and protects any future caller.
  - **B) Drop SQ-022.** The WPF app's lookup-time refusal remains the only guard; the
    swapped-junction window stays open.
  - **C) Merge it into SQ-023** as one "core enforces every WPF safety check" item. That item
    becomes L and should then be split again.
- **Q2. Should the copy refuse Deny entries the technician wasn't warned about?** (safety, risk
  profile)
  - **A) Yes (recommended).** `Copy-FolderPermission` refuses a source with Deny entries unless
    the caller passes `-AllowDeny`. The WPF app passes it only after its Deny confirm. This closes
    the SQ-018 minor where a Deny added after the window loaded the source goes out unwarned. The
    browser GUI can no longer copy Deny sources before it is removed.
  - **B) No.** Deny warnings stay in the window only. AC9 and AC10 are dropped, and the gap stays
    as a known minor.
- **Q3. Should Copy targets on a remote share also get server-side checks?** (the share's real
  server folder vs D-036, and D-045 junctions behind the share) Today a share like `\\fs01\Win`
  that points at `C:\Windows` on the server is not refused as a Copy target. SQ-018 left this to
  "follow-up SQ-022".
  - **A) Yes, as a new item after SQ-023 moves those helpers into the core (recommended).**
    SQ-022 stays M. The new item reuses SQ-023's core functions.
  - **B) Yes, inside SQ-022.** This makes it depend on SQ-023 and grows it to L.
  - **C) No.** D-045 stays whole-tree only, as decided. Inheritable copies onto a share that
    secretly points into Windows remain possible.

## Review notes (2026-10-20 run)
All four reviewers passed. Minor findings, not fixed in this item:
- Risk: README / AllowDeny help / refusal text promise that a Deny added after the window loaded is
  refused; that is only true when the window showed no Deny at all (`-AllowDeny` is a boolean).
  Reword; the real fix is filed as SQ-038.
- Risk: "A Deny ... blocks access even where another permission allows it" overstates it for
  inheriting children (explicit Allow beats inherited Deny, order-of-aces-in-a-dacl); scope it and
  add a test.
- Risk/UI: the next step "Reload ... and copy again" can't help the browser GUI (never passes
  -AllowDeny); the wording also reads as blaming the tech. Suggested: "it now has a Deny (<list>)
  that the warning did not show ...".
- Risk: the existing CopyPermissions and Core suites now reach the real `Get-Win32PathName`
  P/Invoke on `$TestDrive` paths (no UNC guard; a runner whose TEMP is under C:\Windows\Temp would
  see every copy refused). Mock it to return `$Path` or add a UNC guard (a third allowed edit).
- Risk (follow-up): residual window between the late re-check and the path-based `Set-Acl`, which
  rewrites the whole DACL read earlier; a handle-based write would close it.
- Risk (follow-up): refusals name the cause generically, not the reparse kind/tag (wording predates).
- Risk (follow-up): the core does no DFS lookup, so README's "whatever calls it" overstates for DFS
  paths from callers other than the WPF app; fold into SQ-026 or narrow the README.
- UI (follow-up): tie the confirm-shown condition and `$denyConfirmed` together with a comment/test.
- Code (follow-up): no direct test of `Get-CopyDenyRefusal -Rule $null / @()`.
- Spec (follow-up): the browser GUI now fails every Deny-source copy with only the row text.
