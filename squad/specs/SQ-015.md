- status: ready

- risk: high
- touches: `FolderPermissionManager/FolderPermissions.Core.ps1` (copy logic, added by SQ-008a),
  `FolderPermissionManager-GUI.ps1` (`/api/replicate` handler, "Copy Permissions To..." modal and

- depends on: SQ-008 (core file, single-item SDDL backup, change log, `Invoke-AclTool`) and

## Summary (plain English)
The "Copy Permissions To..." action has four bugs. With "Apply recursively" ticked, it first
wipes every custom permission on every subfolder and file under the target. It then turns
"Read & execute" into a broken command. Without the tick, it copies the source folder's
inherited permissions as if they had been set by hand, so later changes higher up the share
no longer reach the target. It also fails on folder names that contain square brackets, such as
`HR [old]`. After this fix, copying permissions copies exactly the permissions set on the
source folder and nothing more. It never removes anything below the target, and it works with
any folder name.

## What users will be able to do
- Copy a folder's permissions to one or more other folders. The target gets exactly the
  permissions set directly on the source folder: the same people, the same level of access
  (Read & execute stays Read & execute; special combinations stay as they are), allow or deny,
  and the same "applies to" settings.
- Permissions the source only inherits from its parent are not copied. If the source has no
  permissions of its own, nothing changes, and the tool says so: "Nothing to copy: <source> has
  no permissions of its own. All of its permissions come from <parent>."
- Permissions already on the target stay. Copying only adds.
- Subfolders and files under the target that inherit permissions get the new ones automatically,
  as they would in Explorer. What happens to subfolders that block inheritance depends on Q1.
  With the recommended answer, they are left alone and the result says so.
- Folder and file names with `[` or `]` work everywhere in the tool: viewing, changing, copying
  and exporting.
- If the target is a file, nothing changes, and the result reads "<path> is a file. Copy
  permissions copies to folders only."

1. AC1 (wrong rights, regression): Given a source ACL with four explicit rules for different
   well-known SIDs: Allow `ReadAndExecute, Synchronize`; Allow `Modify, Synchronize`; Allow
   `Write, ReadData` (a combination the old `switch` mapped to `R`); and Deny
   `ReadData, AppendData` (special rights), when `Copy-FolderPermission` runs, then the ACL
   passed to the mocked `Set-Acl` contains, for each source rule, one explicit rule with an
   identical `FileSystemRights`, `AccessControlType`, `InheritanceFlags` and
   `PropagationFlags`.
2. AC2 (malformed icacls argument, regression): Given the same source as AC1, when
   `Copy-FolderPermission` runs, then `Invoke-AclTool` is never called. No `icacls /grant` or
   `/deny` is built, so an array-valued rights string cannot happen again.
3. AC3 (subtree wipe, regression): Given a target folder in `$TestDrive` with a subfolder, when
   `Copy-FolderPermission` runs, then `Set-Acl` is called only with `-LiteralPath` equal to the
   target. No call is made for any descendant, and `Invoke-AclTool` is never called with
   `/reset`.
4. AC4 (no `/reset` anywhere, static regression guard): Given every `.ps1` in
   `FolderPermissionManager/` (excluding `Tests/`), then none contains the string `/reset`.
5. AC5 (inherited rules made explicit, regression): Given a source ACL built from SDDL with one
   explicit Allow rule and one inherited (`ID` flag) Allow rule for a different SID, when
   `Copy-FolderPermission` runs, then the target ACL passed to `Set-Acl` has the explicit rule
   and has no rule for the inherited rule's SID.
6. AC6: Given a source whose rules are all inherited, when `Copy-FolderPermission` runs, then
   `Set-Acl` is not called, the entry's `Result` = `Skipped (nothing to copy)`, and the message
   starts "Nothing to copy: <source> has no permissions of its own."
7. AC7: Given a target with an explicit rule for a SID the source does not have, when
   `Copy-FolderPermission` runs, then that rule is still in the ACL passed to `Set-Acl` (adds,
   never replaces).
8. AC8: Given a target that already has every explicit source rule, when
   `Copy-FolderPermission` runs, then `Set-Acl` is not called and `Result` =
   `Skipped (nothing to copy)` with `Detail` "Already has these permissions; nothing changed."
9. AC9 (brackets, regression): Given folders `HR [old]` (source) and `Archive [2024]` (target)
   in `$TestDrive`, when `Copy-FolderPermission` runs with the real `Get-Acl` and a mocked
   `Set-Acl`, then the target is found, `Set-Acl` is called once with `-LiteralPath` equal to
   the exact target path, and `Result` = `Done`.
10. AC10 (wildcard sibling, regression): Given `$TestDrive` contains a folder `HR o` but no
    `HR [old]`, when `HR [old]` is a copy target, then the entry is `Skipped (not found)` and
    `Set-Acl` is never called. Under the old `-Path` code, `[old]` matched `HR o`.
11. AC11 (`-Path` sweep, static regression guard): Given the AST of every `.ps1` in
    `FolderPermissionManager/` (excluding `Tests/`), then every call to `Test-Path`, `Get-Item`,
    `Get-ChildItem`, `Get-Acl`, `Set-Acl` or `Resolve-Path` that passes a path uses
    `-LiteralPath`. None uses `-Path` or a positional path argument. The failure message lists
    file, line and command.
12. AC12: Given a target that is a file in `$TestDrive`, when `Copy-FolderPermission` runs, then
    `Set-Acl` is not called and the entry is `Failed` with the error "<path> is a file. Copy
    permissions copies to folders only."
13. AC13: Given a successful copy of two rules, then the change-log entry has
    `Action` = `Copy permissions`, `ItemType` = `Folder`,
    `Detail` = `Copied from <source>: Allow Modify for <identity>; Allow Read & execute for

## Approach
- **Core** (`FolderPermissions.Core.ps1`, `Copy-FolderPermission` as added by SQ-008a; if the
  landed name differs, use what landed):
  - Read the source once: `Get-Acl -LiteralPath`. Keep `@($sourceAcl.Access | Where-Object {
    -not $_.IsInherited })`. If none remain, return `Skipped (nothing to copy)` for each target
    (AC6).
  - Per target (try/catch, then `continue`, as today): check `Test-Path -LiteralPath -PathType
    Container`. If the path is missing, return `Skipped (not found)`. If it is a leaf, return
    `Failed` (AC12). Then `Get-Acl -LiteralPath`. Add each source rule whose identity, rights,
    type and flags are not already present among the target's *explicit* rules, using the same
    comparison as the existing `$exists` block. If none were added, return
    `Skipped (nothing to copy)` (AC8). Otherwise go through SQ-008's single-item backup, then
    `ShouldProcess`, then `Set-Acl -LiteralPath`, then read back for `NewValue`.
  - Rules are added as the source's `FileSystemAccessRule` objects (exact rights and flags). The
    `switch -Wildcard` mapping, the `icacls /reset /T` call and the per-rule `icacls /grant|/deny
    /T` calls are deleted. Windows passes inheritable entries down to children that inherit
    when the DACL is set (verify, below), which matches Explorer and the existing Add permission.
  - Remove `-Recurse` from `Copy-FolderPermission` (Q1 = A). With Q1 = B/C, see the alternatives
    after AC14.
  - `Detail` sentence: rights shown with the same friendly names the GUI's Add permission modal
    uses (find the existing label map in the GUI JS and reuse its wording; for flag combinations
    without a label, show the .NET string).
- **GUI**: the `/api/replicate` handler stays thin (SQ-008 pattern) and stops reading
  `recursive`. Modal: remove the "Apply recursively" checkbox. Replace the help line with "Adds
  the current folder's own permissions to each folder you list (one per line). Nothing is
  removed. Subfolders that inherit permissions get them too." The JS shows `r.message`.
- **`-LiteralPath` sweep** in the GUI (about 40 provider-cmdlet calls: `Get-FolderAcl`,
  `Get-FileAcl`, `Invoke-ExportReport`, `Get-Children`, `Get-Files`, robocopy validators, and
  every `Test-Path`) and in the CLI. The behavior is the same apart from brackets.
  `Join-Path`/`Split-Path` are string operations and are left as they are.
- **README**: update "Replicate parent permissions" to describe add-only copy and the
  inheritance note. Add a "Known limitation: subfolders that block inheritance are not changed"
  line.
- **Microsoft facts to verify on Learn and cite** (root CLAUDE.md; `.NOTES` REFERENCES):
  - `SetNamedSecurityInfo`/`SetSecurityInfo` remarks: setting a DACL automatically propagates
    inheritable ACEs to existing child objects. This is the foundation of Q1 = A.
  - `Get-Acl`/`Set-Acl`/`Test-Path` `-LiteralPath` ("no characters are interpreted as
    wildcards") and `about_Wildcards` (`[ ]` is a character range).
  - `FileSystemAccessRule`, `IsInherited`, and the SDDL ACE flag `ID` (inherited) used to build
    the AC5 fixture.
  - `icacls` `/reset` (only cited if Q1 = C).
- Plans: `docs/plans/2026-03-20-folder-permission-manager-gui.md` (the original
  `/api/replicate` design: "replicating parent permissions to child folders").
  `docs/superpowers/specs/2026-04-07-folder-permission-manager-v2-design.md` keeps the behavior
  "identical to v1". Neither defines the recursive semantics, hence Q1.

### Assumed by the squad
- **Only the source's explicit rules are copied (AC5).** Evidence: the existing recursive
  branch already skips `IsInherited` (`FolderPermissionManager-GUI.ps1` line 377), and the
  SQ-008 analyst listed copying inherited rules as a bug. Freezing inherited rules as explicit
  stops later parent changes from reaching the target.
- **Rules are copied as .NET rule objects, not through `icacls /grant`.** This is exact for every
  rights combination and allow/deny, with no mapping table to get wrong, and it matches every
  other change in the tool (Add/Remove permission use `Set-Acl`).
- **Copy adds and never replaces at the target (AC7).** Evidence: today's non-recursive branch
  is add-only (`if (-not $exists) { AddAccessRule }`).
- **No `Set-Acl` when nothing would change (AC8).** It avoids a pointless re-propagation over a
  large tree and an empty change-log row.
- **New `Result` value `Skipped (nothing to copy)`.** It extends SQ-008's pinned value set (the
  columns are unchanged). A distinct value lets the log tell "nothing done" apart from `Done`.
- **File targets are refused (AC12).** Today they fail with a .NET error, because
  inheritance-flagged rules cannot go on a file. The modal and the action are folder-oriented.
- **The `-LiteralPath` sweep covers the whole folder, not only copy (AC11).** The same bug breaks
  viewing and exporting `HR [old]`. The change is mechanical and low-risk, and a static guard
  stops it from returning.
- **The CLI gets only the `-LiteralPath` change.** Its replicate logic depends on SQ-008 Q3.
- **Status and modal wording** is drafted in plain English by the squad (SQUAD.md conventions).
  Michael can adjust it at review.
