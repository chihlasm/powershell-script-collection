# SQ-023 · FolderPermissionManager: the command line gets the server-side share checks (D-045)

- status: ready
- size: M
- risk: high
- depends-on: SQ-018, SQ-024 (build from main after both merge; the four functions only exist on `squad/SQ-018-fpm-wpf-changes` until SQ-018 merges)
- touches: `FolderPermissionManager/FolderPermissions.Core.ps1` (whole-tree target checks),
  `FolderPermissionManager/FolderPermissionManager-GUI.ps1` (WPF app: functions move out, calls stay),
  `FolderPermissionManager/FolderPermissionManager.ps1` (CLI: next-step text, help),
  `FolderPermissionManager/README.md`, the FolderPermissionManager test suites
- risk profiles: destructive-operations (in full), system-configuration (machine-state reads behind seams; lab check on a real server)

## Summary (plain English)
When a tech takes ownership of a whole folder on a file share, the WPF app first asks the file
server where the share really lives on its disk and checks that folder path for junctions and
for Windows or profile folders (D-045). The command-line script does not, so `\\fs01\Data`
whose real folder on the server is reached through a junction (or is `C:\Users`, or sits in
`C:\Program Files`) gets its owners changed without that check. This item moves the check into
the shared core so the command line refuses those shares the same way the app does.

## What users will be able to do
- Running `FolderPermissionManager.ps1 -Path \\fs01\Data\HR` (or a mapped drive or DFS path
  that leads to a share) behaves like the WPF app: before counting or asking, the script looks
  up the share's real folder on the server. If that folder, or any folder above it on the
  server, is a junction or other link, or cannot be checked, or is a Windows system folder or a
  high-impact folder (`C:\Users`, System Volume Information, `$Recycle.Bin`), the script prints
  one `[FAIL]` line that names the real server folder, says nothing was changed, tells the tech
  to run the tool on the file server itself or ask a senior engineer, and exits 1.
- The same check runs again just before takeown, so a junction created after the question was
  answered is still caught.
- Ordinary shares on ordinary server folders work exactly as before.
- The WPF app behaves exactly as it does after SQ-018 (same checks, same wording); it now uses
  the core's copy of the functions.
- No change for the browser GUI is promised or tested: it is removed after SQ-018's lab test
  (owner decision 2026-10-19). It shares the core, so it gets the same refusals for free.

## Acceptance criteria
Each maps to exactly one Pester test named `AC<n>_...`. "The seams" means the two mockable
functions that touch the server: the NetShareGetInfo level 2 wrapper (share name to server-side
local path) and the attribute read over the administrative share (`\\server\X$\...`). No test
calls the real ones (see Test plan).

1. AC1_MovedFunctionsLiveOnlyInTheCore: `Get-ShareTreeRefusal`, `Get-ServerSideLinkRefusal`,
   `Get-RemoteShareLocalPath` and the reparse-info reader (`Get-AppReparseInfo`, or the core
   function that already does the same job, see Assumed) are each defined exactly once, in
   `FolderPermissions.Core.ps1`; an AST scan finds no definition of them in
   `FolderPermissionManager-GUI.ps1`, and no Add-Type declaring the NetShareGetInfo or
   reparse-info type remains in the GUI file.
2. AC2_WpfLookupStillRefusesServerSideJunction: given the WPF app's whole-tree lookup for
   `\\fs01\Data\HR`, with the share seam returning `D:\Shares\Data` and the attribute seam
   reporting `\\fs01\D$\Shares` as a reparse point, the lookup refuses before the count and
   confirm with the same refusal text the core produces (the app adds no copy of the check).
3. AC3_Core_ServerSideJunctionRefuses: `Get-TreeOwnershipTargetRefusal -Path \\fs01\Data\HR`,

## Approach
- Start from main after SQ-018 merges. The spec writer could not read the SQ-018 branch (no
  shell access in the planning run); names and behaviour come from `squad/specs/SQ-017.md`
  (SQ-018 revision notes, AC52, AC53a, fix round 1) and `squad/BACKLOG.md`. First step of the
  build: read the merged `FolderPermissionManager-GUI.ps1` and confirm which of the four
  functions, and which Add-Type blocks they depend on, are still GUI-only. SQ-018 AC53a already
  moved `Get-HighImpactRootRefusal` and `Get-AppProfilesDirectory` into the core, and its fix
  round 1 runs the high-impact check on the mapped, final, long and link paths. What is still
  WPF-only is everything that starts from the share's server-side folder (NetShareGetInfo):
  D-036, the high-impact check and the D-045 junction walk on `\\server\X$\<local path>`.
- Move the four functions into `FolderPermissions.Core.ps1` next to the existing target checks
  (after `Get-DfsTargetRefusal` / `Resolve-NetworkDrivePath`). Keep the server touches behind
  two small functions that do nothing else (the existing pattern: `Get-DfsTarget`,
  `Get-NetworkDriveRemoteName`, `Get-Win32PathName`), so tests can replace them. If on the
  branch the P/Invoke call or the attribute read is inline, extract it.
- Rewrite anything 5.1-only for the 3.0 floor (`New-Object` instead of `::new()`, cast from
  strings for `0x8...` tag values, `@()` before `.Count`). Add-Type in the core uses the
  `FolderPermissionManager.<Name>` namespace and `-ErrorAction Stop`, like `Win32Dfs`.
- Wire into `Get-TreeOwnershipTargetRefusal`: after the D-036 check on the given/mapped path and
  the DFS loop, for each UNC form that is a non-administrative share (`$given`, and each DFS
  target `Get-DfsTargetRefusal` enumerates), call `Get-ShareTreeRefusal`. Because
  `Invoke-TreeOwnershipChange` already calls `Get-TreeOwnershipTargetRefusal` twice (before
  ShouldProcess and again after the snapshot), the late re-check comes for free (AC11). For DFS
  targets, either have `Get-DfsTargetRefusal` call it per target or collect the targets once;
  avoid a second NetDfsGetClientInfo call per path.
- The WPF app keeps calling the same function names, now from the core. Remove its copies.
  Its pool copies core functions automatically; check AC8d/AC8e.
- CLI: `Get-CliRefusalNextStep` gets a branch for server-side refusals (detected by a marker
  string in the core, like `$script:ChosenFolderUncheckedText`), with the SQ-018 AC53c wording
  "Run the tool on the file server itself, or ask a senior engineer." Check it before the
  existing branches so a server-side refusal never gets the "real server path (Properties >
  DFS tab)" or `-AllowSystemFolder` advice. Update help and README (AC19).
- Learn pages to cite next to the code (verify each when building, per root CLAUDE.md):
  NetShareGetInfo (level 2 needs Administrators or Server Operators membership on the server),
  SHARE_INFO_2 (`shi2_path`), FILE_ATTRIBUTE_REPARSE_POINT, and the administrative shares page
  already cited in `Get-TreeOwnershipRefusal`.

### Assumed by the squad
- What is still WPF-only: the server-side half. Evidence: SQ-017.md revision notes say AC53a and
  fix round 1 put `Get-HighImpactRootRefusal` into the core and run it on the mapped, final,
  long and link paths; main's `Get-TreeOwnershipTargetRefusal` has no NetShareGetInfo step. To
  be confirmed against the merged code before writing tests (Approach, first step).
- D-045 covers every share the change reaches, so each DFS target and a mapped drive's server
  path get the check (AC9, AC10). Reason: D-045 says "whole-tree changes on a remote share",
  and D-040's DFS handling already checks every target, not just the active one.
- Fail closed when the share lookup fails, including a tech without admin rights on the server.
  Evidence: D-045 ("refuse when ... cannot be checked") and the destructive-operations profile
  ("a guard that cannot resolve the path fails closed"). This is a visible change for CLI users
  running from a workstation against a share on a server where they are not admin.
- The CLI next step for these refusals reuses SQ-018 AC53c's owner wording ("run the tool on the
  server itself, or ask a senior engineer") and never points to a `\\server\X$` path. Evidence:
  AC53c, and the read-only-advisory checklist gap from SQ-018 (advice must not send the tech
  down a route that skips the check).
- Function names are kept (`Get-AppReparseInfo` included) unless the core already has a function
  doing the same read (`Test-LinkReparsePoint`, `Get-LinkKind`), in which case the WPF callers
  switch to the core one and the duplicate is dropped. Reason: one implementation, least churn.
- The check is wired into `Get-TreeOwnershipTargetRefusal`, not into the CLI, so every front end
  and the late re-check get it. Reason: the destructive-operations gap from SQ-018 ("safety
  rules enforced only in one UI must also be enforced in the shared core").
- The server-side walk ignores the D-040 allowlist (any reparse point refuses), as AC52 was
  built. Reason: follow SQ-018 as built; the advisory note about it is SQ-018's open owner item.

## Risk and safety notes
- destructive-operations: this item exists to close a guard gap on a destructive action
  (whole-tree owner change on a client file server). All checks run before ShouldProcess and
  again after the snapshot; a refusal writes nothing except the snapshot already named in the
  row. Every write path stays mocked (`Invoke-AclTool` guard), and no test touches a real
  share.
- system-configuration (reads only): NetShareGetInfo and the admin-share attribute reads read a
  remote server's configuration. Both stay behind seams that every reaching suite replaces with
  a throwing guard (AC18). If Add-Type is blocked (constrained language mode, AppLocker), the
  lookup throws and the folder is refused (fail closed, AC5).
- Lab test by hand for Michael (cannot be proven with mocks): the CLI against a real share whose
  folder sits behind a server-side junction and against an ordinary share; a tech account that
  is not admin on the file server (expect a refusal); a share on a mounted-volume folder (a
  mount point is a reparse point, so it will be refused under AC52 as built).
- Behaviour change to flag at review: CLI runs against remote shares now need admin rights on
  the file server, or they are refused. Running the CLI on the file server with a local path
  (its documented use) is unaffected.
