## Summary (plain English)
When a tech copies permissions onto a folder on a file share, the tool checks the path as this
computer sees it, but not where that share really is on the file server. So a share called
`\\fs01\Win` that is really `C:\Windows` on fs01, a share that is really `C:\Users`, or a share
whose folder on the server is reached through a junction, can still receive copied
permissions. After this item, Copy asks the file server where the share's folder really is and
runs the same checks as whole-tree take ownership (D-045): no Windows folder, no profiles folder,
no junction on the way, and refuse when it can't check. The checks run when the targets are
looked up and again just before each write.

## What users will be able to do
- In the WPF app, Copy Permissions To... with a target on another server's share
  (`\\fs01\Data\HR`, a mapped drive that leads there, or a DFS folder whose one target is there)
  is checked on the file server before the confirm opens. A target is refused, with the dialog
  reopening on what was typed (as for every Copy refusal today, AC53) in these cases:
  - the share's real folder on the server, or the target inside it, is a Windows system folder,
    the root of a drive (see Q1), a Users/profiles folder, System Volume Information or
    `$Recycle.Bin`;
  - any folder on the way there on the server is a junction or other link;
  - the server would not say where the share is (for example, the tech is not an admin on
    that server), or a folder on the way could not be read.
  The message names the typed path and the real folder on the server ("\\fs01\Win is C:\Windows
  on fs01 (\\fs01\C$\Windows). Permissions can't be copied to ..."). For the "could not check"
  cases it says to run the tool on the file server itself, or ask a senior engineer. It never
  suggests an admin-share path, and it never offers an override.
- A target typed as the server's admin share (`\\fs01\D$\Shares\Data`, which Copy allows) gets
  the same junction walk, because the client cannot see server-side junctions there either.
- The copy itself does the same check again just before it writes each target. So a junction
  created on the server after the confirm still stops that target. Its row is Failed and says
  "Nothing was changed."
- Ordinary shares on ordinary server folders copy exactly as before. Local folders, and
  shares on this computer (already turned into local paths by the app), are not affected.
- Behaviour change to expect: a tech who is not an admin on the file server can no longer
  copy permissions onto that server's shares from a workstation. The copy is refused with the
  "run the tool on the file server itself" next step. This follows P-006 and D-045's "refuse
  when it cannot be checked".
- No command-line change: the CLI has no copy step (D-035). The browser GUI calls the same core
  function, so it gets the refusals as Failed rows. It gets no ACs, because it is removed after
  the SQ-018 lab test.

## Out of scope
- **The CLI.** It has no copy step (D-035), and nothing is added.
- **The browser GUI.** No ACs. It inherits the refusals as Failed rows, and its existing tests
  must still pass.
- **An override.** There is no `-AllowSystemFolder` for Copy. D-054 is about the CLI's
  whole-tree switch, and Copy has neither a CLI nor an override (SQ-022, Assumed).
- **Server-side checks for links inside the target tree.** Copy writes one ACL on the target
  folder (D-031). Windows propagates inheritable entries below it, but that is not a recursive
  walk by the tool. Not asked for.
- **Relaxing the "any reparse point refuses" rule on server path components** (mounted volumes,
  dedup folders). This follows SQ-018 AC52 as built and SQ-021's noted usability cost.
- **Changing the share-root confirm (AC49)** or the confirm text, apart from the Q1 refusal.
- **Caching the share lookup** across targets or across the plan and late steps.

## Approach
- **Precondition.** Start from main once SQ-024, SQ-023 and SQ-022 have merged. Before writing
  tests, read the merged core and confirm these against the code:
  - the names and signatures of the moved share helpers;
  - the single helper SQ-021 AC7 asked for, "server path for this target" (admin-share branch
    vs NetShareGetInfo branch);
  - the attribute seam's final name;
  - the marker constant SQ-023 adds for server-side refusals;
  - that `Get-CopyTargetResolvedRefusal` now lives in the core and is called from
    `Copy-FolderPermission`'s `-Plan` and `-Change` blocks and from the WPF
    `Get-ChangeTarget -RefuseProtected`.

  This spec was written from the SQ-022/SQ-023/SQ-024/SQ-021 specs and main's code, not from
  their built branches. If a name differs, use the built one; the ACs keep their meaning.
- **One new core function.** `Get-CopyTargetServerRefusal -Path` returns the refusal text or
  `$null`. It works like SQ-023's server-side step in `Get-TreeOwnershipTargetRefusal`, with
  Copy wording:
  1. Mapped drive: `Resolve-NetworkDrivePath`. If it throws, refuse (fail closed).
  2. For a UNC path, list its forms: the path itself plus each DFS target, using the same
     DFS step SQ-023 uses (`Get-DfsTarget`). A lookup error refuses.
  3. For each form, call SQ-023's "server path for this target" helper:
     - `<letter>$`: the path is the server path.
     - ordinary share: `Get-RemoteShareLocalPath`.
     - `ADMIN$`, `IPC$`, `SYSVOL`, `NETLOGON`, `PRINT$`: already refused by
       `Get-CopyTargetRefusal` earlier, so they never get here.
  4. Run `Get-CopyTargetRefusal` on the server path. It covers drive root, D-036 and the
     high-impact roots, with Copy wording. Use it, not `Get-TreeOwnershipRefusal`, whose text
     talks about taking ownership.
  5. Then run `Get-ServerSideLinkRefusal` on the server path.
  6. A refusal reads "`<Path>` is `<local>` on `<server>` (`<serverPath>`). `<refusal>`", like
     `Get-ShareTreeRefusal`.

  Keep the share lookup and the walk in the shared helpers. If SQ-023 left the D-036 step
  inside `Get-ShareTreeRefusal`, add a parameter or split out the lookup half so it is written
  once, not copied. Local paths return `$null` before any seam (AC12).
- **One wiring point.** Call it at the end of the core's `Get-CopyTargetResolvedRefusal`, after
  the final/long-path checks. That one call covers three places:
  - the WPF lookup before the confirm (`Get-ChangeTarget -RefuseProtected`, AC14);
  - the core `-Plan` step (AC1-AC8);
  - SQ-022's late re-check just before `Set-Acl` (AC9, AC15). It is a real re-check because it
    re-runs the share lookup and the walk.

  Update the help comments of `Get-CopyTargetResolvedRefusal`, `Get-ChangeTarget` and
  `Invoke-CopyPermissions`. The WPF window-thread re-check in `Invoke-CopyPermissions` stays
  text-only, as now.
- **The WPF app already passes `ResolvedPath`** to the copy work (`Invoke-CopyPermissions`,
  `$Targets | ForEach-Object { $_.ResolvedPath }`). DFS and this computer's own shares are
  therefore resolved before the core sees them. A share on this computer arrives as a local
  path and skips the server step. In the core, a DFS lookup on an already-resolved
  `\\fs01\Data\HR` comes back "not in DFS" and the path goes on.
- **PowerShell 3.0 floor** (the core is `#Requires -Version 3.0`): no `::new()`, no
  `.Where()`/`.ForEach()`, `@()` before `.Count`. Any new top-level core variable must be in
  `Get-CoreScriptVariableNames`, or AC8d fails.
- **Existing tests.** The AppChanges suite already mocks the seams with an ordinary server
  folder in `BeforeAll` (`Mock Get-RemoteShareLocalPath { "D:\Shares\$Share" }`, ordinary
  `Get-AppReparseInfo`), so the AC50 tests that pass `\\fs01\Data\HR` and `\\fs01\Data` keep
  passing unchanged. Any core Copy test that uses a `\\fs01\...` target gets the same ordinary
  mock. No assertion is changed or removed. If one cannot pass without changing what it
  asserts, stop and report it.
- **Microsoft facts.** The citations already present on the moved helpers move with them:
  NetShareGetInfo (level 2 needs Administrators/Server Operators on the server), SHARE_INFO_2,
  FILE_ATTRIBUTE_REPARSE_POINT and the administrative-shares page. The builder re-checks each
  one on Learn when citing it in the new function. The only new fact is the junction tag value
  used in tests (`IO_REPARSE_TAG_MOUNT_POINT` = `0xA0000003`). Cite MS-FSCC 2.1.2.1 next to the
  test constant, as the existing AC52 tests do.

- D-054: applies to the CLI's whole-tree `-AllowSystemFolder` only. Copy has no override.
- P-006: a change lands where the tool checked, or not at all. The checks live in the core and
  run again before the write.
- 2026-10-19: the browser GUI is removed after the SQ-018 lab test, so it gets no ACs.
- D-056 (Q1): a share whose server folder is a whole drive is refused for Copy onto its root,
  like `E:\` and `\\fs01\E$`.
- Q2 (build order) settled by the lead, not the owner: build from main once SQ-024, SQ-023 and

### Assumed by the squad
- **Fail closed when the share lookup fails, including for techs without admin rights on the
  file server.** Evidence: the backlog text ("failing closed"), D-045 ("refuse when ... cannot
  be checked"), P-006 (which names SQ-026), and the destructive-operations profile ("a guard
  that cannot resolve the path fails closed"). The visible cost is flagged in "What users will
  be able to do".
- **Wire into `Get-CopyTargetResolvedRefusal`, not into each caller.** One call reaches the WPF
  lookup, the core plan step and the late re-check. Reason: the "Safety rules live in the core"
  checklist, and SQ-022 already calls that function in all three places.
- **Use Copy wording on the server path (`Get-CopyTargetRefusal`), not the take-ownership text.**
  Reason: `Get-TreeOwnershipRefusal`'s tail talks about changing owners, which would be wrong in
  a Copy refusal. `Get-CopyTargetRefusal` already covers drive root, D-036 and high-impact.
- **Admin-share targets (`\\server\X$\...`) get the junction walk** without a share lookup.
  Reason: the client cannot see server-side junctions there either, and SQ-021 (built in SQ-023)
  set that pattern for whole-tree.
- **Every DFS target is checked in the core.** Reason: parity with SQ-023 AC10. The WPF app
  already refuses multi-target DFS folders (D-043), so in practice this only matters to other
  callers.
- **The late re-check re-reads the server and does not cache.** Reason: the profile says the
  re-check "re-resolves the path (... server path)". Repeating a text-only check is not a
  re-check.
- **"Any reparse point refuses" on server path components** (no D-040 allowlist), as SQ-018
  AC52 was built. Reason: follow the built behaviour; relaxing it is a separate owner decision.
- **Refusal wording** reuses the existing texts: `Get-CopyTargetRefusal`, SQ-023's lookup-failure
  next step ("Run the tool on the file server itself, or ask a senior engineer."), and
  `Get-ServerSideLinkRefusal`. No new user-facing sentences are added beyond the "`<path>` is
  `<local>` on `<server>`" prefix, which `Get-ShareTreeRefusal` already uses.

## Risk and safety notes
- **destructive-operations, in full.** Copy writes inheritable entries, and on a share root
  they reach the whole tree. This item closes the "non-admin shares that point at a protected
  root are recognised" and "server-side junctions on SMB" gaps for the Copy write path.
- **Order of checks:** the text checks come before any disk read (AC1), then the resolved
  checks, then the server checks. All of them run before ShouldProcess and again just before
  `Set-Acl`.
- **Fail closed** everywhere: the lookup (AC4), an unreadable level (AC5), a mapped drive
  without a server path, and a DFS lookup error.
- **No new write path.** Every test keeps the `Set-Acl` backstop and the throwing
  `Invoke-AclTool`. AC15 proves the backstop in the pool.
- **system-configuration (reads only).** NetShareGetInfo and the admin-share attribute reads
  read a remote server's configuration. Both stay behind seams, and every suite that reaches
  them guards them with a throwing stub (AC16). If Add-Type is blocked (constrained language,
  AppLocker), the lookup throws and the target is refused.
- **Overrides and refusals:**
  - no override is offered;
  - the next step never points to an admin-share path;
  - the refusal names what was found (the link kind, and the server folder).
- **Behaviour change to flag at review:** Copy onto remote shares now needs admin rights on the
  file server. Shares on mounted-volume folders are refused, which is the D-045/AC52 cost
  inherited from SQ-021. Running the tool on the file server itself is unaffected.
- **Pre-mortem: what could stop the build and leave it waiting for the owner?**
  - **A share whose folder is a whole drive** (`\\fs01\Data` = `E:\`). Today the share-root
    confirm lets it through. Under D-036 it is a drive root and would be refused. This is Q1,
    asked now.
  - **Build order.** SQ-022 and SQ-023 are not built yet, and both change the functions this
    item calls. This is Q2.
  - **SQ-023 kept the share lookup and the D-036 step in one function** with take-ownership
    wording. The Approach already says to split or parameterise it rather than copy it, so this
    needs no owner.
  - **An existing core Copy test feeds a `\\fs01` target without seam mocks.** The suite guards
    throw, so it fails loudly. The fix is to add an ordinary-folder mock, without changing any
    assertion.
