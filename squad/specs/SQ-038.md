# SQ-038 · FolderPermissionManager: Copy's Deny acknowledgement names the Deny entries the tech saw

- status: ready
- feature: FolderPermissionManager rewrite
- size: M
- risk: high
- rewrite: no
- touches: FolderPermissions.Core.ps1 (Copy-FolderPermission's Deny check, Get-CopyDenyRefusal, one new key helper, help/.NOTES), FolderPermissionManager-GUI.ps1 (Get-CopySourceDenyEntries, Invoke-CopyPermissions, $script:CopyPermissionsWork, Get-ConfirmSpec's CopyPermissions text for "could not be checked"), README "Copy Permissions To..." and the D-044 confirm list, core and app test suites
- depends-on: SQ-022 (done)
- related: D-052 (revisited by Q1), D-044, D-048 / SQ-037 (Allow entries added late are out of scope here), SQ-025 (Find-ExplicitAccessRule: the exact-entry match this item reuses), SQ-026 / SQ-037 (also edit Copy-FolderPermission; see "Ordering")

## Summary (plain English)
Copy Permissions warns the tech in a red confirm when the folder they copy from has Deny
permissions, and lists them. Today, once the tech accepts that warning, the copy sends out every
Deny the folder has at the moment of the copy, including one someone added after the window
loaded the folder. After this item, the tech's "yes" covers only the Deny permissions the
confirm actually listed. If the folder has a different or extra Deny by the time the copy
reads it, nothing is copied and the result names the Deny the warning did not show.

## What users will be able to do
Nothing new to click; Copy Permissions becomes trustworthy about what the red confirm promised.
- The tech copies from a folder whose confirm listed "CONTOSO\Temps (Deny, Write)". Meanwhile
  someone adds "Everyone Deny Full control" to that folder. The copy is refused for every target,
  each row names "Everyone" as the Deny the warning did not show, and nothing is changed. Before
  this item it was copied, inheritable, onto every target.
- A Deny that was listed and is still exactly the same is copied as today.
- A Deny that was listed but changed since (Deny Write became Deny Full control, or now applies to
  "this folder, subfolders and files" instead of "this folder only") counts as not shown: refused.
- A Deny that was listed but has since been removed from the source is simply not copied (less
  is sent out than the tech accepted; nothing to refuse).
- When the window could not check the source for Deny permissions (its permissions are not
  loaded), behaviour follows Q2. Recommended (Q2 = A): the confirm says so and that a copy from a
  folder with Deny permissions will stop; a source with only Allow permissions copies; a source
  with any Deny is refused with a next step "open the folder's permissions so the warning can
  list them, then copy again".
- The README, `Copy-FolderPermission`'s help and the refusal text say exactly this, and no
  longer promise more than the code does.

## Acceptance criteria
Core tests go in `FolderPermissionManager/Tests/CopyPermissions.Refusal.Tests.ps1` (new
`Describe 'SQ-038 ...'` block, same mocks as SQ-022's AC9). App tests (AC9-AC11) go in
`FolderPermissionManager-AppChanges.Tests.ps1`, next to SQ-022's AC10. Written for Q1 = A,
Q2 = A; the alternatives' changes are listed under each question.

1. AC1_DenyKeyNamesOneExactEntry: `Get-PermissionEntryKey` (new, core) returns the same text for
   a Deny rule read by SID from an ACL (`GetAccessRules($true,$false,[SecurityIdentifier])`) and
   for a view row carrying the same `Sid`, `Type`, `RightsValue`, `InheritanceFlags` and
   `PropagationFlags` (the shape `ConvertTo-AclViewModel` builds). It returns a different text
   when any one of SID, Allow/Deny, raw rights mask, inheritance flags or propagation flags
   differs (one data-driven `It -ForEach`, six rows: same + five single-field changes).
2. AC2_CopyCopiesDenyEntriesThatWereAcknowledged: Given a source whose explicit rules are one
   Allow and one Deny (seeded SDDL), and `-AcknowledgedDeny` holding that Deny's key, when
   `Copy-FolderPermission` runs on two `$TestDrive` targets, then both rows are `Done` and the
   `Set-Acl` mock is called twice, each ACL holding the Deny.
3. AC3_CopyRefusesADenyAddedAfterTheWarning: Given a source with two explicit Deny entries
   (`CONTOSO\Temps`-style Deny Write, and `Everyone` Deny FullControl, inheritable) and
   `-AcknowledgedDeny` holding only the first one's key, then every target row is `Failed`, its
   ErrorText names the source and `Format-PermissionRule` of the `Everyone` Deny, does not name
   the acknowledged one as unwarned, and ends with "Nothing was changed.". `Set-Acl`,
   `Save-AclBackup` and `Write-PermissionChangeLog` are called 0 times.
4. AC4_CopyRefusesADenyThatChangedSinceTheWarning: Given `-AcknowledgedDeny` holding the key of
   "Deny Write, this folder only" and a source whose Deny for the same SID is now "Deny Write,
   this folder, subfolders and files" (different inheritance flags), then every row is `Failed`
   and `Set-Acl` is not called. Same `It` with a second case where only the rights mask differs.
5. AC5_CopyWithoutAcknowledgementRefusesEveryDeny: Given a source with one explicit Deny and no
   `-AcknowledgedDeny` (and, as a second case, `-AcknowledgedDeny @()`), then every row is
   `Failed` with the refusal and `Set-Acl` is not called. A source with only Allow entries and no
   acknowledgement copies (`Done`). This replaces SQ-022's AC9 assertion "with -AllowDeny the rows
   are Done".
6. AC6_AcknowledgedDenyRemovedFromSourceIsNotNeeded: Given `-AcknowledgedDeny` holding a key for
   a Deny the source no longer has, and a source with only Allow entries, then the rows are
   `Done` (nothing outside the acknowledged set is copied).
7. AC7_DenyDecisionUsesTheSameReadThatIsCopied: SQ-022's AC9b test, re-pointed: the first
   `Get-Acl` read of the source holds an unacknowledged Deny, later reads hold none; the rows are
   `Failed` (the decision comes from the read whose rules are copied). The source is read once.
8. AC8_DenyRefusalStandsUnderWhatIf: Given `-WhatIf` and a source with an unacknowledged Deny,
   then every row is `Failed` with the refusal (not `Skipped (WhatIf)`), and there is no
   `Set-Acl`, no backup and no change-log write.
9. AC9_AppPassesExactlyTheDenyEntriesTheConfirmListed: In the WPF app, with
   `$script:ViewState.FolderPermissions` loaded for the current folder holding two explicit Deny
   rows and one inherited Deny row, `Invoke-CopyPermissions` (with `Show-ConfirmDialog` mocked to
   accept) calls `Start-ChangeTask` with an argument list whose acknowledged-Deny element equals
   the keys of the two explicit Deny rows, in any order, and the confirm body (from the mocked
   `Show-ConfirmDialog`'s `-Spec`) lists exactly those two. The `Get-CopySourceDenyEntries`
   result carries the display texts and the keys from the same rows.
10. AC10_AppPassesNoAcknowledgementWhenNoDenyWasShown: Three cases, asserting the
    acknowledged-Deny element of the `Start-ChangeTask` argument list is empty: (a) a loaded
    source with no Deny and no other confirm reason (no confirm shown); (b) a loaded source with
    no Deny but a drive-root target (confirm shown for the root, not for Deny); (c) Q2 = A: the
    source's permissions are not loaded (`DenyUnchecked`, confirm shown and accepted). No code
    path passes `-AllowDeny` (the parameter no longer exists; static AST check over
    `FolderPermissionManager-GUI.ps1`, `FolderPermissionManager-WebGUI.ps1` and the core finds no
    `AllowDeny` parameter or argument).
11. AC11_UncheckedConfirmSaysADenySourceWillStop *(Q2 = A)*: `Get-ConfirmSpec -Action
    CopyPermissions -DenyUnchecked` returns a body that no longer says "Any it has are copied
    too" and does say that a copy from a folder with Deny permissions of its own will stop with
    nothing changed (exact sentence in "Wording" below). It stays destructive (red, not default).
12. AC12_RefusalTextFitsTheCaller: `Get-CopyDenyRefusal` with an acknowledgement passed (the WPF
    path) names the unwarned Deny entries and says the warning did not show them (wording below);
    with no acknowledgement passed at all (any other caller, the browser GUI included) it says
    this copy cannot send Deny permissions and to use the FolderPermissionManager window, which
    lists them first. Neither text says "Reload" or blames the tech, and neither claims a Deny
    "blocks access even where another permission allows it" without the inheritance scope
    (wording below). Also: `-Rule $null` and `-Rule @()` return `$null` (SQ-022 review minor).
13. AC13_DocsMatchTheCode: A static test over `README.md` and `Copy-FolderPermission`'s help
    (`Get-Help` on the dot-sourced core): neither contains "-AllowDeny"; the README's Copy section
    contains "only the Deny permissions the confirm listed" (or the agreed sentence) and no longer
    contains "if a Deny was added to the folder after the window loaded its permissions" as an
    unconditional promise; the help has a `.PARAMETER AcknowledgedDeny` that says the set must be
    the entries the technician was shown.

## Out of scope
- **Allow entries added to the source after the window loaded it.** They are still copied
  without a confirm: "adds access" stays one click (D-048). Whether inheritable Copy of new
  access needs a guard is SQ-037.
- **Re-reading or re-confirming when the target list changes.** Targets already go through the
  core's early and late refusals (SQ-022); this item is about the source's Deny entries only.
- **A handle-based write** to close the window between the late re-check and `Set-Acl` (SQ-022
  review follow-up). Unchanged.
- **Server-side checks for remote targets** (SQ-026) and DFS lookups in the core.
- **The browser GUI's UI.** It gets no new prompt. It calls `Copy-FolderPermission` without an
  acknowledgement, so (as today since SQ-022) it cannot copy a source with Deny entries; only its
  refusal text improves (AC12). It is due for removal after the lab test (SQ-018 note).
- **The old CLI.** It has no copy step (D-035, `AC15_CliHasNoCopyStep_ScriptHasNoCopyCallsStatically`).

## Approach
- **Key helper (core).** Add `Get-PermissionEntryKey` near `Find-ExplicitAccessRule`, with two
  parameter sets: `-Rule` (a `FileSystemAccessRule` whose `IdentityReference` is a
  `SecurityIdentifier`) and `-Sid -Type -RightsValue -InheritanceFlags -PropagationFlags` (a view
  row's fields). Output: `"<SID>|<Allow|Deny>|<raw mask as int>|<[int]InheritanceFlags>|<[int]PropagationFlags>"`.
  This is the same identity SQ-025's `Find-ExplicitAccessRule` uses to find "exactly the entry
  shown" (raw mask with generic rights and Synchronize, flags compared as stored), so the app's
  row and the core's read agree. PS 3.0 safe: no `::new()`, no `.Where()`; the core stays
  `#Requires -Version 3.0`.
- **Core check (Copy-FolderPermission).**
  - Replace `[switch]$AllowDeny` with `[AllowNull()][AllowEmptyCollection()][string[]]$AcknowledgedDeny`.
  - From the same `$sourceAcl` object already read (no second `Get-Acl`), list the explicit Deny
    rules by SID: `$sourceAcl.GetAccessRules($true, $false, [SecurityIdentifier])` filtered to
    Deny. Build each key; any rule whose key cannot be built fails closed (counts as
    unacknowledged). The display text for the refusal uses the NTAccount-form rule at the same
    index, as `ConvertTo-AclViewModel` pairs them, or the SID when the name cannot be read.
  - Any Deny whose key is not in `$AcknowledgedDeny` (case-insensitive compare on the SID part
    is unnecessary: SIDs are upper-case `S-1-...` from .NET; compare ordinal-ignore-case anyway)
    gives one `Failed` row per target with `Get-CopyDenyRefusal`'s text, then return, exactly
    where the D-052 check sits today (before `Invoke-SingleItemAclChange`, so before backup and
    ShouldProcess). Only the unacknowledged Deny entries are named.
  - Keep the comment that the decision uses the read whose rules are copied.
- **Refusal text.** `Get-CopyDenyRefusal` gains `-Acknowledged [bool]` (was an acknowledgement
  passed at all) and `-Rule` now receives only the unwarned Deny rules. Wording below. The
  inheritance-scoped Deny sentence reuses `$denyNote`'s facts and the existing
  order-of-aces citation (https://learn.microsoft.com/windows/win32/secauthz/order-of-aces-in-a-dacl).
- **App.**
  - `Get-CopySourceDenyEntries` returns `Checked`, `Entries` (display texts, unchanged) and
    `Keys` (from the same rows, via `Get-PermissionEntryKey -Sid ... `), so the list shown and the
    list acknowledged cannot drift apart.
  - `Invoke-CopyPermissions`: `$denyConfirmed` becomes `$acknowledgedDeny = [string[]]@()`; set
    to `$deny.Keys` only when the confirm was shown with Deny entries and accepted. Unchecked
    (Q2 = A) leaves it empty.
  - `$script:CopyPermissionsWork`: the sixth parameter `[bool]$AllowDeny` becomes
    `[string[]]$AcknowledgedDeny` at the same position, passed as `-AcknowledgedDeny`. A caller
    passing five arguments gets `$null`, i.e. the safe refusal (as SQ-022 intended). Wrap the
    array in the argument list as `(,[string[]]$keys)` if needed so the pool does not spread it
    (root CLAUDE.md note on `-ArgumentList (,$collection)`); AC9 checks the element is the
    array.
  - `Get-ConfirmSpec` CopyPermissions, `DenyUnchecked` branch: new sentence (Q2 = A).
- **Docs.** Core `.NOTES` line ~98-101 and `Copy-FolderPermission` `.DESCRIPTION`: name D-052 as
  amended by this item's decision; add `.PARAMETER AcknowledgedDeny`, remove `.PARAMETER
  AllowDeny`. README lines ~167-168 (confirm list) and ~413-418 (Copy section): describe the
  acknowledged set, the unchecked case and the browser GUI's limit. Also narrow the "whatever
  calls it" sentence at ~422-423 only as far as it concerns Deny (the DFS part stays for SQ-026).
- **Existing tests to re-point (contract change asked for by this spec, nothing asserted less):**
  `CopyPermissions.Tests.ps1` lines ~143, ~161, ~339 and `CopyPermissions.Refusal.Tests.ps1`
  ~340 pass `-AcknowledgedDeny` built with `Get-PermissionEntryKey` from the seeded source
  instead of `-AllowDeny`; SQ-022 `AC10_AppPassesAllowDenyOnlyAfterTheDenyConfirm` is replaced by
  AC9/AC10 here (its DenyUnchecked case flips from "acknowledged" to "empty" under Q2 = A, by
  owner decision).
- **Wording (squad-drafted; owner may adjust at review):**
  - With an acknowledgement (WPF): "Permissions were not copied from <source>: it now has
    <a Deny permission | N Deny permissions> of its own that the warning did not show
    (<list>). Someone may have added or changed it after this window loaded the folder. Press
    Refresh, check the folder's permissions, and copy again if they are right. Nothing was
    changed."
  - Without one (browser GUI, scripts): "Permissions were not copied from <source>: it has
    <...> of its own (<list>), and this copy cannot send Deny permissions. Use the
    FolderPermissionManager window (FolderPermissionManager-GUI.ps1), which lists them before
    copying. Nothing was changed."
  - Deny scope sentence (both, replacing "blocks access even where another permission allows
    it"): "A Deny is copied too: it blocks access on the folder it is set on even where another
    permission there allows it, and subfolders and files that inherit get it, though a
    permission set directly on one of them can still allow access there."
  - Unchecked confirm (Q2 = A): "The permissions of the folder you copy from are not loaded in
    this window, so it could not be checked for Deny permissions of its own. If it has any,
    the copy stops and nothing is changed; open the folder first so this warning can list them."
- **No new Microsoft facts** beyond the already-cited ACE order page; `GetAccessRules` with
  `SecurityIdentifier` is already cited at `Find-ExplicitAccessRule`.
- **Ordering with the other FPM items.** SQ-038 edits the Deny pre-check in
  `Copy-FolderPermission`, `Get-CopyDenyRefusal`, `Get-CopySourceDenyEntries`,
  `Invoke-CopyPermissions`, the copy work block and the CopyPermissions confirm text.
  - SQ-023 (share helpers into the core, `Get-TreeOwnershipTargetRefusal`) and SQ-028 (Add's
    account resolution) do not touch these functions: no dependency; they can build in the same
    run.
  - SQ-026 adds target checks inside `Copy-FolderPermission`'s `-Plan` block (different hunk,
    same function and same test file): build after SQ-038 or rebase; soft order, not a hard
    depends-on.
  - SQ-037 (owner decision pending) would add confirms/refusals to Copy and touch
    `Invoke-CopyPermissions` and `Get-ConfirmSpec`: put `depends-on: SQ-038` on SQ-037 when it is
    specced, so it builds on the new acknowledgement shape.

What the tests cannot see:
- That a real `Get-Acl` read through the WPF app's background pool and the window's view-model
  read produce the same key for the same ACE on a real NTFS/SMB folder (generic-rights masks,
  Synchronize bit on Deny, an orphaned SID). Tests use seeded SDDL in one process. Lab test.
- The real timing case: open a folder in the window, add a Deny to it from Explorer or icacls on
  another machine, then Copy. Expected: refused, row names the new Deny, nothing changed.
- That the window still starts and the Copy confirm renders the new unchecked sentence. The
  smoke check covers that the app starts; the confirm text in a real dialog is for the owner.
- How the browser GUI shows the new no-acknowledgement text (no tests for it by owner choice).

## Decisions
### Confirmed by the owner
- D-052 (2026-10-19, SQ-022 Q2 = A): the core refuses Deny entries unless the caller
  acknowledges them; the WPF app acknowledges only after its Deny confirm. This item changes the
  acknowledgement from a boolean to the set shown (pending Q1).
- D-044: a Copy whose source has explicit Deny entries gets the destructive confirm.
- D-048: changes that only add access stay one click (why late Allow entries are out of scope).
- D-035: the CLI has no copy step.
- 2026-10-19: the browser GUI gets no ACs and is removed after the lab test.
- D-064 (2026-11-11): Q1 = A, the acknowledged Deny set; -AllowDeny removed. D-065: Q2 = A, unread source copies only with no Deny. The ACs are written for A/A.

### Assumed by the squad
- **Exact-entry key = SID + type + raw mask + inheritance + propagation flags.** Same identity
  SQ-025 uses for "the entry shown" (`Find-ExplicitAccessRule`, FolderPermissions.Core.ps1 ~3325);
  view rows already carry all five fields (`ConvertTo-AclViewModel`, GUI ~1050). Chosen over SDDL
  ACE strings: .NET has no per-ACE SDDL getter on `FileSystemAccessRule`, and the five fields
  are what the app already has.
- **A Deny acknowledged but gone from the source is not an error.** Less is copied than the tech
  accepted; the destructive-operations profile is about unwarned writes.
- **Refusal lists only the unwarned Deny entries.** The tech already saw the others.
- **All targets refused, none written,** when any Deny is unwarned: the same all-or-nothing shape
  as SQ-022's D-052 check (one source read decides for every target).
- **Refusal under `-WhatIf` too**, as SQ-022 did (check runs before ShouldProcess).
- **Sixth work argument keeps its position**, `$null` meaning "no acknowledgement" (SQ-022 build
  note: five-argument callers get the safe refusal).
- **Refusal wording is squad-drafted** (as SQ-022's was); the owner can adjust it at review
  without a rebuild of the logic.
- **No new core parameter for the browser GUI.** It never prompts for Deny; it stays refused.

## Risk and safety notes
- Destructive-operations profile applies: Copy writes inheritable ACEs; a Deny on a root reaches
  the tree.
- This item answers the SQ-022 checklist gap "An acknowledgement switch passed from a UI to a
  core must carry what the user actually saw (the ACE set ...), not a boolean." The lead may add
  that line to `squad/risks/destructive-operations.md` (this agent is read-only there).
- Also answers "Docs and README claims ... must match every caller and every case: a front end
  that never passes the override ... and the boolean-acknowledgement case" (AC12, AC13).
- Same read for decision and write: the keys come from the `$sourceAcl` object whose rules are
  copied (AC7).
- Fail closed: a Deny whose key cannot be built is unacknowledged; `$null` acknowledgement
  refuses every Deny.
- Every write mocked; no real ACL read outside `$TestDrive`; no target is `$env:COMPUTERNAME`.
- Residual (accepted, documented): a Deny added to the source between the core's single
  `Get-Acl` and the target writes is not copied at all (the copy uses that read), so it cannot
  slip through.

## Open questions for the owner
- **Q1. What should the tech's "yes" to the Deny warning cover?** (revisits D-052)
  - **A) Exactly the Deny entries the confirm listed (recommended).** The app passes the shown
    set (SID, type, rights, applies-to); the core refuses if its read has any Deny outside it.
    `-AllowDeny` is removed. Closes the gap; small contract change for tests only.
  - **B) As A, but keep `-AllowDeny` as an explicit "copy any Deny" override for scripts.** No
    front end passes it. Leaves a documented bypass the checklist warns about; only useful if you
    plan to script copies.
  - **C) Keep the boolean; fix only the README, help and refusal text** so they say a Deny added
    after a warning about another Deny is still copied. Size S. The Everyone-Deny example stays
    possible.
  - **D) App-side only: re-read the source just before starting and ask again if its Deny list
    changed.** No core change; the core stays boolean, so the gap remains between that re-read
    and the core's read and for any other caller.
- **Q2. When the window could not check the source for Deny permissions, what should Copy do?**
  (today the confirm says "Any it has are copied too" and the core copies all of them)
  - **A) Copy only if the source turns out to have no Deny (recommended).** The confirm says a
    Deny source will stop the copy; Allow-only sources still copy; a Deny source is refused
    with "open the folder so the warning can list them". No blind Deny ever goes out.
  - **B) Read the source's permissions in the background before the confirm,** so it always
    lists the real Deny entries and the "could not be checked" state disappears (a failed read
    refuses the copy). Nicer for the tech, adds a background read and a wait state: grows to the
    top of M.
  - **C) Keep today's behaviour for this case only:** an accepted "could not be checked" warning
    still copies every Deny. Leaves the gap open for exactly the case where the tech saw nothing.
