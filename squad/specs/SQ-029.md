# SQ-029 · Add a smoke-test start mode

- status: ready
- feature: Squad tooling
- size: M
- risk: medium
- touches: FolderPermissionManager-GUI.ps1 startup path (new `-SmokeTest` switch), new repo
  runner `Tests/Invoke-SmokeTest.ps1`, FolderPermissionManager README and help, new Pester
  suites (unit + Integration-tagged real launch)

## Summary (plain English)
The squad's checks run unit tests only, and those all passed on the day the Folder Permission
Manager window could not open at all (193a907). This item adds a "smoke test" start: the real
app starts, builds its real window off-screen, proves it rendered and that its background
workers run, then closes itself and reports PASS or FAIL. It asks for no admin rights, shows
nothing on screen, reads no drives and writes no files. A small runner script starts it with a
time limit. Once this is merged, Michael points `smokeCommand` at the runner, and the gate then
starts the real app after every implementer.

## What users will be able to do
- Michael (or the squad's build gate) runs
  `powershell.exe -NoProfile -ExecutionPolicy Bypass -File Tests\Invoke-SmokeTest.ps1` from the
  repo root. Within about 10-20 seconds it prints
  `[PASS] FolderPermissionManager-GUI.ps1: the window opened and closed by itself (...)` and
  exits 0, or a `[FAIL]` line saying what went wrong (the app ended before the window, the window
  did not render in time, the background check failed, an error box would have been shown) and
  exits non-zero.
- A tech can run `.\FolderPermissionManager-GUI.ps1 -SmokeTest` on a workstation to check a copy
  of the tool starts there (for example after copying it from the bundle), without a UAC prompt
  and without leaving files behind.
- Normal starts of the app are unchanged.

## Approach
**What the smoke must catch.** 193a907: dot-sourcing the core bound the core's
`-LoadFunctionsOnly` in the app's scope, so `if ($LoadFunctionsOnly) { return }` ended every normal
start with exit code 0 and no window. A smoke that relies on the exit code alone would have
passed, so success needs positive proof: the app prints a `[PASS]` line only after
`ContentRendered` fired and a background task came back, and the runner requires both exit 0
and that line. The smoke runs the real top of the script (core check, core dot-source, the guard,
the startup region, `Add-Type`, the background pool, `Initialize-PermissionWindow`, the 200 ms
`DispatcherTimer`/`Invoke-Tick`, `ShowDialog`, the Closing handler, `Invoke-AppShutdown` with
`Environment.Exit`). 6dc992e (huge-folder freeze) cannot be caught without reading drives; it
stays covered by its unit tests (see "What the tests cannot see").

**App changes (`FolderPermissionManager-GUI.ps1`).**
- Add `[switch]$SmokeTest` to the param block, `.PARAMETER SmokeTest`, an `.EXAMPLE`, and a
  "Smoke test" paragraph under `.NOTES` "Files written" saying nothing is written (the
  destructive-operations Elevation section: a "nothing changes" mode lists any startup writes;
  here there are none, and the tests prove it).
- Capture `$script:SmokeMode = $SmokeTest.IsPresent` next to `$loadOnly`, before the core
  dot-source (same reason as the 193a907 fix; and at script scope `$script:SmokeTest` would be
  the parameter itself, like the `$script:DriveMap` note in the startup region).
- New `#region Smoke test` with the pure helpers: `Get-SmokeVerdict`, `Get-SmokeTickAction`,
  `Set-SmokeWindowMode`, `Add-SmokeFailure`, `$script:SmokeProbeWork`, `$script:SmokeDeadline`
  (30 s), `$script:SmokeFailures` (a `List[string]`), `$script:SmokeState` (Rendered, ProbeOk,
  ProbeDone, TimedOut, RenderMs, ProbeMs, Started). Place it among the function regions, before
  `if ($LoadFunctionsOnly) { return }`. Do not put the text `#region Main` or `#region Startup`
  anywhere earlier in the file: existing tests locate those regions with `IndexOf`.
- `Get-StartupAction` gains `[switch]$SmokeTest`: STA -> `Continue`; not STA -> `SmokeNeedsSta`.
- `Show-AppMessage`, `Show-AppQuestion`, `Write-AppError`, `Invoke-UiAction`: when
  `$script:SmokeMode`, write the `[FAIL]`/console line, `Add-SmokeFailure`, and return without a
  message box, a file write or running the action. A modal box would block the gate until it
  kills the run, so this matters most.
- Startup region, smoke branch (each one an `if ($script:SmokeMode) { ... } else { <existing
  line unchanged> }` so the normal path's text, which tests match, stays as it is):
  - first: refuse `-LogFolder`/`-DriveMap` with exit 1 (AC8);
  - skip `Limit-AppErrorLog`;
  - drive map: `@{ Map = @{}; Source = @{} }` instead of `Get-DriveMapSet`;
  - keep the real STA/admin read; `SmokeNeedsSta` -> `[FAIL]` and `exit 1`, never a relaunch;
  - skip `Request-Elevation` (unreachable: smoke never returns `RelaunchElevated`);
  - log folder: no `Get-OneDriveFolder`, `Get-AppDefaultLogFolder`, `Resolve-ChangeLogFolder`;
    `$script:ChangeLogFolder = '(smoke test: nothing is logged)'`, notices empty;
  - skip `Enter-SingleInstance` (a real window open with the default log folder must not make the
    smoke fail, and the smoke must not lock a real window out).
- `Initialize-PermissionWindow`: in smoke mode use theme `Dark` without `Get-SavedTheme`, call
  `Set-SmokeWindowMode` (off-screen: Left/Top beyond `SystemParameters.VirtualScreenLeft/Top`
  minus the window size, so it is off every monitor; `ShowInTaskbar = $false`,
  `ShowActivated = $false` so it never takes focus from Michael), and do not wire
  `Hide-OwnConsole` on ContentRendered; instead ContentRendered sets `SmokeState.Rendered` and
  starts the probe with the existing `Start-ReadTask` (so the busy line and `Update-BgTasks` run
  for real).
- `Start-PermissionWindow`: in smoke mode, put one `New-TreeInfoItem` "Smoke test: drives are not
  listed." in the tree instead of `Update-DriveList`; the existing 200 ms timer also evaluates
  `Get-SmokeTickAction` and calls `$win.Close()` on `Close`/`TimedOut` (through the real Closing
  handler).
- Main region, smoke mode: after `Start-PermissionWindow` returns (or the catch ran, which counts
  as a failure), write `Get-SmokeVerdict` lines and pass its ExitCode as `-ExitCode` to
  `Invoke-AppShutdown` (so the `Environment.Exit` path used under `-File` carries the verdict),
  then `exit` with it for the in-process case. The existing `$exitCode`/`FatalError` lines stay
  as they are for the normal path (App suite AC8c matches them).
- `$script:SmokeProbeWork` (pool work block): returns `Ok`, and booleans for `Get-ItemOwner`,
  `Get-DriveListModel` and the `$RedirectFreeReparseTags` count. Pure: no file, drive or registry
  access.

**Runner (`Tests/Invoke-SmokeTest.ps1`, new).** `#Requires -Version 5.1`, `[CmdletBinding()]`,
`-ScriptPath [string[]]` (default: the FPM GUI, resolved from `$PSScriptRoot\..`),
`-TimeoutSeconds` (default 90, below the gate's `smokeTimeoutSeconds` of 120 so the runner's own
clearer message wins), `-LoadFunctionsOnly`. Full help block. `Start-SmokeProcess` is the only
place a process starts: `System.Diagnostics.Process` with `UseShellExecute = $false`, stdout and
stderr redirected and read asynchronously (no pipe deadlock), `CreateNoWindow = $true`,
`WaitForExit(ms)`, and `Kill()` on its own process object on timeout. Output lines are echoed with
the target name. Exit codes: 0 all passed, 1 any failed, 2 any timed out. Pure ASCII.
`Tests/Invoke-AllTests.ps1` only picks up `*.Tests.ps1`, so the runner never runs in the gate's
test step.

**Proposed smokeCommand** (Michael sets it with /squad:configure after merge):
`powershell.exe -NoProfile -ExecutionPolicy Bypass -File Tests\Invoke-SmokeTest.ps1`
The gate (`verify-gate.ps1` `Invoke-Check`) runs it from the repo root through a `.cmd` file with
stdout/stderr redirected and kills the tree after `smokeTimeoutSeconds` (120).

**Guard.** `smokeCommand` is run by the gate's hook script, not by an agent's Bash call, so
`guard.appLaunchPatterns` never sees it. The proposed string would not match them anyway: the
`-File` target is `Invoke-SmokeTest.ps1`, not `*GUI.ps1`, and the runner starts the GUI with
`Process.Start` inside PowerShell, which the guard does not inspect. That also means an agent
could run the runner by hand during a run without the guard noticing; see the owner question.

**Docs.** `FolderPermissionManager/README.md`: a short "Smoke test" section (what it proves, what
it does not touch, the runner command, exit codes). Root README is unchanged (the runner is dev
tooling, not a tool for the service desk).

- Pester 5 under pwsh. New suites:
  `FolderPermissionManager/Tests/FolderPermissionManager-SmokeTest.Tests.ps1` (AC1-AC17) and
  `Tests/Invoke-SmokeTest.Tests.ps1` (AC18-AC22 unit; AC23-AC25 in a `Describe` tagged

- Loading: core then app with `-LoadFunctionsOnly`, `Set-TestAppPaths`-style isolation of

- In-process runs (AC3-AC8, AC16, AC17) follow App suite AC8_StartedWithoutLoadFunctionsOnlyGetsPastTheGuard:
  `& $AppPath ...` with Pester mocks, which are aliases and outrank the functions the script
  defines. Each throwing fake is also asserted with `Should -Invoke -Times 0 -Exactly`, so a
  missed path fails loudly instead of touching the machine. Backstops in every in-process test:
  `Start-Process`, `Request-Elevation`, `Enter-SingleInstance`, `Get-CimInstance`, `Set-Acl`,

  mocked in AC3-AC6 because the WPF assemblies load without side effects; if the host is not STA
  the in-process runs fake `Get-StartupAction`, so they do not depend on the runner's apartment.
- AC12 starts a real runspace pool (as App AC8e already does) and runs only the pure probe.
- AC13 runs only on an STA thread (skip otherwise, existing AC3/AC4 convention); it parses XAML
  and never calls `Show`/`ShowDialog`.
- Runner unit tests mock `Start-SmokeProcess` for every case; a backstop asserts it was the only
  route (a `Mock` of `Start-Process` that throws, and a static check that
  `[System.Diagnostics.Process]` appears only inside `Start-SmokeProcess`).
- Repo gates: `Tests\Test-ScriptParse.ps1` (5.1 parse; both files stay pure ASCII),
  `Tests\PSVersionFloor.Tests.ps1` (runner declares 5.1), `Tests\ScriptEncoding.Tests.ps1`.
- Edge cases covered: exit 0 without PASS (the 193a907 shape), non-zero exit, timeout and kill,
  non-STA host, smoke with -LogFolder/-DriveMap, -WhatIf allowed, an error routed to a message
  box or the error log during smoke, a change action triggered during smoke, the deadline.

What the tests cannot see:
- Whether the real window opens off-screen and still fires `ContentRendered` on Michael's
  workstation under Windows PowerShell 5.1 (WPF renders off-screen windows, but only a real run
  shows it), and how long a cold start takes there. AC23-AC25 cover this but are Integration-
  tagged, so the squad never runs them; Michael runs them once at review, then the gate's
  `smokeCommand` covers "the app starts" on every later item.
- Whether a smoke window ever becomes visible or takes focus (multi-monitor layouts with
  negative coordinates, display scaling). Michael should glance once while it runs.
- Behaviour with no interactive desktop (a locked workstation, a service session): expected to
  fail with a `[FAIL]` line rather than hang, but untested.
- Everything past the first render: drive listing, opening folders, the huge-folder tree
  (6dc992e), dialogs, changes. Those stay on the owner's try-list as before.
- The smoke runs non-elevated, so an elevation-only startup failure would not be seen.

## Decisions
### Confirmed by the owner
- D-062 (Q1): when `smokeCommand` is set after merge, a guard rule blocks agents from running
  `Tests\Invoke-SmokeTest.ps1` by hand. Not part of this item's code.
- D-061 (Q2): the six other GUIs get their own smoke-mode items (SQ-031..SQ-036) after this one;
  the runner should take a list of GUIs so each can be added in one line.
- Related: D-038 (WebGUI slated for removal, so it gets no smoke mode), D-041 (FPM WPF
  app is the current GUI).

### Assumed by the squad
- Scope is FolderPermissionManager-GUI.ps1 only; other GUIs are follow-ups. Reason: the backlog
  item and the caller name only FPM; each GUI has its own startup path, and the runner's target
  list makes adding one cheap later.
- A separate runner (`Tests/Invoke-SmokeTest.ps1`) rather than calling the GUI directly in
  `smokeCommand`. Reason: under `-File` a script that returns early exits 0, which is exactly the
  193a907 failure; the runner also requires the `[PASS]` line, enforces its own timeout below the
  gate's, and gives one place to add GUIs. Evidence: `verify-gate.ps1` fails only on non-zero exit
  or timeout.
- Success is positive proof (ContentRendered plus a background round trip, then a `[PASS]` line),
  never "no error". Reason: 193a907 produced no error at all.
- Off-screen, not hidden or minimised. Reason: a hidden window never renders, so ContentRendered
  would not prove anything; off-screen with ShowActivated false does not disturb the desktop.
- The admin check (`WindowsPrincipal.IsInRole`) still runs in smoke mode; only its consequence is
  skipped. Reason: it reads the process token only, and keeps the real startup path.
- The single-instance mutex is skipped, not given a smoke-only name. Reason: its logic is unit
  tested (App suite), and a skipped lock cannot collide with a window Michael has open.
- No drive, CIM, registry (HKCU:\Network, OneDrive keys) or settings reads; no gui-errors.log
  trim. Reason: backlog item ("no drive or network reads, no log writes") and SQUAD.md "Agents do
  not read this machine while building" plus the system-configuration "Machine reads" section.
- The background pool and one pure probe task do run. Reason: the pool is part of startup and a
  broken pool would break every pane; the probe reads nothing.
- Exit codes: app `-SmokeTest` 0 pass / 1 fail; runner 0 pass / 1 fail / 2 timeout. Window
  deadline 30 s, runner timeout 90 s, gate 120 s. Reason: each layer reports before the one
  outside it kills it.
- `-SmokeTest` with `-LogFolder`/`-DriveMap` is refused rather than ignored. Reason: either value
  would steer the smoke toward real folders or mappings; a refusal is clearer than silent
  ignoring.
- Messages that would be boxes, error-log lines and change actions count as smoke failures.
  Reason: a modal box would block the unattended gate; an error-log line means something failed
  that a user would hit.
- The runner and the switch ship with the tool folder / repo; the switch is harmless in the
  ServiceDesk-Toolkit bundle. Reason: self-contained folders; no separate build needed.

## Risk and safety notes
- destructive-operations applies (path `FolderPermissionManager/**`). The item changes no write
  path, but it adds branches to the startup of a tool that changes permissions, so AC17 pins that
  the normal start (drive map, elevation) still runs, and the existing App/AppChanges suites must
  stay green unchanged.
- Elevation, prompts and shutdown section: the smoke mode is a "nothing changes" mode, so its help
  lists the startup writes, which are none (AC1, AC5). It never relaunches (no path hand-off to an
  elevated copy), takes no `Global\` mutex, and its shutdown goes through the same
  `Invoke-AppShutdown`; no change can be running because change actions are refused (AC15) and no
  folder is ever selected.
- system-configuration "Machine reads and test fakes": every machine read the smoke skips is
  faked to throw in the in-process tests and asserted not hit (AC5, AC6).
- Tests never launch the GUI outside the Integration tag. The runner's unit tests never start a
  process. Agents do not run the runner or the Integration tests during runs (SQUAD.md "Real
  systems"; run skill: "nobody else runs it").
- The smoke process inherits Michael's token when the gate runs it; it is non-elevated and opens
  nothing on the network.
