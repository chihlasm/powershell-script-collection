# SQ-019 · M365 user check: blocked synced user advice must escalate, not "change it" (D-017)

- status: ready
- size: S
- risk: medium
- touches: `M365-UserQuickCheck/M365UserCheck.Core.ps1` (next-step strings only),
  `M365-UserQuickCheck/Tests/M365UserCheck.Core.Tests.ps1`, `M365-UserQuickCheck/README.md`

## Summary (plain English)
When the M365 user check finds a synced user whose sign-in is blocked but it could not compare
with on-premises AD, it currently tells the tech to "change it in on-premises AD if it is wrong",
which can mean removing a block a senior engineer set on purpose. This fix makes that step say
"Check with the senior engineer" first, as the same case already does when AD was read. Every
step that turns an account back on gets the same check with the manager that AD-UserQuickCheck
uses. A wider test makes sure no next step anywhere in the tool tells tier 1 to undo a block
without that check.

## What users will be able to do
- A tier 1 tech who runs the check without RSAT, with `-SkipOnPremises`, or where no DC answers,
  and gets "Sign-in is blocked" for a synced user, is told to check with the senior engineer
  before undoing the block, and how to find out which kind of block it is (run the check again
  where it can read AD). They are never told to "change it" on their own.
- Every "turn it back on" step (AD account disabled, cloud account blocked, sign-in error 50057,
  AD disabled while Microsoft 365 still allows sign-in) starts with a check with their manager
  that the account should be back in use. This is the wording AD-UserQuickCheck already uses
  (pending Q1).
- When AD is disabled but Microsoft 365 still lets the user in, the step also says that a
  deliberate disable (a leaver) reaches Microsoft 365 at the next sync, and to check the Entra
  Connect server if it does not. Today it only says "enable the AD account".
- The ticket note, console, HTML and CSV show the new steps automatically. They all read
  `Reason.Action`.

## Acceptance criteria
Tests live in `M365-UserQuickCheck/Tests/M365UserCheck.Core.Tests.ps1`, in a new
`Describe 'SQ-019 next steps never undo a block without a check'` that reuses the file's
`New-Facts` / `New-HybridFacts` / `New-AdUser` / `New-AdGate` fixtures. The `SQ019_` prefix
keeps them apart from SQ-002's AC1-AC29 in the same file.

The checker used by AC6-AC8 (defined once in the test file's `BeforeAll` as
`Test-M365StepNeedsApproval`, returning the failing reason or `$null`):
- **Reversal pattern** (case-insensitive):
  `\b(remov\w*|delet\w*|clear\w*|undo\w*|undoing|change it|unblock\w*|re-?enable\w*|enable|reset)\b`.
  Bare `enable` does not match "enabled" / "enabling", so status text such as "AD has the
  account enabled" is not flagged.
- **Marker pattern**: `block marker|BlockCloudSignIn|cloudExtensionAttribute10`.
- **Escalation phrases**: `Escalate`, `Check with the senior engineer`,
  `Ask the senior engineer`, `involve the security lead`.
- **Manager phrase**: `Check with their manager` (case-insensitive, so it also matches
  mid-sentence "check with their manager").
- A step passes when (a) it matches neither pattern; or (b) an escalation phrase appears before
  the first reversal or marker match; or (c) it does not match the marker pattern, every reversal
  match is `enable`/`re-enable`/`unblock`, and the manager phrase appears before the first
  reversal match (Q1 option A; with option B, rule (c) is dropped); or (d) it is exactly one of
  the four pinned password steps (AC7).

1. **SQ019_AC1_NoAdSyncedBlockedEscalates:** Given a synced user (`onPremisesSyncEnabled = $true`)
   with `accountEnabled = $false`, when the AD comparison did not explain the block, then the
   SignInBlocked `Action`:
   - starts with `Check with the senior engineer`;
   - contains `on-premises AD`, `M365-SyncedUserFixes` and `-Server`;
   - does not contain `Change it`.

   This is checked in four cases: no `OnPremisesGate` at all (SQ-002 shape), gate `NotChecked`
   (-SkipOnPremises), gate `Failed`, and gate `Available` with `AdUser = $null`. This is the
   regression test for the old line-829 text.
2. **SQ019_AC2_AdDisabledBlockedNeedsManagerCheck:** Given a synced user blocked in Microsoft 365
   and an AD account with `Enabled = $false` and no marker, then the SignInBlocked `Action`

   the next sync. With Q1 option B, it starts with `Escalate` instead.
3. **SQ019_AC3_AdDisabledCloudEnabledNeedsManagerCheck:** Given a synced user allowed in
   Microsoft 365 and an AD account with `Enabled = $false`, then the AdDisabledCloudEnabled
   `Action`:
   - starts with `Check with their manager`;
   - contains the tenant last-sync sentence (`2026-10-17 13:40 UTC` for that fixture);
   - says that a deliberate disable reaches Microsoft 365 at the next sync and to check the
     Entra Connect server if it does not;

   The Warning level and Message do not change.
4. **SQ019_AC4_Error50057NeedsManagerCheck:** `Get-M365SignInNextStep -Code 50057 -Synced $true`
   puts `check with their manager` before `enable`, and names the senior engineer for a block
   set on purpose with M365-SyncedUserFixes. The cloud-only 50057 step is unchanged (it already
   passes).
5. **SQ019_AC5_EnabledMismatchStepDropsMarkerWording:** Given AD enabled, Microsoft 365 blocked,
   no marker, then the SignInBlocked `Action`:
   - still points to `"AD and Microsoft 365 disagree"`;
   - does not match the marker pattern (it says "not blocked on purpose with
     M365-SyncedUserFixes" instead of "without the ... block marker").
6. **SQ019_AC6_NoReversalStepWithoutApproval:** Every next step the core can produce passes the
   checker. That covers:
   - every reason `Action` from the existing D017 scenario list, plus the four AC1 no-AD cases
     and the AC3 case;
   - `$script:M365NoSignInHistoryStep` and `$script:M365AddressCheckStep`;
   - `Get-M365SignInNextStep` for each mapped code (50053, 50055, 50057, 50126, 53003, 530035)
     with `-Synced $false` and `$true`.

   This widens `D017_NoRemovalStepForTier1` in place: its scenario list gains the AC1 cases and

7. **SQ019_AC7_PasswordStepsPinned:** The rule-(d) exemption is exactly the four strings
   `Get-M365SignInNextStep` returns for 50055 and 50126 (synced and cloud). The test asserts:
   - each one matches the reversal pattern only through `reset` / `change it` (password wording);
   - the exempt list has exactly four entries.

   So a new "reset" or "change it" step cannot reuse the exemption.
8. **SQ019_AC8_CheckerIsNotVacuous:** The checker rejects each of these known-bad samples:
   - the old line-829 SignInBlocked text;
   - the old AdDisabledCloudEnabled text (`If they should be able to sign in, enable the AD account ...`);
   - the old line-680 text;
   - `Clear the marker and wait for the next sync.`;
   - `Undo the block in AD.`;
   - `Check with their manager, then remove the block marker.` (the manager phrase is not
     enough for the marker);
   - `Reset the sign-in block.`

   It accepts the new AC1, AC2 and AC3 texts.
9. **SQ019_AC9_ReadmeStepsMatch:** In `M365-UserQuickCheck/README.md`, every "What to do" cell

   - the "Sign-in is blocked" row's synced part says to check with the senior engineer before

## Approach
- `M365UserCheck.Core.ps1`: change the strings only, with no change to control flow.
  - **Line 829**, synced fallback in `Get-M365UserAssessment`. Proposed:
    `Check with the senior engineer before undoing this block. The account syncs from on-premises AD, so the block comes from there: either the AD account is disabled, or it was blocked on purpose with M365-SyncedUserFixes (block marker msDS-cloudExtensionAttribute10 = BlockCloudSignIn). This check could not compare it with the AD account: run it again where it can read AD (on a client server, or with -Server and -Credential) to see which.`
    It is worded "could not compare" because the same fallback is reached when AD was read but
    the account was not found (AdAccountNotFound).
  - **Line 680**, AD disabled (option A):
    `Check with their manager that the account should be back in use, then enable it in on-premises AD (AD-UserQuickCheck shows its state) and wait for the next sync: the AD account is disabled, and sync carries that to Microsoft 365.`
  - **Line 684**:
    `On-premises AD has the account enabled and it was not blocked on purpose with M365-SyncedUserFixes, so the block has not come from AD this sync: see "AD and Microsoft 365 disagree".`
  - **Line 688**, AdDisabledCloudEnabled:
    `"Check with their manager whether they should still be able to sign in. If not (a leaver), Microsoft 365 blocks sign-in at the next sync: $lastSyncText If it stays allowed after that, check the Entra Connect server. If they should, enable the AD account (AD-UserQuickCheck shows its state)."`
  - **Line 738**, 50057 synced:
    `The account is disabled. It syncs from on-premises AD, so look at the AD account with AD-UserQuickCheck. If it is disabled there, check with their manager that it should be back in use, then enable it in AD and wait for the next sync. If AD has it enabled, it may have been blocked on purpose with M365-SyncedUserFixes: check with the senior engineer.`
  - **Line 831**, cloud-only, and line 739 (50057 cloud): unchanged. They already start with, or
    contain before the verb, `Check with their manager`.
  - Keep every string ASCII, with straight quotes and no em dashes, so the file's encoding needs

  - The PowerShell version floor is unchanged: there is no new syntax.

## Decisions
### Confirmed by the owner
- D-050 (2026-10-19 plan, Q1 = option C): re-enabling or unblocking a plain disabled/blocked account (no block marker, not a risky user) needs a manager check **and** the approver noted on the ticket. Amends AC2, AC3, AC4, AC6, AC8, AC9: every step the ACs say "starts with / puts `Check with their manager`" must read "Check with their manager that the account should be back in use, note on the ticket who approved it, then enable it ..." (wording may be tightened; both phrases must stay). Checker rule (c) requires the manager phrase **and** `note on the ticket who approved` before the first `enable`/`re-enable`/`unblock` match. AC8 adds a known-bad sample with the manager phrase but no approver note. The existing cloud-only step and the 50057 step change the same way. AD-UserQuickCheck (`Get-ADUserQuickCheck.ps1:422`) keeps the manager check without the approver note: out of scope here; note it in the run report as a follow-up.
- D-017: a destructive or reversing next step says "Escalate" plus the reason, and tier 1 never
  sees it as a plain instruction.
- D-014: the AD stage can be "could not check", and the tool still gives a verdict. That is why
  the no-AD fallback text matters.

### Assumed by the squad
- **The no-AD synced step starts with "Check with the senior engineer"**, even though the block
  may be a plain disabled account. Without AD the tool cannot tell a deliberate marker block from
  a disable. The backlog asks for the D-017 wording, and the with-AD marker case already uses it
  (`M365UserCheck.Core.ps1:678`). The step tells the tech how to get the precise answer (run
  again with AD).
- **Rule (b) uses "an escalation or manager phrase before the first match", not "the step starts
  with".** Steps like 50057 begin with a fact ("The account is disabled.") before the check. The
  approval must come before the action in reading order, which "before the first match" enforces.
- **`reset` stays in the verb list, with an exact-string exemption for the four password steps.**
  The read-only-advisory risk profile asks for a wide verb list including reset. Password resets
  are routine tier 1 work, not undoing a deliberate block, so they are pinned by exact string
  (AC7) rather than dropped from the list.
- **"involve the security lead" counts as escalation.** It is the existing RiskyUser step
  (`M365UserCheck.Core.ps1:885`), and the security lead is a more senior route than the senior
  engineer.
- **Line 684 is reworded** to drop "block marker". The backlog rule is that any step mentioning
  the marker needs escalation, and this step only states the marker is absent. Rewording keeps
  the rule simple with no exceptions.
- **Tests are named `SQ019_AC<n>_...`**, because this file already holds SQ-002's `AC1`-`AC29`.
  This is the closest idiom to the squad's `AC<n>_` rule without name collisions.
- **`D017_NoRemovalStepForTier1` is widened in place.** The backlog asks for that, and the change
  only makes it stricter, so nothing is weakened.

  enumerates every reason code and action string, and a wide verb list.

  says Escalate. AD-UserQuickCheck, the existing cloud-only M365 step and this backlog item use a
  manager check instead.
  - If the owner picks option A, record a D-entry, and the profile line should be clarified

    AD-UserQuickCheck gets a follow-up item.
- **Destructive-operations profile:** not directly. The code still writes nothing, and the
  static read-only guard tests are untouched. The marker it refers to is written only by

- **Personal-data profile:** no change. No new fields reach the ticket note or the CSV.
