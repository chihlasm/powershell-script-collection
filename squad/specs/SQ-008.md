# SQ-008 · FolderPermissionManager: back up permissions and log every change

- status: ready
- size: L (proposed split into SQ-008a and SQ-008b, see "Split" below)
- risk: high
- touches: FolderPermissionManager GUI backend (`FolderPermissionManager-GUI.ps1`), a new
  core file in the same folder, the GUI's status messages, the CLI script
  (`FolderPermissionManager.ps1`, subject to Q3), README, `.gitignore`, new Pester tests

## Summary (plain English)
Today, when a tech changes folder or file permissions in FolderPermissionManager, the tool
keeps no copy of what the permissions were before and no record of who changed what. After
this change, the tool saves the current permissions to a backup file before every change, and
it adds a line to a daily change log saying who made the change, when, on which path, and what
the permissions were before and after. Any change can then be proven and undone.

## What users will be able to do
- Make the same permission changes as today (add or remove a permission, take ownership, copy
  permissions to other folders, for folders and for selected files). Before anything changes,
  the tool saves the current permissions. If it cannot save them, it changes nothing and says
  why.
- After each change, the status bar shows what was done and where it was logged, for example
  "Added Modify for CONTOSO\HR-Staff on \\FS01\Data\HR. Backed up and logged to
  C:\Tools\FolderPermissionManager\Logs\Changes_2026-10-17.csv." Partial failures show how
  many items failed, plus the first error.
- Open `Logs\Changes_<yyyy-MM-dd>.csv` to see every change made from this copy of the tool,
  one row per item, with the previous and new permissions. Backups are in `Logs\Backups\`.
- Follow the README's "Undo a change" section to put back the saved permissions, either for one
  folder or file (from the saved SDDL) or for a whole tree (`icacls /restore`).
- The console shows at startup where changes will be logged.

## Change-log format (pinned; SQ-009 LocalAdminManager uses the same format)
This follows `Write-SyncedUserChangeLog` and `Set-SyncedUserMarker` in
`M365-SyncedUserFixes/SyncedUserFixes.Core.ps1`. Column names are generalized because
M365-SyncedUserFixes is AD-specific (`User`/`Attribute`). M365-SyncedUserFixes is not changed.

- **File:** `<LogFolder>\Changes_<yyyy-MM-dd>.csv`, appended, one header row per file, written
  with `ConvertTo-Csv -NoTypeInformation` + `Add-Content -Encoding UTF8` (same as M365).
- **Default `LogFolder`:** `Logs` next to the script (`$PSScriptRoot\Logs`), overridable with
  `-LogFolder`. Same reason as M365: when a script runs as administrator, the current directory
  is `C:\Windows\System32`.
- **Columns, in this order:**

| Column | Meaning | FolderPermissionManager | LocalAdminManager (SQ-009) |
|---|---|---|---|
| `Time` | `yyyy-MM-dd HH:mm:ss`, local time | same | same |
| `Technician` | `[Security.Principal.WindowsIdentity]::GetCurrent().Name` | same | same |
| `Computer` | `$env:COMPUTERNAME`, the machine the tool ran on | same | same |
| `Action` | Plain-English verb | `Add permission`, `Remove permission`, `Take ownership`, `Take ownership (all subfolders and files)`, `Copy permissions`, `Copy permissions (all subfolders and files)` | `Add administrator`, `Remove administrator` |
| `Target` | What was changed | Full path after mapped-drive resolution (UNC when mapped) | `<ComputerName>\Administrators` |
| `ItemType` | Kind of target | `Folder`, `File`, `Folder tree` | `Local group` |
| `Detail` | One plain-English sentence | e.g. `Allow Modify for CONTOSO\HR-Staff` | e.g. `CONTOSO\jsmith` |
| `OldValue` | Value before | SDDL of the item (`Get-Acl`'s `.Sddl`); for tree actions `Saved in <backup file>` | Member list before, `; `-separated |
| `NewValue` | Value after | SDDL read back after the change; for tree actions a summary, e.g. `Owner: CONTOSO\tech` | Member list after |
| `Result` | Outcome | `Done`, `Failed`, `Partly done`, `Skipped (WhatIf)`, `Skipped (not found)` | same set |
| `Error` | Error text, empty on success | same | same |
| `BackupFile` | Path to the backup written before the change, or empty | same | empty (old list is in `OldValue`) |

Tool-specific columns, if a tool ever needs one, go after `BackupFile`. The squad does not need
a shared module for this: each tool carries its own `Write-*ChangeLog` with the same column set.
A parity test is optional and is not required here.

## Backup format
- **Single items** (folder or file actions that use `Set-Acl`): one CSV per action at
  `<LogFolder>\Backups\<yyyy-MM-dd_HHmmss>_<ActionSlug>.csv` with columns `Path, ItemType, Sddl`,
  one row per item, written **before** the first `Set-Acl`.
- **Folder trees** (the "all subfolders and files" options that use `icacls ... /T`):
  - Copy permissions (all subfolders and files): `icacls "<target>" /save "<backup>.acl" /T /C`
    to `<LogFolder>\Backups\<yyyy-MM-dd_HHmmss>_CopyPermissions_<n>.acl`, before `/reset`.
  - Take ownership (all subfolders and files): `icacls /save` does not store owners (verify on
    Learn, see Approach), so write `<yyyy-MM-dd_HHmmss>_TakeOwnership.csv` with
    `Path, ItemType, Owner, OwnerSid` for every folder and file under the target, before
    `takeown`. Items whose owner cannot be read are listed with `Owner` = `Could not read`.
    What happens next with them depends on Q1.

## Acceptance criteria
Each maps to exactly one Pester test named `AC<n>_...`. ACs 1-13 are SQ-008a; ACs 14-21 are
SQ-008b.

### SQ-008a: core, single-item actions, and the GUI
1. AC1: Given a folder in `$TestDrive`, when Add permission runs, then a backup CSV containing the
   folder's pre-change SDDL exists at the moment `Set-Acl` is called (the `Set-Acl` mock asserts
   that the file exists and holds the old SDDL), and `Set-Acl` is called exactly once.
2. AC2: Given the backup cannot be written (`New-Item`/`Export-Csv` mocked to throw), when any
   change is requested, then `Set-Acl` and the native-tool wrapper are never called, and the
   result is `Failed` with an error that starts "Could not save a backup of the current
   permissions" and ends "Nothing was changed."
3. AC3: Given a successful Add permission on a folder, then the change-log row has exactly the
   pinned columns in the pinned order, `Time` matches `^\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}$`,
   `Action` = `Add permission`, `ItemType` = `Folder`, `OldValue` = the pre-change SDDL,
   `NewValue` = the SDDL read back after the change, `Result` = `Done`, and `BackupFile` = the
   backup path.
4. AC4: Given a successful Remove permission on a folder, then the row has
   `Action` = `Remove permission`, `Detail` naming the identity, rights and Allow/Deny, and the
   old and new SDDL.
5. AC5: Given three selected files where the second one's `Set-Acl` throws, when Add permission
   runs on the files, then one backup CSV has three rows, the log has three rows (`Done`,
   `Failed` with the error, `Done`), and the third file is still processed.
6. AC6: Given a folder, when Take ownership (this folder only) runs, then the backup holds the
   old SDDL including the previous owner (`O:` part), and the row has
   `Action` = `Take ownership`.
7. AC7: Given two target folders where one does not exist, when Copy permissions (this folder
   only) runs, then the existing target is backed up, changed and logged `Done`, and the missing
   one is logged `Skipped (not found)` with no `Set-Acl` call for it.
8. AC8: Given `-WhatIf` on each core change function, then no `Set-Acl` or native-tool call
   happens, no backup file is written, and each returned row has `Result` = `Skipped (WhatIf)`.
9. AC9: Given two writes to the change log on the same day, then both go to one
   `Changes_<yyyy-MM-dd>.csv` with a single header row and all rows present.
10. AC10: Given the log folder cannot be written after a change succeeded, then the log writer
    returns `$null` without throwing, and the result message says the change was made but
    "the change log could not be written to <folder>", plus the backup path.
11. AC11: Given the default log folder is not writable (mocked), when the log folder is
    resolved at startup, then it falls back to `$env:LOCALAPPDATA\FolderPermissionManager\Logs`.
    Given `-LogFolder` is passed, that folder is used unchanged.
12. AC12: Given a folder whose name contains `[` and `]` (e.g. `HR [old]`) in `$TestDrive`, when
    Add permission runs, then the backup holds that folder's real SDDL (regression guard: the
    current code uses `-Path`, which treats brackets as wildcards).
13. AC13: Given a backed-up SDDL and an ACL object that was modified afterwards, when
    `SetSecurityDescriptorSddlForm` is applied to the modified object with the backed-up SDDL,
    then its access rules and owner equal the original's. This proves the backup is enough to
    undo the change. The test works on in-memory ACL objects and does not call `Set-Acl`.

### SQ-008b: whole-tree actions and the CLI
14. AC14: Given Copy permissions (all subfolders and files), then the native-tool wrapper is
    called with `icacls <target> /save <backup> /T /C` before any `/reset` or `/grant` call
    (call order asserted), and the row's `OldValue` = `Saved in <backup>`.
15. AC15: Given the tree backup failed outright (non-zero exit and no backup file written),
    then no `/reset`, `/grant` or `/deny` call is made and the row is `Failed` with "Nothing was
    changed."
16. AC16: Given Take ownership (all subfolders and files), then the owner snapshot CSV is
    written with one row per item before the `takeown` call, and the row's `NewValue` =
    `Owner: <current identity>`.
17. AC17: Given a tree action where the native tool returns an exit code meaning some items
    failed, then the row's `Result` = `Partly done` and `Error` holds the tool's output summary.
18. AC18: Given a tree where some items' owners cannot be read, then the action follows the Q1
    decision (default if Q1 is answered as recommended: it continues, the snapshot lists those
    items as `Could not read`, and the result message says "<n> items had no readable
    permissions before the change and cannot be restored from this backup").
19. AC19 (only if Q3 = include the CLI): Given `FolderPermissionManager.ps1 -Path <dir> -WhatIf`,
    then no native-tool or `Set-Acl` call is made.
20. AC20 (only if Q3 = include the CLI): Given the CLI is run without `-Force` and the
    confirmation is declined, then ownership is not taken and permissions are not copied. Today
    the CLI takes ownership recursively before it asks anything.
21. AC21: Given the real `Get-Acl` and `Set-Acl` cmdlets (`Microsoft.PowerShell.Security`,
    always present), then every parameter the core passes to them (`LiteralPath`, `AclObject`,
    `ErrorAction`, `WhatIf`) exists on the real cmdlet (`Get-Command`). This guards against
    mocks that share a wrong parameter name.

## Out of scope
- An in-tool Undo or Restore button (Q2). v1 documents restore steps in the README.
- Robocopy actions (`/api/robocopy`, `/api/robocopy-files`). They copy data, and `/COPY:DATSO`
  overwrites destination ACLs. That is a separate risk item: mirror mode already has a preview
  and confirmation.
- Fixing the existing bugs found while reading (listed under Risk and safety notes), except the
  `-LiteralPath` use in the new backup code.
- Showing scope ("this will change 1,240 items on FS01") in the confirmation dialogs. The risk
  profile asks for this, but it is a separate GUI item.
- Retention or cleanup of logs and backups. They are never deleted automatically.
- SQ-001 ticket-note stamp and SQ-004 hand-off. This item only exposes the log path they will use.
- Changing M365-SyncedUserFixes' log columns.

## Approach
- **New core file** `FolderPermissionManager/FolderPermissions.Core.ps1`, following the
  `M365-SyncedUserFixes/SyncedUserFixes.Core.ps1` split (SQUAD.md: logic separated from UI). The
  GUI and the CLI dot-source it. It contains:
  - `Resolve-ChangeLogFolder` (default, `-LogFolder`, LOCALAPPDATA fallback, AC11)
  - `New-PermissionChangeEntry` (the pinned columns)
  - `Save-AclBackup` (single items, SDDL CSV) and `Save-TreeAclBackup` (icacls `/save`) and
    `Save-OwnerSnapshot` (recursive take-ownership)
  - `Invoke-AclTool` (a thin wrapper around `icacls.exe`/`takeown.exe` returning
    `ExitCode` and `Output`, so Pester can mock native commands)
  - Change functions with `[CmdletBinding(SupportsShouldProcess)]` and `ShouldProcess` per
    target, each returning one entry per item and never throwing (pattern: `Set-SyncedUserMarker`):
    `Add-FolderPermission`, `Remove-FolderPermission`, `Set-ItemOwnerToCurrentUser`,
    `Copy-FolderPermission`, each with a `-Recurse` switch where the GUI has one, and taking
    `-Path` arrays for the file batch endpoints
  - `Write-PermissionChangeLog` (a copy of `Write-SyncedUserChangeLog` under this name)
  - `Get-ChangeResultMessage` (builds the status-bar text from entries, log path and backup path)
  - `if ($LoadFunctionsOnly) { return }` guard, as in the M365 core.
- **GUI** (`FolderPermissionManager-GUI.ps1`): add `-LogFolder`, dot-source the core, print
  `[INFO] Changes are backed up and logged to <folder>` at startup. The handlers for
  `/api/take-ownership`, `/api/replicate`, `/api/add-ace`, `/api/remove-ace`,
  `/api/file-acl/add`, `/api/file-acl/remove`, `/api/file-acl/take-ownership` stay thin: they
  parse the request, call the core, write the log, and return the existing JSON shape plus
  `message`, `logPath`, `backupPath`. The JS `then` handlers show `r.message` in the status bar
  instead of their fixed strings ("ACE added", etc.). The recursive take-ownership confirm text
  "This cannot be undone" becomes "The current owners will be saved to a backup first."
  Keep the existing behavior of each action (same icacls/takeown arguments, same rules added).
  Only the backup, logging and messages are new.
- **CLI** (Q3): bring `FolderPermissionManager.ps1` up to the conventions it needs for this:
  `[CmdletBinding(SupportsShouldProcess)]`, help block, `-Force`, `-LogFolder`, confirmation
  before taking ownership, backups and log through the core.
- **README**: "Changes are logged" section (log location, columns, backups), "Undo a change"
  (single item: read `Sddl` from the backup CSV, `$acl = Get-Acl -LiteralPath $p;
  $acl.SetSecurityDescriptorSddlForm($sddl); Set-Acl -LiteralPath $p -AclObject $acl`; tree:
  `icacls "<parent of target>" /restore "<backup>.acl" /C`; owners: from the owner snapshot),
  and requirements. Add `FolderPermissionManager/Logs/` to `.gitignore` next to the M365 entry.
- **Microsoft facts to verify on Learn before coding and cite in `.NOTES` REFERENCES** (root
  CLAUDE.md): `icacls` `/save`, `/restore`, `/T`, `/C` and exit codes. In particular, confirm
  that `/save` stores DACLs only (no owner, SACL or integrity label), and that `/restore` takes
  the *parent* directory. Also verify `takeown` `/R /A /D`; `Get-Acl` (`-LiteralPath`, the `.Sddl`
  property, and that the SACL is excluded without `-Audit`); `Set-Acl` (`-LiteralPath`,
  `-AclObject`, `-WhatIf`); and
  `ObjectSecurity.SetSecurityDescriptorSddlForm` / `GetSecurityDescriptorSddlForm`.
- Plan documents: `docs/plans/2026-03-20-folder-permission-manager-gui.md` and
  `docs/superpowers/specs/2026-04-07-folder-permission-manager-v2-design.md` describe the
  current endpoints. Neither covers logging.

### Assumed by the squad
- **The backup is written before the change, and the change is refused if the backup fails.**
  Evidence: `squad/risks/destructive-operations.md` ("ACLs are exported (`Get-Acl` / SDDL)
  before `Set-Acl`").
- **The log is written after the change, and a log-write failure does not undo the change but is
  reported.** Evidence: `Complete-MarkerChange` in `Start-M365SyncedUserFixes.ps1` ("The change
  log could not be written to ..."). The backup already exists at that point.
- **Both scripts in the folder are in scope** unless Q3 says otherwise. Evidence: the backlog item
  names the tool, and the risk profile path is `FolderPermissionManager/**`.
- **Log location:** `$PSScriptRoot\Logs` with `-LogFolder`, as in M365-SyncedUserFixes.
  **LOCALAPPDATA fallback** (technical): techs often run tools from a read-only share or bundle
  copy. With fail-closed backups, an unwritable folder would block every change.
- **Pinned column set** generalized from M365's (`User`/`Attribute` become `Target`/`ItemType`/
  `Detail`, plus `BackupFile`). Reason: SQ-009 needs a non-AD target, and the item asks for "who,
  when, path, old, new".
- **`Technician` from `WindowsIdentity.GetCurrent().Name`**, not `$env:USERDOMAIN\$env:USERNAME`.
  Evidence: the existing comment in `Invoke-TakeFileOwnership` says `$env:USERNAME` is unreliable
  under SYSTEM/service accounts.
- **SDDL as OldValue/NewValue** for single items. It is exact and restorable. `Detail` carries
  the plain-English sentence for helpdesk readers.
- **Tree actions log one row per action, not per item.** A per-item SDDL for a large tree would
  make the CSV unusable. The full state is in the `.acl` backup or the owner snapshot.
- **`icacls /save` for tree DACL backups.** It is Windows' own format and restores with one command.
  **The owner snapshot is a separate CSV**, because `/save` does not keep owners (to verify on Learn).
- **`Invoke-AclTool` wrapper** so that native commands can be mocked (SQUAD.md fakes rule).
- **New code uses `-LiteralPath`.** Paths with `[ ]` otherwise break `Get-Acl -Path` (AC12).
- **No SACL in backups.** None of the actions touch auditing entries, and reading them needs
  `SeSecurityPrivilege`.
- **No automatic cleanup of logs or backups.** Deleting audit records is itself destructive.
- **PowerShell version:** the GUI stays `#Requires -Version 5.1` (it already uses `::new()` and is
  an admin-workstation tool). If the CLI is included, the core avoids `::new()` and classes and
  declares 3.0, and the CLI declares 4.0 for `#Requires -RunAsAdministrator` (root CLAUDE.md
  version rules; CLI targets may be old file servers). Otherwise, the core declares 5.1.
- **The existing JSON response shapes are kept and fields are only added**, so the JS only
  changes in its status messages.

## Risk and safety notes
- The destructive-operations profile applies in full. Every `Set-Acl` and native-tool call is
  mocked in tests. The squad never launches the GUI or runs icacls/takeown against real paths.
- After this item, the tool meets the profile's "reversible" and "change log" lines. It still
  falls short on "show scope before confirming" for add/remove and copy permissions. That is a
  follow-up item, not part of this one.
- Existing bugs seen while reading, not fixed here (suggested follow-ups):
  - In `Invoke-ReplicatePermissions`, the recursive branch maps rights with `switch -Wildcard`
    and no `break`. `ReadAndExecute, Synchronize` matches both `*ReadAndExecute*` and `*Read*`, so
    `$perm` becomes an array and the `icacls /grant` argument is malformed. Rights such as
    `Write` combined with others can also map wrongly (the default is `R`).
  - The recursive branch runs `icacls /reset /T` on the target, which wipes explicit entries in
    the whole subtree. The new `.acl` backup is what makes that recoverable.
  - The non-recursive copy adds the source's *inherited* rules as explicit rules on the target.
  - The CLI takes ownership recursively before showing anything or asking (fixed only if Q3 =
    include).
  - Existing handlers use `Get-Acl -Path`/`Set-Acl -Path` (wildcard paths).
- Logs and backups contain client paths, account names and SIDs. They stay on the machine that
  ran the tool and are gitignored ("Output stays local", SQUAD.md).
- For SQ-009: `LocalAdminManager.ps1` calls `Add-LocalGroupMember`/`Remove-LocalGroupMember` with
  `-ComputerName`. To my knowledge those cmdlets have no such parameter. The SQ-009 planner should
  verify this on Learn, because it decides how "old and new member lists" are read remotely.

## Split
- **SQ-008a** (M): the core file, the pinned log format, single-item backups and logging for every
  GUI action that uses `Set-Acl` (add/remove for folders and files, take ownership of one folder or
  files, copy permissions to one folder), GUI messages, README, `.gitignore`. ACs 1-13 and 21.
  SQ-009 can start once this lands.
- **SQ-008b** (M): whole-tree actions (`icacls /save` before the recursive copy, the owner snapshot
  before recursive take-ownership, `Partly done`, unreadable items per Q1) and the CLI per Q3.
  ACs 14-20.
