# SQ-028 · FolderPermissionManager: a bare account name on a network folder must not resolve to this workstation's local account

- status: ready
- feature: FolderPermissionManager rewrite
- size: M
- risk: high
- depends-on: SQ-023 (hard: needs the reparse-info reader `Get-AppReparseInfo` in the core; SQ-023 itself waits for SQ-024). Build after SQ-022 and SQ-025 (soft: they edit the same core change functions and the permission dialog, so building later avoids merge conflicts. SQ-025 is P1 anyway.)
- touches: `FolderPermissionManager/FolderPermissions.Core.ps1` (new locality and account checks, `Add-FolderPermission`), `FolderPermissionManager/FolderPermissionManager-GUI.ps1` (`Resolve-AddIdentity`, `Test-AddTargetOnThisComputer`, `Find-PermissionAccount`, the Add dialog, `Invoke-AddPermission`, `$script:AddPermissionWork`), `FolderPermissionManager/README.md`, `FolderPermissionManager/Tests/*`
- risk profiles: destructive-operations (in full: "Right target, right object", "Safety rules live in the core", "Overrides and refusals", "Advice and commands")

## Summary (plain English)
When a tech adds a permission and types a bare name like `micha`, Windows looks the name up on
the tech's own PC first. If that PC has a local account called `micha`, the permission on
`\\fs01\share` goes to the PC's account, which the file server cannot use. The tool still says
"Done". After this item, the tool sees that the account belongs to this PC and refuses it on any
folder that is not on this PC. It shows the full account name (`CONTOSO\micha`) before the
change. A local folder that is really a link to a network share no longer counts as "this
computer" either.

## What users will be able to do
- Add Permission on `\\fs01\share\HR` (or a mapped drive, a DFS path, or a local link that
  leads to a share) with a name that turns out to be an account of this PC (`micha` resolving to
  `PC01\micha`, `.\micha`, or `PC01\micha` typed in full). The dialog stays open with the text,
  says the account only exists on this PC and the server cannot use it, and tells the tech to
  type the domain account or a domain group. Nothing is changed.
- Add Permission on a folder that really is on this PC (`D:\Data`) with a local account. This
  works as before (`.\micha` becomes `PC01\micha`).
- See which account the name resolved to (`CONTOSO\micha`) before the change starts (Q3 decides
  how). The confirm dialog, status line, result and change log name that resolved account.
- `D:\Link`, a directory symbolic link to `\\FS01\Data` on a Fixed drive, is not treated as
  this computer. `.\micha` there is refused, and so is `PC01\micha`. A symbolic link to another
  local disk still counts as this computer.
- Running the tool on a domain controller still lets domain accounts be added to remote shares.
  A DC has no accounts of its own.
- The browser GUI (to be removed) and any other caller of the core's `Add-FolderPermission` get
  the same refusal, as a `Failed` row. No new UI there.

(in the core after SQ-023). "The final-path seam" is the core's `Get-Win32PathName -Kind Final`.
"The drive seam" is `Get-DriveLetterType`. "The machine-SID seam" is the new

see Approach). Texts in quotes marked *[Q2]* or *[Q3]* are the recommended option's wording. If
the owner picks another option, the spec is revised before the build.

## Out of scope
- Looking names up on the server itself (`LookupAccountName` with the server as `lpSystemName`)
  so that `FS01\name` or a bare name resolves to the server's own accounts. That is Q2 option C
  and would be a new item.
- Remove Permission and SQ-025's Change Permission. Both act on the SID of an existing entry and
  never resolve a typed name (SQ-025 AC18: "the rule is built from the SID"), so they do not share
  this lookup path. Copy Permissions copies existing SIDs and is out of scope too.
- The CLI. It has no add step (D-035), so it gets no AC. It shares the core and would inherit the
  refusal.
- The browser GUI gets no AC and no UI work. It is removed after the SQ-018 lab test, and it
  inherits the core refusal as `Failed` rows, as in SQ-022.
- Warning about orphaned workstation SIDs that are already on server ACLs. Existing entries show
  as `S-1-...` and Remove handles them (SQ-018).
- A volume mounted in a folder with no drive letter. Its final path has no `X:\`, so it counts
  as not local and `.\name` there is refused. This is a rare, fail-closed false refusal, and
  typing a domain account still works.

## Approach
Builds on `main` after SQ-023 has merged (SQ-023 puts `Get-AppReparseInfo` in the core).

**Core (`FolderPermissions.Core.ps1`, `#Requires -Version 3.0`).** No `::new()`, classes or
`.Where()`. Use `New-Object`, and wrap with `@()` before `.Count`.
- `ConvertTo-IdentitySid` moves from the GUI into the core, unchanged, defined once. The app's
  background pool copies core functions (`Initialize-BackgroundPool`), so the work block and
  `Find-PermissionAccount`'s default lookup keep working. `Find-PermissionAccount`'s runspace runs
  the lookup from its text (`$Lookup.ToString()`), so the default lookup scriptblock must stay
  self-contained (see "Find-PermissionAccount" below).
- `Test-PathOnThisComputer -Path` returns `[PSCustomObject]@{ IsLocal; Reason }`:
  1. Only `^[A-Za-z]:\\` counts. Anything else is `$false`, with no machine read.
  2. The drive seam must give `Fixed` or `Removable`. If it throws, the answer is `$false`.
  3. Normalise doubled and trailing `\` the way `ConvertTo-ComparablePath` does, without
     resolving `..`. SQ-024 already refuses dot segments upstream. Then walk from the path up to,
     but not including, the drive root with `Get-AppReparseInfo`:
     - a missing entry or a non-reparse entry continues;
     - a tag in `$script:RedirectFreeReparseTags` continues;
     - any other tag records the first link (path and `Get-LinkKindName`);
     - a throw means `$false`, "could not be checked".
  4. If a link was recorded, the final-path seam on the full path must match
     `^\\\\\?\\([A-Za-z]):\\`, and that letter must pass step 2. Otherwise the answer is `$false`.
     The Reason names the link and where it leads (`\\?\UNC\x` shown as `\\x`), or says the
     destination could not be told. Deciding from the final path also covers a junction that
     leads to another link.
  This follows the risk profile rule: "a local symbolic link or mounted folder at or above the
  target that leads to UNC, is not local. When it cannot be decided, refuse."
- `Get-ThisComputerAccountDomain` is the machine-SID seam. It returns
  `[PSCustomObject]@{ Sid; Name; IsDomainController }` from
  `LsaOpenPolicy(POLICY_VIEW_LOCAL_INFORMATION)` and `LsaQueryInformationPolicy`:
  - `PolicyAccountDomainInformation` gives `POLICY_ACCOUNT_DOMAIN_INFO.DomainSid` and
    `DomainName`;
  - `PolicyDnsDomainInformation` gives `POLICY_DNS_DOMAIN_INFO.Sid`. When that SID equals the
    account domain SID, `IsDomainController` is `$true`.
  Buffers are freed with `LsaFreeMemory`, the handle is closed with `LsaClose`, and NTSTATUS is
  turned into an error with `LsaNtStatusToWinError`. Add-Type is used in the existing
  `FolderPermissionManager.*` namespace style. The result is cached in a script variable for
  the session. A failure is not cached, and the function throws.
  If Learn does not support "account domain SID equals primary domain SID on a DC", use
  `Win32_ComputerSystem.DomainRole` 4 or 5 instead, behind the same seam. That is a technical
  fallback that needs no owner input.
- `Get-ThisComputerAccountRefusal -Sid -Path [-AccountName]`:
  - A SID whose `AccountDomainSid` is `$null` (well-known, BUILTIN) gives `$null`.
  - Otherwise read the seam. If it throws: when every path is local, return `$null`; else
    return the AC11 text.
  - A DC gives `$null`.
  - `AccountDomainSid` not equal to the machine SID gives `$null`.
  - Otherwise: if every path is local, return `$null`; else return the AC7 text naming the first
    three non-local paths.
  - Paths are checked only when needed (AC9), so domain accounts cost no disk reads.
- `Add-FolderPermission` gains `[string]$Sid` (optional). Before `Invoke-SingleItemAclChange`:
  - Translate `-Identity` once through the name seam. If it does not translate, keep today's
    failure.
  - If `-Sid` is given and differs from the translation, every row is `Failed` (AC15).
  - Then use `-Plan` (the contract `Copy-FolderPermission` uses; SQ-022 pattern): per item,
    `Get-ThisComputerAccountRefusal -Sid $checked -Path $p` returns `Result 'Failed'` and
    `ErrorText "<refusal> Nothing was changed."`.
  - In `-Change`, run the refusal again just before `Set-Acl` and throw on refusal (late
    re-check, P-006).
  - `New-PermissionRule` gets an `-Sid` path that builds the `FileSystemAccessRule` from
    `New-Object System.Security.Principal.SecurityIdentifier`, so the SID that was checked is the
    one written. If SQ-025 has already added a SID-based rule builder, reuse it rather than add a
    second one.
- The `.NOTES` REFERENCES block gets every page listed under "Facts to verify" below.

**WPF app (`FolderPermissionManager-GUI.ps1`).**
- `Test-AddTargetOnThisComputer` becomes `(Test-PathOnThisComputer -Path $Target.ResolvedPath).IsLocal`.
  `IsLocal` no longer short-circuits. A local share's `ResolvedPath` is already its local folder
  (`Get-ChangeTarget`), and a UNC `ResolvedPath` is not local (AC17). Keep its comment updated
  and cite the risk profile line.
- `Resolve-AddIdentity`: same logic, with the new `.\name` text *[Q2]*.
- `Find-PermissionAccount`: the result gains `AccountName`. The default lookup returns the SID
  and `ConvertTo-SidAccountName` of that SID from the same timed runspace, so the reverse
  translation is inside the same 4-second limit. Test seams that return a plain SID string still
  work (`AccountName` is empty, and callers fall back to the name that was looked up). The
  existing AC56 tests keep passing unchanged.
- `Get-AddAccountProblem -Account -Targets -TypedIdentity` calls
  `Get-ThisComputerAccountRefusal` with the targets' `ResolvedPath`s, adding the "<typed> was
  found as " prefix when the typed text differs. `Get-AddAccountConfirmation` covers Q3.
- `Show-PermissionDialog` Add click order: input check, `Resolve-AddIdentity`,
  `Find-PermissionAccount` (busy state as today), `Get-AddAccountProblem` (an error keeps the
  dialog open, as AC56 does), then `Get-AddAccountConfirmation`. On the first click, show the text
  in a new info line `PermDialogFound`. This is not the red error block, and it gets a live region
  like `PermDialogError`. Store `Tag.ConfirmedSid` and return. Only a later click whose fresh
  lookup gives the same SID sets `Tag.Answer` (Identity = resolved `AccountName`, Sid). Enter
  still never submits a Deny.
- The disk read happens on the window thread. `Get-AddAccountProblem` reads the disk only for
  this-computer accounts (AC9). It runs right after the lookup, while the dialog already shows
  "Checking...", so the busy state covers it.
- `Invoke-AddPermission` gains `-Sid` and `-AccountName`. It runs `Get-ThisComputerAccountRefusal`
  again (a direct caller has not had the dialog), uses `AccountName` in Detail and the confirm,
  and passes both to `$script:AddPermissionWork`. That work gains a `[string]$Sid` parameter and
  passes `-Sid` to `Add-FolderPermission`. Its read-back already matches by identity, and gets
  the SID added.
- Wording follows the D-044/AC55 house style: what was found, why the server cannot use it,
  "nothing was changed", and the next step. The next step never points at a route that skips the
  check (risk profile "Overrides and refusals").

**README.** Rewrite the Add Permission paragraph (lines 89-95): local accounts are refused on
folders not on this computer (links included), the resolved name is shown first, and the new
`.\name` advice *[Q2]*.

**Facts to verify on Microsoft Learn and cite.** This spec agent had no web or Learn access in
its session, so none of these were re-fetched here. The builder must verify each one and quote it
next to the code:
- LookupAccountNameW: the search order for a name without a domain (well-known SIDs, built-in,
  this computer's accounts, then the primary domain, then trusted domains), and that `lpSystemName
  = NULL` means the local system. The guard checks the resolved SID and does not depend on the
  exact order, but the comment quotes it:
  https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-lookupaccountnamew
- NTAccount.Translate / SecurityIdentifier.Translate (already cited) and
  SecurityIdentifier.AccountDomainSid ("returns the account domain SID portion ... if the SID
  represents a Windows account SID; otherwise null"):
  https://learn.microsoft.com/dotnet/api/system.security.principal.securityidentifier.accountdomainsid
- LsaOpenPolicy, LsaQueryInformationPolicy, POLICY_INFORMATION_CLASS
  (PolicyAccountDomainInformation, PolicyDnsDomainInformation), POLICY_ACCOUNT_DOMAIN_INFO,
  POLICY_DNS_DOMAIN_INFO, LsaFreeMemory, LsaClose, LsaNtStatusToWinError, and what the account
  domain is on a domain controller. All are under
  https://learn.microsoft.com/windows/win32/api/ntsecapi/ (and
  https://learn.microsoft.com/windows/win32/cimwin32prov/win32-computersystem for the
  DomainRole fallback).
- Symbolic links can point to remote (UNC) targets, and remote-to-local and local-to-remote
  evaluation (`fsutil behavior set SymlinkEvaluation`, L2R on by default). This explains why
  `D:\Link` to `\\FS01\Data` works:
  https://learn.microsoft.com/windows/win32/fileio/symbolic-links and
  https://learn.microsoft.com/windows-server/administration/windows-commands/fsutil-behavior
- GetFinalPathNameByHandleW returns `\\?\UNC\server\share\...` for a network path with
  VOLUME_NAME_DOS. The page is already cited in the core; quote the UNC form.
- IO_REPARSE_TAG_SYMLINK 0xA000000C and IO_REPARSE_TAG_MOUNT_POINT 0xA0000003 (MS-FSCC 2.1.2.1)
  are already cited at `$script:SymbolicLinkReparseTag`.

## Test plan
- Pester 5 under `pwsh`. Core ACs (1-15, 22) go in `FolderPermissionManager/Tests/` next to the
  core suites, which load `FolderPermissions.Core.ps1 -LoadFunctionsOnly`. App ACs (16-21) go in
  `FolderPermissionManager-AppChanges.Tests.ps1`, in a new
  `Describe 'SQ-028: accounts of this computer on network folders'` that uses the existing
  `New-FakeTarget`, `Get-LastStatus`, `$script:Captured` and AST helpers.
- **Seams, all mocked in every test that reaches them:**
  - `Get-AppReparseInfo`, `Get-Win32PathName` and `Get-DriveLetterType`;
  - `Get-ThisComputerAccountDomain`, returning literal SIDs; it is never real outside the
    Integration test;
  - `ConvertTo-IdentitySid` and `ConvertTo-SidAccountName`, returning literals. No real
    `NTAccount.Translate` of `micha` or of `$env:COMPUTERNAME\...`;
  - `Set-Acl` as a recording backstop, `Save-AclBackup` and `Write-PermissionChangeLog` counted,
    and the throwing `Invoke-AclTool` stub.
  Expected values are literals (`PC01`, `S-1-5-21-1-2-3`), never `$env:COMPUTERNAME`, except the
  existing AC55 `.\name` rewrite tests, which already use it.
- **Existing tests that need a seam (no assertion weakened):** the SQ-018 AC55 tests build
  `IsLocal`/`Fixed` targets such as `D:\Data\HR`. After this change those targets reach
  `Test-PathOnThisComputer`, so that Describe's `BeforeEach` gains mocks of the reparse seam (no
  reparse point) and the drive seam (`Fixed`). `AC55_ReviewFix_DriveLetterTarget...` mocks the
  drive seam already and keeps its assertions. The three tests that assert "Type the server's
  name instead, for example FS01\name." are updated to the Q2 text. This is a wording change the
  owner decides, not a weaker test, and the run report must call it out. `AC55_OtherNamesAreUnchanged`
  stays as it is: `Resolve-AddIdentity` still returns those names unchanged, and the new refusal
  happens after the lookup.
- **Edge cases:** a target that is a file (the walk starts at the file); a drive root
  (`D:\`, no levels to walk); trailing and doubled `\`; a mixed list of local and network
  targets; well-known SIDs; a DC; a machine-SID read that fails; a link that appears between the

### Assumed by the squad
- **The check is in the core, with a late re-check.** Reason: P-006 and the risk profile ("Safety
  rules live in the core"; "the check runs again just before the call"). Evidence: the same
  pattern in SQ-022 (Plan refusal plus a re-check in Change).
- **The decision uses the resolved SID, not the name or the search order.** Reason: the risk
  profile says "acts on the same identifier it matched (the SID)". The search order only explains
  the bug. Evidence: `New-PermissionRule` today builds the rule from the name (`NTAccount`), which
  `Set-Acl` translates on this computer (core :1871-1882).
- **This PC cannot resolve another computer's local accounts.** The code already says so:
  `Get-RemoveIdentityProblem` (GUI :1681-1683, "local to the server (another computer's local
  group, which this computer cannot translate)"), and the README (lines 102-103, "Windows can't
  look up from here ... local to the server"). So `FS01\name` typed on a workstation would most
  likely fail the AC56 lookup. That is why Q2 recommends rewording.
- **Locality comes from the final path when a link is found, else from the walk.** Reason: the
  final path follows every link, including one inside a junction's destination. The walk names
  what was found, as "Overrides and refusals" requires. A failure on either side is not local
  (fail closed).
- **In the core, a UNC path is never local.** Reason: the app already turns this computer's own
  shares into their local folder (`Get-ChangeTarget` :4654-4683), so only the browser GUI could
  pass `\\PC01\x`. For it, refusing a local account is the fail-closed answer.
- **`IsLocal` no longer short-circuits `Test-AddTargetOnThisComputer`.** Reason: a share on this
  computer can hold a link to UNC too. The only behaviour change is that a this-computer share
  whose folder could not be found refuses `.\name`.
- **Well-known and BUILTIN SIDs pass on network folders.** Reason: `AccountDomainSid` is null for
  them, and they mean the same group on the server.
- **The machine-SID read fails closed only for domain-style SIDs on non-local targets.** Reason:
  this keeps BUILTIN/Everyone usable, and a domain account is not guessed safe when this
  computer's own SID is unknown.
- **The machine-SID read uses LSA P/Invoke behind one seam, cached for the session.** Reason: it
  matches the core's existing Add-Type wrappers. WMI `Win32_UserAccount` is slow on domain
  members. The risk profile requires a 5.1 compile check (AC22).
- **`ConvertTo-IdentitySid` moves to the core, under the same name.** Reason: the core now
  needs it, and keeping one definition avoids two lookups that could drift apart. The pool copies
  core functions.
- **The reverse name lookup runs inside `Find-PermissionAccount`'s timed runspace.** Reason: an
  unreachable domain must not freeze the dialog (SQ-018 AC56).
- **No new log columns.** The resolved `DOMAIN\name` goes in Detail, using the D-030 format as is.

destructive-operations applies in full.
