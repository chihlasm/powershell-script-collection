## Summary (plain English)
The Juniper console setup GUI is a small web server that a browser talks to; unit tests cannot
tell whether it actually starts. This item adds a "smoke test" start: the real script starts
its real web server on a private local port, asks itself for its own page and its status the
way a browser would, then stops and prints PASS or FAIL. It opens no browser, never looks for
or opens a COM port, sends nothing to any device, touches no network adapter, and writes no
file. The squad's smoke runner then checks this tool after every change, next to the Folder
Permission Manager.

## What users will be able to do
- Michael (or the build gate, once `smokeCommand` is set) runs
  `powershell.exe -NoProfile -ExecutionPolicy Bypass -File Tests\Invoke-SmokeTest.ps1` and, within
  a few seconds per tool, sees
  `[PASS] Invoke-JuniperConsoleSetup-GUI.ps1: the web page and status answered and the server stopped by itself (page N ms, status N ms)`,
  or a `[FAIL]` line saying what went wrong (the server could not start, the page or status did
  not answer within 30 seconds, the page came back without the setup screen, a request failed).
- A tech can run `.\Invoke-JuniperConsoleSetup-GUI.ps1 -SmokeTest` on a laptop to check a copy of
  the tool starts there, without a console cable, without a browser tab opening, and without
  anything being sent to a switch.
- Normal starts of the tool are unchanged (same port 8280 default, browser opens, `-ComPort`
  pre-connects).

## Approach
**What the smoke proves for a browser GUI.** There is no window to render off-screen: the user
interface is a page served by `System.Net.HttpListener` to the default browser. "Came up" means:
the script got past its top-level code, the listener started on `http://localhost:<port>/`, the
request loop served the real `$htmlContent` for `/` and a well-formed `/api/status` JSON (route
handler plus `ConvertTo-Json -Depth 5`), and the loop stopped by itself. Success is positive proof
(a `[PASS] <file name>:` line after both answers), never "no error", as in SQ-029. Search-DNSRecords
(SQ-034) is the other HttpListener GUI; whichever of SQ-034/SQ-036 is built first sets the
browser-GUI smoke pattern, and the other should match its helper names and wording.

**App changes (`Invoke-JuniperConsoleSetup-GUI.ps1`).**
- Param block: add `[switch]$SmokeTest`, `[switch]$LoadFunctionsOnly`. Help: `.PARAMETER` for
  both, an `.EXAMPLE`, a "Smoke test" paragraph and "Files written: none" in `.NOTES`, and a
  REFERENCES block (HttpListener prefixes and `Start`, `HttpListener.GetContextAsync`,
  `WebClient.DownloadStringTaskAsync` / `WebClient.Proxy`, `TcpListener` on `IPAddress.Loopback`
  port 0 and `LocalEndpoint`; verify each on Microsoft Learn and cite next to the code, root
  CLAUDE.md).
- First statement after `param()`: `$script:SmokeMode = $SmokeTest.IsPresent`, plus
  `$script:SmokeFailures` (`List[string]`), `$script:SmokeState` (PageOk, StatusOk, PageMs,
  StatusMs, PageError, StatusError, TimedOut) and `$script:SmokeDeadline = 30`. Nothing reads the
  machine before this line today (globals only), so there is no pre-flag path to except (SQ-029
  checklist gap 2).
- `Add-LogEntry`: in smoke mode prefix the console line (`  app log: [LEVEL] ...`) so the existing
  `[PASS] ... Web server started` line can never satisfy a runner looking for a PASS line.
- Serial chokepoint (checklist gap 1): `Get-AvailableComPorts`, `Connect-SerialPort` and
  `Send-SerialData` start with `if ($script:SmokeMode) { Add-SmokeFailure ...; return <safe value> }`.
  Move `New-Object System.IO.Ports.SerialPort` into a one-line seam `New-SerialPortObject` so tests
  never build a real port. Every device command (`Invoke-JunosCommand`, login, account, mgmt IP,
  firmware, config) goes through `Send-SerialData`, so this one guard covers every write to a
  device. `Read-SerialResponse` already returns '' without an open port.
- Route guard (defence in depth): `Invoke-ApiRoute` in smoke mode answers only `GET /api/status`
  and `GET /api/log`; everything else returns the refusal and a smoke failure.
- Move the server region into functions so it is testable: `New-AppListener -Prefix` (creates and
  starts the listener; seam), `Start-ConsoleSetupServer -Port -ComPort -BaudRate -OpenBrowser
  [-SmokeTest]` (banner, optional pre-connect, optional `Start-Process $baseUrl`, the request loop,
  the `finally` with `Disconnect-SerialPort` and listener close). Keep the loop body's text and
  responses as they are. Put `if ($LoadFunctionsOnly) { return }` after `$htmlContent` and before
  the main region.
- Smoke branch in the loop: before the loop, start the probe with a .NET async client
  (`WebClient` with `Proxy = $null`, `DownloadStringTaskAsync` for `/`, then `/api/status` once the
  page completed); in the existing `while (-not ...WaitOne(100))` wait, evaluate
  `Get-SmokeTickAction` and on `Close`/`TimedOut` stop the listener and leave the loop. The served
  page and status are checked with `Test-SmokePage` / `Test-SmokeStatus`. The request handler's
  catch and the outer `[FATAL]` catch add smoke failures.
- Main region: in smoke mode, refuse `-ComPort` (`[FAIL]`, `exit 1`) before anything else; pick
  the port (`-Port` if bound, else `Get-SmokePort`); call `Start-ConsoleSetupServer -SmokeTest
  -OpenBrowser:$false`; print `Get-SmokeVerdict` lines; `exit` with its ExitCode. Normal mode calls
  `Start-ConsoleSetupServer -Port $Port -ComPort $ComPort -BaudRate $BaudRate -OpenBrowser:(-not
  $NoBrowserOpen)`.
- File stays at `#Requires -Version 5.1` (it already uses `::new()`); keep it ASCII or save with
  BOM if any non-ASCII is added (`Tests/ScriptEncoding.Tests.ps1`).

**Runner changes (`Tests/Invoke-SmokeTest.ps1`).**
- Add `'Juniper-ConsoleSetup\Invoke-JuniperConsoleSetup-GUI.ps1'` to `$script:DefaultTargets`.
- Require `^\s*\[PASS\] <leaf name>:` instead of any `[PASS]` line (SQ-029 review follow-up;

- Change the runner's pass message from "the window opened and closed by itself" to "it started

## Decisions
### Confirmed by the owner
- D-061: each of the six other GUIs gets its own smoke-mode item; the runner takes a list.
- D-062: when `smokeCommand` is set, a guard rule blocks agents from running the runner by hand
  (configure step, not this item's code).
- 2026-11-11 plan: depends on SQ-031 (shared runner changes, see Revision notes). Squad call on the open question: server-only proof (recommended option); the item is kept (D-061 names all six GUIs).

### Assumed by the squad
- No browser in the smoke run; the page is checked as served text. Reason: launching a browser
  would write a profile under `LOCALAPPDATA`/`TEMP` and the page's start-up script calls
  `/api/ports`, which reads the serial-port registry key (backlog: no drive, network or directory
  reads; SQUAD.md "Agents do not read this machine"). Raised as Q1 in case Michael wants more.
- "Rendered" for this tool means page plus status answered over loopback. Reason: the backlog's
  "window rendered off-screen" has no equivalent for an HttpListener GUI; this is the nearest
  positive proof that the real startup path and request loop work.
- Smoke picks a free loopback port unless `-Port` is passed. Reason: a normal instance on 8280
  must neither make the smoke fail nor be disturbed (same reasoning as SQ-029 skipping the mutex).
- Opening a localhost listener is allowed in smoke mode; it is the startup path itself, bound to
  `localhost` only. Assumed to need no elevation for a `http://localhost:<port>/` prefix (the tool
  already runs non-elevated); the builder verifies this on Microsoft Learn (HttpListener / netsh
  http urlacl docs) and cites it. If it turns out to need elevation, the smoke fails with a clear
  `[FAIL]`, it never elevates.
- `-ComPort` with `-SmokeTest` is refused, not ignored. Reason: SQ-029 refused `-LogFolder` /
  `-DriveMap` the same way; a pre-connect would open a real port.
- Guard at the serial layer (`Get-AvailableComPorts`, `Connect-SerialPort`, `Send-SerialData`)
  and also at the route table. Reason: SQ-029 destructive-operations checklist gap 1 (enforce at
  the chokepoint, not only the UI wrapper).
- Add `-LoadFunctionsOnly` and move the server into functions. Reason: SQUAD.md "logic separated
  from collection and UI" and the testing pattern; the script has neither today.
- Runner hardening (target's own PASS line; target declares `-SmokeTest`) is done here. Reason:
  this app prints `[PASS]` log lines, so without the first change a broken smoke could pass; the
  second is SQ-029 checklist gap 3. First sibling to land owns it.
- Integration tests redirect `LOCALAPPDATA`/`TEMP`/`TMP` for the child. Reason: SQ-029 checklist
  gap 4.
- REWRITE: no. The tool's behaviour is unchanged; only its top-level server code moves into
  functions.
- Size M, no split: one switch, one guard set, one runner line; no user-facing slice smaller than
  "the smoke runs for this tool".

## Risk and safety notes
- system-configuration applies (path `Juniper-ConsoleSetup/**`): the tool sends configuration
  commands to network devices (root password, a super-user account, management IP and default
  route, firmware install with reboot). This item adds no change path; the smoke mode is a
  "nothing changes" mode, enforced where every device command passes (`Send-SerialData`) and where
  ports are opened or listed, and proven by AC5-AC7. It never enumerates COM ports (the
  `HARDWARE\DEVICEMAP\SERIALCOMM` registry read is skipped), never opens a serial port, never runs
  `netsh` or touches an adapter (AC6), never opens a browser (AC3).
- Normal start must stay byte-for-byte equivalent in behaviour (AC16); the request loop's body is
  moved, not rewritten. A reviewer should diff the loop body before/after.
- personal-data keyword `password` appears in the touched file (device passwords pass through
  routes); no handling changes, and smoke mode refuses those routes.
- Tests never open a serial port, never start a browser, and never start the app outside the
  Integration tag. Agents do not run the runner or Integration tests during runs (SQUAD.md, D-062).
