# SQ-039 · M365 user check: a cloud block on a synced account (AD enabled, no marker) is framed as a sync fault

- status: ready
- feature: M365 user check
- size: S
- risk: medium
- touches: `M365-UserQuickCheck/M365UserCheck.Core.ps1` (`Get-M365OnPremisesAssessment`, the
  AD-enabled/no-marker branch at `:719-722`; two step texts; one REFERENCES entry),
  `M365-UserQuickCheck/README.md` (rows "Sign-in is blocked" `:98` and "AD and Microsoft 365

  `M365-UserQuickCheck/Tests/Get-M365UserQuickCheck.Tests.ps1`

## Summary (plain English)
When a synced user is blocked in Microsoft 365 while their AD account is enabled and carries no
block marker, the M365 user check today calls it a sync disagreement: "wait for the next sync,
then check Entra Connect for a sync rule or an export error". That is exactly what an account
blocked in Microsoft 365 during a security incident looks like, and a tech who "fixes" the sync
could undo the block. After this change the check says the block may be deliberate and tells the
tech to check with the senior engineer before any sync troubleshooting. For a user ID Protection
flags, it says only "escalate to the security lead". When ID Protection could not be checked, it
adds the D-059 reminder.

## What users will be able to do
- A tier 1 tech checks a synced user who is blocked in Microsoft 365 while AD has the account
  enabled and there is no block marker. The answer is still NO. Both "Why not" steps ("Sign-in is
  blocked" and "AD and Microsoft 365 disagree"), and the ticket note's Next step, now start with
  "Check with the senior engineer". They say the account may have been blocked in Microsoft 365
  on purpose, for example during a security incident. The "wait for the next sync / check Entra
  Connect" advice is still there, but only after that, and only for when the senior engineer
  confirms it should not be blocked.
- If ID Protection flags the same user, both steps are the security-lead step (SQ-027). No
  sync-troubleshooting advice reaches "Why not" or the ticket note for that user.
- If ID Protection could not be checked (no Entra ID P2, a role that cannot read it, or the read
  failed), both steps end with the D-059 sentence: "ID Protection could not be checked: if this
  account was blocked during a security incident, escalate to the security lead instead."
- The README's "AD and Microsoft 365 disagree" row explains the same, and the "Sign-in is blocked"
  row names this third kind of block.
- Every other blocked/disabled path shows exactly the text it shows today.

## Approach
- **Verified by the lead at planning (2026-11-11, Microsoft Learn MCP):**
  `https://learn.microsoft.com/entra/identity/users/users-revoke-access` ("Revoke access for a
  user in the hybrid environment") tells admins to disable the user in AD *and* to disable the
  user in Microsoft Entra ID (`Update-MgUser -AccountEnabled:$false`) plus revoke sessions. A
  cloud-side block on a synced user is therefore a documented incident-response step, which is
  the premise of this item. Cite this page for AC9. Whether the next sync overwrites the cloud
  block is not stated there; the wording stays neutral on it, as already specified.
- **`M365UserCheck.Core.ps1`, `Get-M365OnPremisesAssessment`, branch `$adEnabled -eq $true` (`:719-722`).**
  It already receives `-IsRisky` and `-RiskNotChecked`.
  - AdEnabledMismatch `Action`:
    - risky: `$script:M365RiskyUserStep`;
    - otherwise: `Join-M365RiskNotCheckedSentence -RiskNotChecked $RiskNotChecked -Step <text>`,
      where the text is:
      `Check with the senior engineer first: the account may have been blocked in Microsoft 365 on purpose, for example during a security incident. Only if they confirm it should not be blocked: <$lastSyncText> If the AD account was enabled after that, wait for the next sync (normally <$script:M365SyncIntervalText>). If it stays blocked, check the Entra Connect server for a sync rule or an export error for this account.`
  - `$blockedAction` (SignInBlocked, non-risky; the caller already overrides it for a risky
    user): `Join-M365RiskNotCheckedSentence -RiskNotChecked $RiskNotChecked -Step <text>` with
    `Check with the senior engineer before undoing this block or changing anything in sync: on-premises AD has the account enabled and it was not blocked on purpose with M365-SyncedUserFixes, so it may have been blocked in Microsoft 365 itself, for example during a security incident. See "AD and Microsoft 365 disagree".`
  - Put the fixed SignInBlocked text in a `$script:` constant next to
    `$script:M365RiskNotCheckedSentence`, matching the existing fixed-step constants. The
    AdEnabledMismatch text stays inline because it embeds `$lastSyncText`.
  - The wording above is the squad's proposal. The ACs pin its properties, not its exact text,
    except where an existing test pins a phrase. ASCII only.
  - The 50057 consistency comes for free: `Get-M365UserAssessment` already gives a 50057 failure
    the SignInBlocked action when SignInBlocked fired (`:985-986`). AC4 pins that.
- **Microsoft facts: verify and cite (root `CLAUDE.md`).** The new wording rests on one
  documented fact: an admin can block sign-in for a synchronized user in Microsoft Entra ID
  (`accountEnabled = false`) independently of the on-premises account, and Microsoft's
  incident guidance does this for hybrid users. The planner could not reach Microsoft Learn in
  this session, so the builder verifies it and cites what they read. Candidate pages:
  - https://learn.microsoft.com/entra/identity/users/users-revoke-access (revoke access, hybrid
    environment)
  - https://learn.microsoft.com/entra/identity/hybrid/connect/how-to-connect-sync-technical-concepts
    or the attribute-flow pages, for how Entra Connect treats a cloud-side `accountEnabled`
    change.

  The wording deliberately does not say whether the next sync overwrites a cloud-side block
  (it says "may have been blocked on purpose" and "before changing anything in sync"), so the
  outcome of that check does not change the ACs. If the docs say a cloud-side block on a synced
  user is impossible, stop and flag it: the premise of this item would be wrong. This is
  unlikely, since the observed state (cloud blocked, AD enabled) proves something set it.
- **README:**
  - Row `:121` "AD and Microsoft 365 disagree": add the "may have been blocked on purpose
    (security incident)" meaning. The "What to do" becomes: the SQ-027 lead sentence, then
    "Check with the senior engineer first...", then the existing sync advice, gated on their

  - Row `:98` "Sign-in is blocked": in the synced part, add the third kind of block (blocked in

- **Version floor and encoding:** no new syntax, ASCII only (`Tests/PSVersionFloor.Tests.ps1`,

## Decisions
### Confirmed by the owner
- D-017: a step that undoes a deliberate block says Escalate plus the reason.
- D-050: deliberate blocks (marker, risky user) say Escalate; only a plain disabled account gets
  the manager path.
- D-059: the "ID Protection could not be checked" sentence (extended here; see Assumed).
- D-002/D-014: the tool stays read-only; the AD stage runs when a DC answers.
- 2026-11-11 plan: no owner questions. Build before SQ-040 (same test file and README).

### Assumed by the squad
- **Escalate to the senior engineer, not the security lead, when ID Protection was checked and
  does not flag the user.** This matches the other deliberate-block steps (marker `:716`, no-AD
  `:878`) and D-017's "Escalate to a senior engineer". The security lead is reserved for a user
  ID Protection flags (D-050, SQ-027), or via the D-059 sentence when risk is unknown. Michael
  can change the target with a one-string edit.
- **The D-059 sentence is appended to these two escalating steps**, although SQ-027 kept it off
  the marker and no-AD steps. The reason: a cloud-side block with AD enabled and no marker is
  the incident-response signature, so "blocked during a security incident" is the likeliest
  reading. The marker step already names the engineer who blocked it. This is the backlog
  item's own proposal.
- **The sync-troubleshooting advice stays, gated behind the escalation** ("Only if they confirm
  it should not be blocked"). It is still the right path for a genuine stale or broken sync.
  The backlog says "escalate before any sync troubleshooting", not "remove it".
- **The Message and Level of AdEnabledMismatch are unchanged.** The "may be deliberate" framing
  lives in the Actions, which reach "Why not" and the note's Next step. This keeps `AC23_*` and
  the verdict logic untouched.
- **NotAllowed counts as "could not be checked"** (SQ-027 build decision, `$script:M365RiskNotCheckedStates`).
- **Two non-identical escalation lines in the note for a non-risky user** (SignInBlocked and
  AdEnabledMismatch) are acceptable. They agree, and the first one points to the second.
  Merging them into one string would change the existing SignInBlocked/BlockedAction contract
  for no safety gain.
