- status: ready
- size: M
- risk: medium
- builds after: SQ-007 (extends its entry script and `MailboxCheck.Core.ps1`; SQ-001 and SQ-002
  come before SQ-007)
- touches: `M365-UserQuickCheck/Get-M365MailboxCheck.ps1`, `M365-UserQuickCheck/MailboxCheck.Core.ps1`,
  `M365-UserQuickCheck/Tests/` (new test file), `M365-UserQuickCheck/README.md`

## Summary (plain English)
The mailbox check (SQ-007) shows what is set on a mailbox now. This adds *when* it changed. It
looks in the Microsoft 365 audit log for the last 14 days (changeable with `-RecentDays`) for
inbox rules that were created or changed, forwarding that was switched on, and people given
access to the mailbox. Each change is shown with when it happened and who did it. A recent change
counts as a takeover sign, so the report opens with "do NOT reset yet. Escalate." If the tech's
account cannot read the audit log, or the client has auditing turned off, the report says
"Recent changes: could not check" and the verdict becomes "partly checked", never an all-clear.

## What users will be able to do
- Run the same command as SQ-007, `.\Get-M365MailboxCheck.ps1 -Identity accounts@contoso.com`.
  The recent-changes lookup is on by default for the last 14 days. `-RecentDays 30` looks
  further back (1 to 90 days). `-NoRecentChanges` skips it when the audit search is slow, but
  then the report says "partly checked".
- Read a new **Recent changes (last N days)** section, newest first. Each row has the date and
  time, what changed in plain English, who did it, and where from (client IP and app, if the
  audit record has them). Examples:
  - "2026-10-15 09:12 - Inbox rule 'xx' created by jdoe@contoso.com (Outlook on the web). This
    rule no longer exists."
  - "2026-10-14 17:40 - Forwarding turned on to an address at gmail.com by admin@contoso.com."
  - "2026-10-13 11:02 - Full Access given to helpdesk@contoso.com by admin@contoso.com."
- When a recent change is found, the SQ-007 verdict opens with the takeover line. The change is
  then listed as a sign, for example "Inbox rule 'xx' was created 2 days ago by the mailbox's own
  account".
- When nothing changed, the section reads `No inbox rules, forwarding or mailbox access were
  added or changed in the last 14 days.` It is followed by `Changes from the last few hours may
  not be in the audit log yet.`
- When the lookup could not run, the section and the verdict's could-not-check list name the
  reason and the fix:
  - The account is missing the audit role: "your account needs the View-Only Audit Logs role in
    Exchange Online".
  - The tenant has auditing turned off: "audit logging is turned off in this tenant".
  - Mailbox auditing is off or bypassed: "rule changes made in Outlook are not being recorded
    for this mailbox".
  - The search returned more results than it can page through: "results were cut off".
  - The tech used `-NoRecentChanges`: "skipped".
- The ticket note (SQ-001) lists recent-change signs as their kind, the date, the rule name, and
  whether the change was made by the mailbox's own account or by another account. The full
  actor, IP and app stay in the local report.
- Nothing is changed. The tool only reads the audit log and audit settings, and never turns
  auditing on.

## Acceptance criteria
Each maps to one Pester test named `AC<n>_...` in
`M365-UserQuickCheck/Tests/MailboxCheck.RecentChanges.Tests.ps1`. All Exchange cmdlets are stubbed
and mocked. "Now" is injected (core functions take a `-Now` parameter) so the tests do not depend
on the clock.

1. AC1: Given the entry script, when its parameters are read, then `-RecentDays` defaults to 14
   and is `[ValidateRange(1,90)]`. The test checks that 0 and 91 are rejected by parameter
   validation.
2. AC2: Given `-RecentDays 14` and Now = 2026-10-17 12:00, when the audit search runs, then
   `Search-UnifiedAuditLog` is called with `-StartDate` 2026-10-03 12:00, `-EndDate` 2026-10-17
   12:00, `-Operations` containing exactly `New-InboxRule`, `Set-InboxRule`, `UpdateInboxRules`,
   `Add-MailboxPermission`, `Add-RecipientPermission` and `Set-Mailbox`, `-SessionCommand
   ReturnLargeSet`, `-ResultSize 5000`, and the same `-SessionId` on every page. Paging stops
   when a page is empty or the last `ResultIndex` reaches `ResultCount`.
3. AC3: Given a mailbox with alias `jdoe`, UPN `jdoe@contoso.com`, a secondary proxy
   `smtp:j.doe@contoso.com`, display name `Jane Doe`, ExchangeGuid and
   ExternalDirectoryObjectId, when audit records are matched to it, then records are kept whose
   target (`ObjectId`, or the `Identity`/`Mailbox` parameter, or the part before `\` in
   `jdoe\RuleName`, or `MailboxOwnerUPN`/`MailboxGuid` for mailbox-audit records) is any of
   those identifiers, compared without regard to case. Records for `asmith@contoso.com` are
   dropped. One test, with a case for each identifier form.
4. AC4: Given a matched `New-InboxRule` record for rule `xx` that is not in the current rule
   list, when signs are evaluated, then a `RecentRuleChange` sign is raised. The sign carries the
   rule name, the time, and the actor (`UserId`), and is marked "rule no longer exists". Given a
   matched `Set-InboxRule` record for an existing rule, a `RecentRuleChange` sign is raised
   without that mark.
5. AC5: Given a matched `UpdateInboxRules` mailbox-audit record, when signs are evaluated, then
   a `RecentRuleChange` sign is raised with the time, the actor, and `ClientIP` and client app in
   the report row.
6. AC6: Given a matched `Add-MailboxPermission` record (`AccessRights` FullAccess, `User`
   helpdesk@contoso.com) and a matched `Add-RecipientPermission` record (`AccessRights` SendAs),
   when signs are evaluated, then two `RecentDelegateChange` signs are raised, each naming the
   delegate and the right.
7. AC7: Given matched `Set-Mailbox` records, when signs are evaluated, then:
   - a record setting `ForwardingSmtpAddress` or `ForwardingAddress` to a non-empty value raises

   - a record setting `GrantSendOnBehalfTo` raises `RecentDelegateChange`;
   - a record that clears forwarding is listed as a fact ("Forwarding turned off") with no sign;
   - a record that changes only other parameters (for example `ProhibitSendQuota`) is neither
     listed nor a sign.

8. AC8: Given `Search-UnifiedAuditLog` is not available in the session (`Get-Command` finds

   Audit Logs role, the verdict starts with `PARTLY CHECKED`, and the exit code is 2 (if no other

## Out of scope
- Any change to audit settings. The tool never turns auditing on and never runs
  `Set-AdminAuditLogConfig` or `Enable-OrganizationCustomization`. It only says the setting is
  off and names who can fix it (README).
- Operations beyond the owner's list. Out: `Remove-InboxRule`, `Remove-MailboxPermission`,
  `Add-MailboxFolderPermission` / `Set-MailboxFolderPermission`, `MailItemsAccessed`, sign-in
  events, MFA and OAuth changes (CIPP BEC covers these).
- Lookback beyond 90 days, Purview audit search jobs, and the Graph audit log query API.
- Takeover scoring (D-003), remediation, message content.
- Changes to SQ-007's existing signs, wording, exit codes or trace.

## Approach
- **Where:** `MailboxCheck.Core.ps1` gets these pure functions:
  - `Get-MailboxIdentifierSet`: builds the identifier set from the `Get-EXOMailbox` object
    SQ-007 already fetches.
  - `ConvertFrom-AuditRecord`: parses the `AuditData` JSON and flattens `Parameters` (Name/Value)
    into a hashtable.
  - `Test-AuditRecordTargetsMailbox`
  - `Get-RecentChangeSigns`: returns facts, signs and could-not-check entries.
  - Additions to `ConvertTo-MailboxCheckHtml` and `Get-MailboxCheckNote`.

  The entry script gets the collection step `Get-RecentMailboxChanges` and the
  `-RecentDays`/`-NoRecentChanges` parameters. "Recent changes" is registered as a
  sign-producing section in SQ-007's assessment. SQ-007's rule then applies as it stands:
  the clean wording appears only when every sign-producing section was checked.
- **Collection order (one try/catch, per SQ-007's section pattern):**
  1. `Get-Command Search-UnifiedAuditLog`. If it is missing, record the role reason (AC8).
  2. `Get-AdminAuditLogConfig` → `UnifiedAuditLogIngestionEnabled` (AC9).
  3. `Get-OrganizationConfig` (already fetched by SQ-007) → `AuditDisabled`, and
     `Get-MailboxAuditBypassAssociation -Identity` → `AuditBypassEnabled` (AC10; this step
     fails on its own without failing the section).
  4. Paged `Search-UnifiedAuditLog` (AC2, AC12, AC15).

  Console shows `[INFO] Searching the audit log for the last N days (this can take a
  minute)...` before the search.
- **Matching runs client-side** against the identifier set. The search is filtered on the
  server by date and operations only. Reason: in admin-cmdlet records, `ObjectId` is whatever
  `-Identity` the admin typed (alias, display name, UPN, GUID). An exact `-ObjectIds` filter
  would miss changes, and a missed change is a false all-clear.
- **Times** are stored in UTC as returned (`CreationDate`/`CreationTime`). They are shown in the
  workstation's local time as `yyyy-MM-dd HH:mm`, with the time zone named in the section header.
- **Own account vs another:** "own account" means the actor `UserId` equals the mailbox UPN or
  one of its SMTP addresses. Everything else is "another account".
- **Verify on Microsoft Learn before coding, and cite in code and `.NOTES` REFERENCES:**
  - `Search-UnifiedAuditLog`: parameters, `ResultSize` max 5000, `ReturnLargeSet` 50,000 cap and
    paging semantics, `ResultIndex`/`ResultCount`, required role (View-Only Audit Logs or Audit
    Logs), any deprecation notice.
  - The audit log activities page: operation names, including `UpdateInboxRules` being a
    mailbox-audit owner/delegate/admin default action.
  - Audit record schema: `ObjectId`, `UserId`, `ClientIP`, `Parameters`, `MailboxOwnerUPN`,
    `MailboxGuid`.
  - `Get-AdminAuditLogConfig`: `UnifiedAuditLogIngestionEnabled` is only accurate when read from
    Exchange Online PowerShell.
  - Mailbox auditing on by default: organization `AuditDisabled`, and that per-mailbox
    `AuditEnabled` is not reliable while the default is on.
  - `Get-MailboxAuditBypassAssociation`.
  - Audit (Standard) retention, to justify the 90-day cap.
  - Search latency (how long before events appear), for the latency line.

  If Learn contradicts a value here (role name, caps, field names), use Learn's value and note
  it in Revision notes. The behaviour in the ACs stays the same.
- **Docs:** add to the folder `README.md`: the audit role needed, what "Recent changes: could
  not check" means and who can turn auditing on, `-RecentDays`, `-NoRecentChanges`, and that
  the search can take a minute or more on large tenants. No ServiceDesk-Toolkit or root README
  change: the tool's row already exists from SQ-007.
- **Floor:** unchanged, `#Requires -Version 5.1`. Keep UTF-8 with BOM if any non-ASCII is added.

### Assumed by the squad
- **`-RecentDays` range 1-90.** Reason: Audit (Standard) keeps at least 90 days (to be
  re-cited), so a wider window would look complete when it is not.
- **Send on Behalf via `Set-Mailbox -GrantSendOnBehalfTo` counts as a delegate change.**
  Reason: SQ-007 lists Send on Behalf as a delegate (its AC5), and SQ-007's draft AC26 already
  included it.
- **Clearing forwarding is a fact, not a sign.** Reason: the owner's sign is about rules,
  forwarding and delegates being *added*. Turning forwarding off is still shown, so a tech
  can see an attacker's cleanup.
- **A rule created in the window that no longer exists is still a sign, marked "no longer
  exists".** Reason: a rule created and then deleted is a known way to hide a takeover, and the
  owner's sign is "recently added".
- **Client-side matching, server-side filter by date and operations only.** Reason: avoids
  missed changes from varying `-Identity` forms (see Approach). Cost: slower search on large
  tenants. That cost is accepted, with the progress line and `-NoRecentChanges`.
- **Cut-off results count as could-not-check.** Reason: matches SQ-007's structural rule that a
  partial look is never an all-clear (SQ-007 AC16-AC18).
- **`-NoRecentChanges` makes the run "partly checked".** Reason: same rule; mirrors SQ-007's
  `-NoTrace` switch name.
- **Mailbox-audit-off is a partial could-not-check ("Rule changes made in Outlook"), not a
  failure of the whole section.** Reason: admin-cmdlet records (New-InboxRule from Outlook on the
  web or PowerShell, permission and forwarding changes) still come from the unified log.
- **The ticket note shows "own account" or "another account", not the actor's address or IP.**
  Reason: consistent with SQ-007's paste-safe note (no full addresses) and the personal-data
  profile. The full detail stays in the local report.
- **Test file separate from SQ-007's.** Reason: SQ-007's tests stay untouched, the same reason
  SQ-007 used for its own core.
- **Who checks the role against a real tenant follows the owner's answer to SQ-007 Q3**, which
  this item inherits. It does not ask again.
- **SQ-007's AC26 (conditional on Q1 = A) moves here and should be removed from SQ-007** when
  SQ-007 is revised.

## Risk and safety notes
- **personal-data:** audit records hold actor UPNs, client IPs, user agents and rule
  parameters, which can include client keywords. Handled by:
  - the redacted ticket note (AC17);
  - HTML encoding (AC18);
  - output under the SQ-007 gitignored pattern;
  - synthetic fixtures with documentation-range IPs;
  - no new connection or scope (same Exchange session, disconnected per SQ-007 AC22).
- **Read-only under a write-capable account (D-002):** the code never changes audit settings
  (AC19). The README names who can turn auditing on, and the tool does not do it.
- **False all-clear** is the costliest failure. Missing role, auditing off, mailbox-audit
  bypass, cut-off results, skip and errors all produce "partly checked" (AC8-AC12, AC14). The
  latency line warns that changes from the last few hours may not show yet.
- **False alarms:** see Q1. Under the owner's sign as written, any rule or delegate change in
  the window triggers "Escalate".
- destructive-operations, system-configuration: not applicable.
