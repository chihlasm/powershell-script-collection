## Summary (plain English)
Today a tech can give `BUILTIN\Users` Full Control on `C:\Users`, on a folder in `C:\Windows` or
`C:\Program Files`, or on System Volume Information with one click, because "only adds access" never
asks (D-048). With this item the tool knows these places. The ones where no helpdesk task needs new
access (the Windows folder, the Program Files and ProgramData folders themselves, the Users folder
itself, System Volume Information, the Recycle Bin, SYSVOL/NETLOGON and the admin shares) are refused
with a plain reason. Inside Program Files and ProgramData, where techs do sometimes fix an old app,
the change gets the red "are you sure" step that says why the place matters. The check lives in the
shared core, so no front end can skip it.

## What users will be able to do
- **Add Permission** (folder or selected files) and **Change Permission** on an ordinary folder work
  exactly as today: a plain Allow add, or a change that only gives more access, stays one click.
- On a refused place, the Add or Change dialog does not open. The status bar says what the place is
  and that nothing was changed, for example: "Permissions can't be added or changed on
  C:\Windows\Temp: it is in the Windows folder, which Windows needs to run. Choose the folder that
  needs the access instead. Nothing was changed." The same applies when the typed path only leads
  there (a mapped drive, `\\fs01\C$\Windows`, a junction, a short name).
- Inside Program Files, Program Files (x86) or ProgramData, and on the root of a drive, the red
  confirm opens before the change, also for a plain Allow add or a raised Allow. It names the real
  location and says why: "C:\Program Files (x86)\Legacy\Data is inside Program Files (x86), where
  installed programs live. Anyone you give write access here can change files that programs, other
  users and Windows itself run." The button says what it does ("Add permission", "Change
  Permission"), is red and is never the default.
- In the browser version (to be removed), adds on these places now fail with the core's reason.
- `-WhatIf` shows the refusals too.

## Approach
- **Core (`FolderPermissions.Core.ps1`, 3.0 floor: no `::new()`, `.Where()`, classes).** Next to
  `Get-CopyTargetRefusal`:
  - Marker constants for the kinds (`SystemShare`, `WindowsFolder`, `ProgramFolderRoot`, `ProfilesRoot`,
    `VolumeSystemFolder`, `ProgramFolder`, `DriveRoot`), per the risk profile's "shared marker constant".
  - `Get-PermissionTargetGuard -Path` (text only): `ConvertTo-ComparablePath` first; an empty result
    fails closed (Refuse, "could not tell"). Share names as `Get-CopyTargetRefusal` reads them;
    `%SystemRoot%` at or below -> Refuse; `%ProgramFiles%`, `%ProgramW6432%`, `%ProgramFiles(x86)%`,
    `%ProgramData%` equal -> Refuse, below -> Confirm; the same four names under `\\server\X$\`; the
    high-impact roots via `Get-HighImpactRootRefusal` (Refuse, its own text not reused: it speaks of
    ownership); `Get-TargetRootKind` `DriveRoot`/`AdminShareRoot` -> Confirm. Do not parse the texts of
    `Get-TreeOwnershipRefusal`; reuse its variable list and comparison rules (whole segments,
    case-insensitive, WOW64 note).
  - `Get-PermissionTargetResolvedGuard -Path`: the `Get-CopyTargetResolvedRefusal` pattern (final and
    long path, each read in try/catch, fail closed), returning the stricter of the given and resolved
    results. For files, the builder checks that `Get-Win32PathName` opens a file (CreateFile with
    `FILE_FLAG_BACKUP_SEMANTICS` does); if not, resolve the parent folder and append the leaf.
  - `Add-FolderPermission` and `Set-FolderPermissionEntry` gain `[switch]$ProtectedFolderConfirmed`.
    In the `-Plan` block (SQ-028 adds one to Add; Change has one): text guard, then resolved guard;
    Refuse, or Confirm without the switch -> `Result 'Failed'`, ErrorText ending "Nothing was
    changed.". In `-Change`, re-run the resolved guard just before `Set-Acl` and throw on the same
    condition (the `Copy-FolderPermission` late re-check pattern; for Change, before the existing
    `Set-Acl` try).
- **App (`FolderPermissionManager-GUI.ps1`, 5.1).**
  - `Get-ChangeTarget` and `Resolve-ChangeTargetSet` gain `-GuardPermission` (next to
    `-RefuseProtected`), on the resolved path; Refuse -> refused target; Confirm -> `New-ChangeTarget`
    carries `Guard` (`Level`, `Kind`, `Text`). `$script:ChangeTargetWork` and `Start-ChangeLookup` pass
    it as a new trailing `[bool]` (the `$RefuseProtected` precedent).
  - `Open-AddPermission` and the Change entry point (`Open-ChangePermission`) request it. Remove and
    take ownership do not.
  - `Get-ConfirmSpec` gains `-ProtectedNote` (text), added to the AddPermission and ChangePermission
    bodies and making `IsDestructive` true. `Invoke-AddPermission` and `Invoke-ChangePermission` add
    "any target has a Confirm guard" to their existing confirm condition, and pass
    `[bool]$guardConfirmed` (set only on that path) as the work's last argument.
- **Docs.** README sections "Add a permission" and "Change a permission"; help as AC18. Record the
  owner's answer as a new D-### amending D-048 ("changes that only add access stay one click" except on
  the places in this spec) and D-044 for Allow adds.
- **Plans.** No document under `docs/plans/` covers this; the SQ-022 and SQ-025 specs are the patterns.

### Assumed by the squad
- **Copy is already guarded.** Evidence: `Copy-FolderPermission` Plan and late re-check call
  `Get-CopyTargetRefusal` / `Get-CopyTargetResolvedRefusal`, which refuse every AC1 Refuse and Confirm
  row and drive roots (`FolderPermissions.Core.ps1`, SQ-022 AC2). Nothing to add here.
- **The guard is by place, not by direction or inheritance.** It applies to Add (Allow and Deny) and to
  every Change, inheritable or "This folder only", folders and files. Reason: write access to a file
  in `C:\Windows\System32` or a folder in Program Files lets the account change what Windows and other
  users run, inheritance or not; and a Deny on `C:\Windows` breaks Windows. Matches D-044 for Copy (Allow
  and Deny alike).
- **Core acknowledgement switch, not core prompts.** The core cannot ask (SQ-022 "D-044 confirms stay in
  the WPF app"); a caller switch passed only after the red confirm is the D-052 pattern.
- **The switch passes only the Confirm level.** Refuse places, "could not tell" and every other guard
  (SQ-028 account check, non-canonical ACL, DFS) ignore it: risk profile "one switch does not turn off
  unrelated guards".
- **Fail closed when the real location cannot be told**, as for Copy (SQ-022): risk profile "a guard
  that cannot resolve the path fails closed". Listed under what tests cannot see for the NAS case.
- **Profile folders below the Users folder stay ordinary** (`C:\Users\bob`): giving someone access to a
  colleague's profile folder is a normal ticket, and `Get-HighImpactRootRefusal` already allows it.
- **Drive roots keep the confirm, now core-acknowledged**; ordinary share roots keep the app-only confirm
  (D-044 not relitigated; a share root is the usual place to grant access).
- **Texts are squad-drafted** (refusal, confirm line, missing-acknowledgement text). Michael adjusts at
  review.
- **Build order:** after SQ-028 (same `Add-FolderPermission` Plan block and `Invoke-AddPermission`
  lines). SQ-023 and SQ-026 edit other functions; no dependency unless Q3 = B.

## Owner questions
- **Q1. How should Add and Change be guarded on high-impact folders? (revisits D-048)**
  - **A (recommended): refuse the places no helpdesk task needs, red confirm for the rest, enforced in
    the core.** The core refuses Confirm places unless the caller passes `-ProtectedFolderConfirmed`,
    which the WPF app passes only after the red confirm (the D-052 `-AllowDeny` pattern). For a tech: a
    plain add on an ordinary folder is still one click; inside Program Files or ProgramData they get one
    extra red click that says why; `C:\Windows`, `C:\Users` and the like are simply refused. Which places
    are which is Q2.
  - **B: refuse every place Copy refuses.** Simplest and consistent with Copy, but a tech fixing an old
    app ("users need Modify on `C:\Program Files (x86)\Sage\Data`") is refused and goes to Explorer or
    icacls, with no backup or change log.
  - **C: confirm only when the account is a broad one** (Everyone, Authenticated Users, BUILTIN\Users,
    Domain Users, Guests, Anonymous); a named user or group stays one click everywhere. Least friction,
    but one named account with write on `C:\Windows\System32` is still a privilege-escalation path, and
    a custom "All Staff" group is not caught.
  - **D: leave D-048 as it is and drop SQ-037.** Adds stay one click everywhere; the backup and log are
    the only safety net. The destructive-operations checklist gap stays open.
- **Q2. (only if Q1 = A) Which places are refused outright, and which get the red confirm?**
  - **A (recommended):** Refused: SYSVOL, NETLOGON, ADMIN$, IPC$, PRINT$; the Windows folder and
    everything in it; the Program Files, Program Files (x86) and ProgramData folders themselves; the
    Users folder itself; System Volume Information; $Recycle.Bin. Red confirm: anything inside Program
    Files, Program Files (x86) or ProgramData; the root of a drive (already confirmed in the window,
    D-044, now also checked in the core). A tech can still fix a legacy app's folder, never "Users Full
    Control on C:\Users".
  - **B: no refusals except the system shares;** everything else in the list gets the red confirm. Fewer
    dead ends, but "Users Full Control on C:\Windows" becomes two clicks.
  - **C: refuse everything in the list including Program Files/ProgramData subfolders** (as Copy does).
    Same trade-off as Q1 = B for legacy-app fixes.
- **Q3. A share whose folder on the server is one of these places** (`\\fs01\Apps` is `C:\Program Files`
  on the server): should Add and Change check it too?
  - **A (recommended): yes, as a separate follow-up after SQ-026**, reusing SQ-026's share-to-server-folder
    check. SQ-037 stays M and does not wait for SQ-026.
  - **B: inside SQ-037.** Depends on SQ-026, grows to L (core guard + app + remote mapping); would then be
    split by action (Add first, Change second), each usable on its own.
  - **C: no.** Typed `\\fs01\C$\...` paths are caught; a renamed share pointing into Windows is not.
