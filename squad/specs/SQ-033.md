# SQ-033 · Smoke-test start mode for M365-SyncedUserFixes

- status: ready
- feature: Squad tooling
- size: M
- risk: medium
- touches: `M365-SyncedUserFixes/Start-M365SyncedUserFixes.ps1` (new `-SmokeTest` switch, startup
  seams, smoke branches), `M365-SyncedUserFixes/SyncedUserFixes.Core.ps1` (one new pure probe
  function), `Tests/Invoke-SmokeTest.ps1` (one target line + a "does the target declare
  -SmokeTest?" check), `Tests/Invoke-SmokeTest.Tests.ps1` (fixture/count updates only),
  `M365-SyncedUserFixes/README.md`, new suite
  `M365-SyncedUserFixes/Tests/Start-M365SyncedUserFixes-SmokeTest.Tests.ps1`

## Summary (plain English)
The M365 Synced User Fixes window gets the same "smoke test" start the Folder Permission Manager
got in SQ-029: the real app starts, builds its real window off-screen, proves the window drew
itself and that its background workers can load the tool's logic, then closes and prints PASS or
FAIL. In this mode it does not load the ActiveDirectory module, does not contact a domain
controller or the Entra Connect server, writes no change log or settings file, and shows no
message box. The smoke runner (`Tests\Invoke-SmokeTest.ps1`) then checks this tool as well as
FolderPermissionManager, and it now refuses to start any tool that does not declare a smoke mode.

## What users will be able to do
- Michael (or the squad gate, once `smokeCommand` is set) runs
  `powershell.exe -NoProfile -ExecutionPolicy Bypass -File Tests\Invoke-SmokeTest.ps1` and gets a
  second result line, `[PASS] Start-M365SyncedUserFixes.ps1: the window opened and closed by
  itself (...)`, or a `[FAIL]` line saying why (window not rendered in time, background check
  failed, the ActiveDirectory module got loaded, a message box would have been shown, a change or
  AD search was attempted, the core file is missing).
- A tech can run `.\Start-M365SyncedUserFixes.ps1 -SmokeTest` on a workstation or server to check
  a copied tool folder starts there, without RSAT being touched, without AD or network traffic, and
  without leaving files behind.
- If someone adds a GUI to the runner's list that has no `-SmokeTest` switch, the runner reports
  it as failed instead of starting that GUI normally.
- Normal starts of the window (launchers, `-Tab`, `-EntraConnectServer`, ...) are unchanged.

## Approach
**Pattern.** Follow SQ-029 (`FolderPermissionManager-GUI.ps1` `#region Smoke test`, lines
~6996-7145; `Tests/Invoke-SmokeTest.ps1`). Tool folders are self-contained, so the smoke helpers
(`Add-SmokeFailure`, `Get-SmokeVerdict`, `Get-SmokeTickAction`, `Set-SmokeWindowMode`,
`Invoke-SmokeTick`, `Start-SmokeProbe`, `$script:SmokeState`, `$script:SmokeDeadline` 30 s,
`$script:SmokeFailures`) are copied into this script, adapted, not shared.

**3.0 floor.** This script declares `#Requires -Version 3.0` (unlike FPM). No `::new()` (use
`New-Object` / `New-Object System.Collections.Generic.List[string]`), no `.Where()/.ForEach()`,
no `-NoNewline`. Pure ASCII. `Tests\PSVersionFloor.Tests.ps1` and the tool's
`Compatibility.Tests.ps1` must stay green.

**App changes (`Start-M365SyncedUserFixes.ps1`).**
- Param block: add `[switch]$SmokeTest`; help `.PARAMETER SmokeTest`, `.EXAMPLE`, and a
  `.NOTES` line "Smoke test: writes nothing, loads no AD module, contacts nothing".
- Directly after the param block (before any other code): `$script:SmokeMode = [bool]$SmokeTest`
  so every later path, including the pre-window failure paths, sees it (SQ-029 checklist gap 2).
- Startup seams (functions, defined before the `if ($LoadFunctionsOnly)` return):
  - `Get-StartupAction -IsSta [bool] [-SmokeTest]` -> `Continue` / `RelaunchSta` / `SmokeNeedsSta`.
  - `Show-StartupMessage -Title -Message` wraps the three startup `MessageBox::Show` calls
    (AD module missing, core missing, could not start); in smoke mode it writes `[FAIL]` and
    records a failure instead.
  - `Initialize-SyncedUserWindow` = today's lines from `[xml]$xaml = Get-MainWindowXaml` through the
    `Add_Closed` wiring, moved unchanged into a function, plus smoke branches; the Loaded handler
    body becomes `Invoke-WindowLoaded`. `Start-SyncedUserWindow` = `Initialize-SyncedUserWindow`
    + `ShowDialog()`. The core dot-source and `$script:` state initialisation stay at script level
    (dot-sourcing the core inside a function would scope its functions to that function).
  - `Copy-RuleScript` (the CopyScript handler body) and a save-dialog seam inside `Save-RuleScript`,
    so both can be guarded and faked.
- Start region, in order (each smoke branch is `if ($script:SmokeMode) { ... } else { <existing
  line unchanged> }`):
  1. smoke + any of `-LogFolder`, `-EntraConnectServer`, `-Credential`, `-SearchBase`,
     `-SkipRuleCheck` in `$PSBoundParameters` -> `[FAIL]` naming it, `exit 1`;
  2. `Get-StartupAction` with the real STA read; `SmokeNeedsSta` -> `[FAIL]` "The smoke test needs
     a single-threaded apartment: start powershell.exe with -STA.", `exit 1`; `RelaunchSta` ->
     existing relaunch block unchanged;
  3. `Add-Type` WPF (both modes);
  4. `Import-Module ActiveDirectory` skipped in smoke;
  5. core check -> `Show-StartupMessage` (smoke: `[FAIL]` + `exit 1`);
  6. core dot-source, state init (both modes); `Get-ADDomain` skipped in smoke
     (`$script:DomainName = $null`, chip text "not read (smoke test)");
  7. `Start-SyncedUserWindow`; then in smoke: verdict = `Get-SmokeVerdict` with
     `$script:SmokeFailures` + `Get-SmokeModuleFailures`, write its lines (Green/Red), `exit` its
     ExitCode; outer `catch` in smoke -> `[FAIL] ... could not start: <msg>`, `exit 1`.
- Inside `Initialize-SyncedUserWindow`, smoke only: `Set-SmokeWindowMode` (window XAML is
  `CenterScreen` 1220x780); `Add_ContentRendered` -> `Start-SmokeProbe`; a 200 ms smoke
  `DispatcherTimer` -> `Invoke-SmokeTick` (closes through the real `Closed` handler, which also
  stops the smoke timer); start `$script:SmokeState.Started` stopwatch.
- `Invoke-WindowLoaded`: always `Show-Section -Name $Tab` and `Update-RuleBuilder` (pure, uses
  `Get-SyncRuleBlueprint`/`Format-SyncRuleBlueprint`); normal mode then `Start-RuleCheck` +
  two `Start-PeopleLoad` as today; smoke mode instead sets both grids' Empty text to
  "Smoke test: Active Directory is not searched." and the server chip to "not checked (smoke test)".
- **Chokepoint (SQ-029 checklist gap 1).** Every AD read/write, Entra Connect call and delta sync
  goes through `Start-UiTask`. In smoke mode it accepts only `Test-SyncedUserCoreLoaded`; any other
  command adds a failure and returns without creating a PowerShell instance. Direct writers outside
  it are guarded too: `Complete-MarkerChange` (change log + delta-sync prompt), `Save-RuleScript`
  (modal dialog + file write), `Copy-RuleScript` (clipboard). `Show-Problem` / `Confirm-Action`
  become lines in smoke mode (`Confirm-Action` returns `$false`). The theme toggle writes nothing
  in this tool, so it needs no guard.
- Pool script block: lift the `AddScript({...})` block into `$script:UiTaskWork` with a fourth
  parameter `$Smoke`. Smoke: dot-source the core without `Import-Module ActiveDirectory` and
  without the `Get-Command` probe (which can trigger command discovery across PSModulePath).
  Normal: identical to today. `Start-UiTask` passes `[bool]$script:SmokeMode`.
- `Start-SmokeProbe` (on ContentRendered): marks Rendered, then
  `Start-UiTask -Command 'Test-SyncedUserCoreLoaded'` whose OnDone sets ProbeDone, and ProbeOk only
  when `Ok` is true and `LoadedModules` is empty (else ProbeError names the module or the missing
  functions). Using the literal `-Command 'Test-SyncedUserCoreLoaded'` keeps the existing
  "Background tasks" regression test green, because that function lives in the core.
- `Get-SmokeModuleFailures`: `Get-Module -Name ActiveDirectory, ADSync, 'Microsoft.Graph*'`
  (loaded modules only) in the window's runspace -> one failure text per module.

**Core change (`SyncedUserFixes.Core.ps1`).** Add `Test-SyncedUserCoreLoaded`: checks
`Test-Path -LiteralPath "Function:\<name>"` for the six commands the window runs in the
background, and `Get-Module -Name ActiveDirectory, ADSync, 'Microsoft.Graph*'` (loaded only).
Returns `[PSCustomObject]@{ Ok; Missing; LoadedModules }`. Function drive only, no disk, no AD.
3.0-compatible. Nothing else in the core changes.

**Runner (`Tests/Invoke-SmokeTest.ps1`).**
- Add `'M365-SyncedUserFixes\Start-M365SyncedUserFixes.ps1'` to `$script:DefaultTargets` after FPM.
- SQ-029 checklist gap 3: new `Test-SmokeTargetDeclaresMode -ScriptPath` (AST via
  `[System.Management.Automation.Language.Parser]::ParseFile`; true only when the script's own
  param block declares a `SmokeTest` parameter of type `switch`). `Invoke-SmokeTarget` calls it
  before `Start-SmokeProcess` and returns Failed (exit 1) with the AC21 texts. Update the runner's
  help (`-ScriptPath`: "Each must declare -SmokeTest; one that does not is reported as failed and
  not started").
- Existing runner tests that this changes (no assertion weakened; reviewers diff them):
  AC21/AC22 count `Start-SmokeProcess` / `Stop-SmokeProcess` calls per `$script:DefaultTargets`
  entry instead of exactly 1 for the default run; AC21's `one.ps1`/`two.ps1` and AC22's
  `Other-GUI.ps1` are created in `$TestDrive` with `[CmdletBinding()] param([switch]$SmokeTest)`
  so they pass the new check. This supersedes SQ-029's build note "-ScriptPath is not checked
  for existence".

**Docs.** `M365-SyncedUserFixes/README.md`: "Smoke test" section (what it proves, what it does
not touch, runner command, exit codes) and a `-SmokeTest` row in "Window options". Root README
unchanged.

**Sibling conflict.** SQ-031, SQ-032, SQ-034, SQ-035, SQ-036 each add a line to
`$script:DefaultTargets`, and each would want the declaration check and the AC21/AC22 count
change. Whichever lands first adds `Test-SmokeTargetDeclaresMode` and the per-target counts;

one-line). If a sibling merged first with the check, reuse it and drop that part from this item.

## Test plan
- New suite `M365-SyncedUserFixes/Tests/Start-M365SyncedUserFixes-SmokeTest.Tests.ps1`: AC1-AC21
  unit; AC22-AC24 in a `Describe ... -Tag 'Integration'`.
- Isolation for every test: `$env:ADPS_LoadDefaultDrive = '0'`; stub functions with the real
  parameter names for `Get-ADDomain`, `Get-ADUser`, `Set-ADUser` where RSAT is absent, each
  throwing; backstop mocks in every in-process run: `Start-Process`, `Invoke-Command`,
  `Get-CimInstance`, `Set-ADUser`, `Write-SyncedUserChangeLog`, `Write-EntraConnectSettings`
  throw; `Import-Module` throws for `ActiveDirectory`/`ADSync`/`Microsoft.Graph*` (ParameterFilter)
  and passes through otherwise; `Add-Type` mocked in in-process runs.
- In-process runs (`& $AppPath -SmokeTest ...`) follow SQ-029: Pester mocks are aliases and beat
  the functions the script defines; fake storage via `$global:` with cleanup by name in
  `AfterEach` (inside a mock called from an `& $Path` run, `$script:` is the run's scope). Each
  throwing fake is also asserted `-Times 0 -Exactly`. `Start-SyncedUserWindow` is always faked in
  in-process runs, so no window and no real pool there.
- AC10 uses a fresh runspace with a counting `Import-Module` function defined first, so even a
  broken implementation cannot load the real module. AC12 opens and closes its own pool.
- AC16/AC17 run only on an STA thread (skip otherwise), parse XAML, never call `Show`/`ShowDialog`.
- Runner tests mock `Start-SmokeProcess` in every case; `Start-Process` mocked to throw.
- Repo gates: `Tests\Test-ScriptParse.ps1`, `Tests\PSVersionFloor.Tests.ps1` (app and core at
  3.0), `Tests\ScriptEncoding.Tests.ps1`, the tool's existing three suites, and
  `Tests\Invoke-SmokeTest.Tests.ps1` unit tests.
- Edge cases: non-STA, each refused parameter, `-Tab` allowed, missing core, startup exception,
  every background command refused, every direct writer refused, AD module loaded in the window
  runspace or the pool, deadline, target without smoke mode / missing / unparsable.

What the tests cannot see:
- Whether the real window renders off-screen and fires ContentRendered under Windows PowerShell
  5.1 on Michael's workstation, how long a cold start takes, and that no window flashes or takes
  focus (multi-monitor / scaling). AC22-AC24 cover the first part but are Integration-tagged, so
  the squad never runs them; Michael runs them once at review. After that, the gate's
  `smokeCommand` (not yet set in `squad/squad.config.json`) covers "the app starts" on every item.
- Whether the real ActiveDirectory module still imports and a real AD search, rule check, Entra
  Connect discovery or marker change works: the smoke skips all of them by design. These stay on
  the owner's try-list for any item that touches them.
- RSAT missing or broken on a machine: the smoke passes there although the normal start would show
  "Missing prerequisite".
- Behaviour with no interactive desktop (locked session, service): expected `[FAIL]`/timeout, untested.
