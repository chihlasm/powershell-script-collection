# SQ-005 · End-of-support section in AD-Audit

- status: ready
- size: M
- risk: low
- touches: AD-Audit (`Invoke-ADAudit.ps1` collection, HTML and CSV export; one entry in the
  `Show-ADAuditGUI.ps1` section list; `README.md`; `Tests/Invoke-ADAudit.Tests.ps1`)

## Summary (plain English)
AD-Audit gets a new "End of support" section. It lists every enabled Windows Server in the domain
with Microsoft's support end dates, how many days are left (or how long ago support ended), and
when the server last logged on. Each date links to the Microsoft Learn lifecycle page it came
from, and the report shows when the date table was last checked. Wording is careful: a server
past extended support is "covered only if the client bought ESU", because AD cannot tell. The CSV
records when the audit ran and who ran it, so this quarter's list can be compared with last
quarter's.

## What users will be able to do
- Run AD-Audit as today (CLI or GUI) and get an "End of support" section after "Computer
  Accounts", listed in the table of contents. It can be run on its own with
  `-IncludeSection EndOfSupport` and is ticked by default in the GUI.
- See one row per enabled Windows Server computer account: name, OS as AD records it, matched
  product, support status in plain words, mainstream / extended / ESU end dates, days until
  extended support ends (negative means "ended N days ago"), last logon, a "not seen in
  `-DaysInactive` days" flag, and a link to the Learn lifecycle page.
- See a headline count in the Audit Summary: "Servers past end of support".
- See, above the table: the date the lifecycle table was last checked against Microsoft Learn,
  who ran the audit, from which machine, and a note that last logon can be up to about 14 days
  behind.
- Get `AD-Audit-<timestamp>-EndOfSupport.csv` with the same rows plus audit date, audited domain,
  run-by account, run-on machine, and table-checked date on every row, so two quarters' files
  can be compared side by side.
- Servers whose OS string is not in the table appear as "Not in the lifecycle table - check
  https://learn.microsoft.com/lifecycle manually", never as supported and never dropped.

Status wording (one per row; the builder keeps these words):
| Status | Note shown |
|---|---|
| Mainstream support | "In mainstream support until <date>." |
| Security updates only | "Mainstream support ended. Security updates until <ext>; <N> days left." |
| Extended support ended | "Extended support ended on <ext>; covered only if the client bought ESU (ESU available until <esu>)." If ESU exists but no end date is published, omit the bracket. |
| No support | "All support ended on <last date>, including paid ESU." (or "...; no ESU was offered.") |
| Unknown | "Not in the lifecycle table - check https://learn.microsoft.com/lifecycle manually." |

Severity: No support = High (red); Extended support ended = Warning; Security updates only with
365 days or fewer left = Warning, otherwise Info; Mainstream = Low; Unknown = Warning.

## Acceptance criteria
Tests live in `AD-Audit/Tests/Invoke-ADAudit.Tests.ps1` (Pester 5). Unit tests use synthetic
lifecycle rows where the exact real date does not matter, so a later table update does not break
them.

1. AC1_LifecycleTableIsCitedAndWellFormed: Given `Get-ServerLifecycleTable`, then every row has
   `Product`, `Pattern`, `MainstreamEnd`, `ExtendedEnd` (strings parsable with
   `ParseExact('yyyy-MM-dd', InvariantCulture)`), optional `EsuEnd` in the same format,
   `Source` starting with `https://learn.microsoft.com/lifecycle/`, and the table exposes a
   `CheckedOn` date in the same format. MainstreamEnd <= ExtendedEnd <= EsuEnd where present.
2. AC2_OsStringsMapToTheRightProduct: Given OS strings "Windows Server 2012 R2 Standard",
   "Windows Server 2012 Datacenter", "Windows Server 2008 R2 Enterprise",
   "Windows Server<U+00AE> 2008 Standard" (built with `[char]0x00AE`), "Windows Server 2003",
   "Windows Server 2016 Standard", "Windows Server 2019 Datacenter", "Windows Server 2022
   Datacenter", "Windows Server 2025 Datacenter", when `Resolve-ServerLifecycle` runs, then each
   maps to its own product ("2012 R2" never resolves to 2012, "2008 R2" never to 2008).
3. AC3_UnknownOsIsNeverReportedSupported: Given "Windows Server Datacenter" (Semi-Annual
   Channel), "Windows Storage Server 2016 Standard", and "Windows Server 2031 Standard", when
   status is computed, then Status is `Unknown`, Severity `Warning`, and the note contains
   "check https://learn.microsoft.com/lifecycle manually".
4. AC4_ExtendedEndDayBoundary: Given a synthetic row with ExtendedEnd 2027-01-12 and no ESU,
   when AsOf is 2027-01-11, 2027-01-12 23:59, and 2027-01-13 00:01, then DaysUntilExtendedEnd is
   1, 0, -1 and Status is Security updates only, Security updates only, No support (the listed
   end date is the last covered day; time of day is ignored).
5. AC5_EsuWindowIsHedged: Given a synthetic row with ExtendedEnd 2023-10-10 and EsuEnd
   2026-10-13, when AsOf is 2024-06-01, then Status is `Extended support ended` and the note
   contains "covered only if the client bought ESU"; when AsOf is 2026-10-14, then Status is
   `No support` and the note says ESU also ended.
6. AC6_MainstreamToExtendedTransition: Given a synthetic row with MainstreamEnd 2026-10-13,
   when AsOf is 2026-10-13 then Status is `Mainstream support`, and on 2026-10-14 it is
   `Security updates only`.
7. AC7_WarningThreshold: Given a row in "Security updates only", when 365 days are left then
   Severity is `Warning`, and when 366 days are left it is `Info`.
8. AC8_CultureIndependent: Given the current culture is set to `de-DE` (and restored after),
   when the table is parsed and status computed for AC4's dates, then results equal the
   invariant-culture results.
9. AC9_QueriesOnlyEnabledWindowsServersWithAdParams: Given `Get-ADComputer` is mocked, when
   `Get-EndOfSupportAudit` runs with `$ADParams` holding Server and Credential, then
   `Get-ADComputer` is called with a `-Filter` limited to `OperatingSystem -like '*Windows
   Server*'`, `-Properties` including `OperatingSystem`, `OperatingSystemVersion`,
   `LastLogonDate`, `Enabled`, and the `Server`/`Credential` values; disabled accounts are not in
   the result.
10. AC10_RowsCarryStampAndNoSecrets: Given a mocked server and a `-Credential`, when the audit
    row is built, then it has `AuditDate` (yyyy-MM-dd HH:mm:ss), `AuditedDomain`, `RunBy`,
    `RunOn`, `TableCheckedOn`, and `Source`; `RunBy` includes the credential's user name when
    one is given; no property holds a `PSCredential`, `SecureString`, or the word "password".
11. AC11_StaleAndNeverLoggedOn: Given servers with LastLogonDate older than `-DaysInactive`,
    newer, and `$null`, then `Stale` is `$true`, `$false`, `$true` and the `null` row shows last
    logon as "Never".
12. AC12_CsvExport: Given audit results with two End of support rows, when
    `Export-CSVReports` writes to `$TestDrive`, then `<ReportName>-EndOfSupport.csv` exists with
    columns in this order: Name, OperatingSystem, OperatingSystemVersion, Product, Status,
    Severity, DaysUntilExtendedEnd, MainstreamEnd, ExtendedEnd, EsuEnd, Note, LastLogonDate,
    Stale, Source, TableCheckedOn, AuditDate, AuditedDomain, RunBy, RunOn. With zero rows no
    file is written (matches existing CSVs).
13. AC13_HtmlSectionAndSummary: Given results with one row per status, when
    `Export-HTMLReport` writes to `$TestDrive`, then the HTML has `id="endofsupport"`, a TOC link
    `#endofsupport`, the "last checked" date, the 14-day last-logon note, the ESU hedge text, a
    "Servers past end of support" metric equal to the number of `Extended support ended` plus
    `No support` rows, and a server named `<script>x</script>` appears only escaped.
14. AC14_StaleTableWarns: Given `CheckedOn` is more than 180 days before the audit date, when
    the section runs, then `Write-AuditLog -Level Warning` is called with a message naming the
    checked date and https://learn.microsoft.com/lifecycle, and the HTML shows the same warning;
    at 180 days or fewer, no warning.
15. AC15_SectionIsSelectable: Given the script text and `Show-ADAuditGUI.ps1` text, then
    `IncludeSection`'s ValidateSet and `$AllSections` contain `EndOfSupport`, and the GUI
    `$sections` list contains `@{ Name = 'EndOfSupport'; ... }` (static parse, the GUI is never
    launched).
16. AC16_AdFailureIsReportedNotHidden: Given `Get-ADComputer` throws, when
    `Get-EndOfSupportAudit` runs, then it does not throw, logs `-Level Error`, returns no rows
    with an `Error` message, and the HTML section says "Could not read servers from AD: <msg>"
    rather than "No Windows Server computer accounts found".
17. AC17_EmptyState: Given no enabled Windows Server accounts, then the HTML section says "No
    enabled Windows Server computer accounts found." and the metric is 0.
18. AC18_ComputersUnsupportedListUsesTable: (only if the owner picks option A on the question
    about the existing list) Given servers on 2012 R2, 2016 and 2022 and an audit date of
    2027-02-01, when `Get-ComputerAccountAudit` runs, then its `UnsupportedComputers` server
    entries are exactly those whose lifecycle status is `Extended support ended` or `No support`
    (2012 R2 and 2016, not 2022); client OS patterns (XP, Vista, 7, 8) are unchanged.

## Out of scope
- Automatic comparison with a previous audit's CSV (pending owner answer; default is out).
- Client operating systems (Windows 10/11), Hyper-V Server, Azure Stack HCI / Azure Local,
  Windows Storage Server, Small Business Server, Semi-Annual/Annual Channel releases: shown as
  `Unknown` if their OS string contains "Windows Server", otherwise not listed.
- Detecting whether a server actually has ESU (AD cannot tell; the wording hedges instead).
- Any remoting, roles, services, or tasks on the servers. No new permissions; AD read only.
- Fetching lifecycle dates at run time (output stays local; the table is static and cited).
- Restyling the AD-Audit HTML report.

## Approach
- **Lifecycle table**: new function `Get-ServerLifecycleTable` in `Invoke-ADAudit.ps1`'s helper
  region, next to `Get-SchemaVersionOS` (which already embeds a cited map). Returns
  `@{ CheckedOn = 'yyyy-MM-dd'; Rows = @(...) }`. One row per product: Windows Server 2003,
  2008, 2008 R2, 2012, 2012 R2, 2016, 2019, 2022, 2025. Each row: `Product`, `Pattern` (regex,
  anchored, tolerant of `(R)`/`®` and `\s+`, e.g. `'^Windows Server\W*2012 R2\b'`), ordered so
  R2 patterns come first, `MainstreamEnd`, `ExtendedEnd`, `EsuEnd` (or `$null`), `Source`, and
  a comment with the Learn URL above each row.
- **Every date is verified on Learn during the build** (root `CLAUDE.md`): Learn MCP, or
  `WebFetch` of `https://learn.microsoft.com/lifecycle/products/windows-server-<version>`.
  Store the last covered calendar day. Where Learn writes an end as "<date> 06:59 PT" style
  (start of the next day), store the previous day. For ESU, store the latest end date of any
  ESU offering (on-premises or Azure), so the tool never says "no coverage possible" while some
  offering could still cover. Set `CheckedOn` to the build date.
- **Pure functions** (testable without AD): `Resolve-ServerLifecycle -OperatingSystem -Table`,
  `Get-EndOfSupportStatus -Lifecycle -AsOf` (date-only arithmetic on `.Date`,
  `ParseExact` with `InvariantCulture`), `Test-LifecycleTableAge -CheckedOn -AsOf`.
- **Collection**: `Get-EndOfSupportAudit` follows `Get-ComputerAccountAudit`'s shape:
  `Write-AuditLog`, try/catch, `Get-ADComputer -Filter "OperatingSystem -like '*Windows Server*'"
  -Properties ... @ADParams -ErrorAction Stop`, enabled only, returns
  `@{ Servers = @(...); PastEndCount = n; StaleTableWarning = ...; Error = $null }`. Uses
  `$AuditDate`, `$StaleDate`, `$Domain`/`(Get-ADDomain).DNSRoot` for AuditedDomain,
  `"$env:USERDOMAIN\$env:USERNAME"` for RunBy (plus `" (as <Credential.UserName>)"`),
  `$env:COMPUTERNAME` for RunOn.
- **Wiring**: add `EndOfSupport` to the `IncludeSection` ValidateSet, `.PARAMETER` help,
  `$AllSections`, the `$auditResults` hashtable (with an empty default like the others),
  `$csvMap` (`'EndOfSupport'`), the HTML TOC and a section after Computers using existing CSS
  classes (`severity-*`, `badge-*`), and the Audit Summary metric block. All AD-sourced values
  go through `Escape-Html`. `Show-ADAuditGUI.ps1`: one entry in `$sections`
  (`Label = 'End of Support'`); 11 checkboxes still fit the existing 3-column grid (row 3,
  y=100, above Select All at y=148).
- **Docs**: `.DESCRIPTION` bullet, `.NOTES` REFERENCES (each lifecycle page and
  `a-lastlogontimestamp`), README "Section Names", "Audit Sections" and "Output" entries, and the
  test table in README "Files". Bump `.NOTES` Version.
- `#Requires -Version 5.1` stays (already 5.1). Keep the script ASCII-only, or save it as
  UTF-8 with BOM if a non-ASCII character is unavoidable (`Tests/ScriptEncoding.Tests.ps1`).
- Plans: no document under `docs/plans/` covers this; the idea card
  `squad/ideas/sessions/2026-10-16/cards/I-11-end-of-support-in-ad-audit.md` is the source.

## Decisions
### Confirmed by the owner
- D-020 the Unsupported OS list's server entries come from the new lifecycle table (adds AC18).
- D-021 no automatic previous-audit comparison in v1.
- Backlog item text (approved 2026-10-17 pitch session): AD-Audit only, no new remoting, hedged
  ESU wording, cited dates with a last-checked date, dated CSV recording who ran it, date edge
  cases tested.
- (Pending: comparison feature; existing "Unsupported Operating Systems" list. See questions.)

### Assumed by the squad
- **New section `EndOfSupport` rather than extending `Computers`.** Lets seniors run it alone
  (`-IncludeSection`) and keeps its CSV separate; costs one extra filtered `Get-ADComputer`
  query, which is cheap. Evidence: every audit area is its own section in `$AllSections`.
- **Table embedded in the script, not a separate `.psd1`.** The card suggested a psd1, but
  AD-Audit is copied and run as one file and already embeds its cited schema map in
  `Get-SchemaVersionOS`; a missing psd1 would silently drop the section. Pure-data tests work
  the same either way.
- **Enabled accounts only, stale ones flagged, not hidden.** Matches `UnsupportedComputers`
  (enabled only) in `Get-ComputerAccountAudit`; flagging rather than removing stale servers
  avoids hiding a forgotten-but-running box.
- **"Days left" counts to the extended support end date** (the day security updates stop
  without paid ESU), signed: negative means days since. One sortable column; the note gives
  the plain-words version.
- **End dates are the last covered calendar day; comparisons are date-only** in the audit
  machine's local date. Microsoft states ends in Pacific time; a sub-day difference does not
  matter for a quarterly audit. Tested at the boundary (AC4).
- **ESU end = latest end of any ESU offering** (on-premises or Azure), so the report never
  rules out coverage that might exist. Follows the card's "covered only if the client bought
  ESU" hedge.
- **Warning at 365 days or fewer before extended end.** Server migrations take quarters, and a
  quarterly audit with a 90-day threshold could miss the window. It is one constant and easy
  to change.
- **Table-age warning after 180 days** since `CheckedOn`. Two quarterly audits; Microsoft does
  change dates (new ESU offers).
- **If a date cannot be verified on Learn during the build, its product row is left out**
  (servers on it show as `Unknown - check manually`) instead of using a recalled date. Root
  `CLAUDE.md` forbids unverified Microsoft facts; this keeps the build from stopping.
- **Who ran it**: `$env:USERDOMAIN\$env:USERNAME` plus the `-Credential` user name when one is
  given; never the credential object. Matches personal-data rules.
- **Last logon uses `LastLogonDate`** (from replicated `lastLogonTimestamp`, which can lag by
  about 14 days), as the rest of AD-Audit does, with a visible note. Builder cites
  https://learn.microsoft.com/windows/win32/adschema/a-lastlogontimestamp after verifying.
- **No new `.gitignore` entry**: AD-Audit writes to `-OutputPath` (default current directory),
  not a fixed case folder, as today.

## Risk and safety notes
- Read-only, AD only, no new permissions or remoting. No destructive or system-configuration
  profile applies.
- `squad/risks/personal-data.md` applies through `Export-Csv`: the CSV adds the tech's account
  name and machine name, nothing else; no credential material; all AD values HTML-escaped;
  synthetic test data only.
- The real accuracy risk is wrong or stale dates. Mitigations: per-row Learn citation,
  build-time verification, visible "last checked" date, table-age warning, hedged ESU wording,
  unknown OS never shown as supported.
- Do not launch `Show-ADAuditGUI.ps1` or run `Invoke-ADAudit.ps1` against a domain during the
  build.
