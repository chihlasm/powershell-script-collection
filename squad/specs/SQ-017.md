## Summary (plain English)
FolderPermissionManager becomes a normal Windows window instead of a web page served from a
PowerShell window. Slow work (opening folders on a busy share, taking ownership of a big tree)
runs in the background, so the window never freezes, and nothing listens on the network any
more. Everything a tech can do today stays, with the same safety: permissions are backed up and
every change is logged before and after, exactly as now, because the same core code does the
work. The old browser version stays in the folder until Michael has lab-tested the new one.

## What users will be able to do
- Start the tool by running `FolderPermissionManager-GUI.ps1` (D-038) or "Run with PowerShell". If it is not
  elevated it asks Windows for admin rights (UAC) and reopens itself; if that is declined it
  says why it needs admin and closes. A second copy using the same log folder is refused with
  "Folder Permission Manager is already open (possibly in another session on this computer).
  Use that window, or close it first."
- See, at all times: the full path of the selected folder (and the UNC path behind a mapped
  drive letter), where changes are backed up and logged (with an "Open log folder" button), and
  a clear busy line with a progress bar and elapsed time while anything is loading or changing.
- Browse drives (local and mapped) and folders in a tree; folders load in the background. A
  folder that can't be opened shows the same plain next step as today ("Take ownership (this
  folder only) first, then use Add Permission..." or "You own '<path>' but have no permission to
  open it...").
- View a folder's owner and permission entries (User or Group, Permission Level, Allow/Deny,
  Inherited), the files in it (name, size, modified), and each file's owner and entries
  (expand a row). Select files (one, several, all); when the selected files' permissions differ,
  see "Selected files have different permissions — this operation applies uniformly to all".
- Make every change available today, one at a time:
  - Folder: Add Permission, Remove Permission, Take Ownership (this folder only), Take Ownership
    of all subfolders and files, Copy Permissions To... (add only, D-031).
  - Selected files: Add Permission, Remove Permission, Take Ownership.
  Each destructive action asks first in a dialog that names the path(s) and how many items, with
  a verb on the button ("Take ownership of 12,408 items"), Cancel as the default. After each
  change the status area shows the same message as today (what was done, backup and log paths,
  "Partly done: ...", "Check this: ...", "could not read ... cannot be restored from this
  backup", the D-034 "Escalate: <n> folder(s) could not be opened..." line, the D-036 refusal).
  The message text can be selected and copied.
- Export the selected folder's permission report (folder and all subfolders) to a CSV file they
  choose in a Save dialog; it runs in the background and can be stopped.
- Switch between dark (default) and light; the choice is remembered.
- Start in dry-run mode with `-WhatIf`: the window says "Dry run (WhatIf): nothing will be
  changed" and every result reads "WhatIf: nothing was changed (<n> items would be)."
- Robocopy tab and "Copy Files To...": not in the new app (D-037); the window and README point
  to RobocopyMigration.

## Approach
- **Files.** New app script in `FolderPermissionManager/` named `FolderPermissionManager-GUI.ps1` (D-038), UTF-8 with BOM. SQ-017 renames the
  browser GUI to `FolderPermissionManager-WebGUI.ps1` with `git mv` and repoints its two GUI
  test files to the new name (path only, no assertion changes). It
  dot-sources `FolderPermissions.Core.ps1 -LoadFunctionsOnly` exactly as the current GUI does
  (fail with a plain message if the core is missing). Layout follows
  `RobocopyMigration/RobocopyMigration-GUI.ps1`: help block, `param()`, pure helpers, work
  script blocks, XAML getter functions, then `if ($LoadFunctionsOnly) { return }`, then startup
  checks, themes, background pool, UI wiring, main. Put the XAML in getter functions before the
  return (M365-SyncedUserFixes `Get-MainWindowXaml` pattern) so tests can read it.
- **Startup**, in this order, as RobocopyMigration does: STA check and relaunch; `Add-Type`
  PresentationFramework/PresentationCore/WindowsBase/System.Windows.Forms; elevation check with
  `WindowsPrincipal.IsInRole(Administrator)` and `Start-Process -Verb RunAs` relaunch passing
  `-LogFolder`, `-WhatIf` and the drive map (see below); `Resolve-ChangeLogFolder` (fail with a
  message box on throw); single-instance mutex named from the resolved log folder; hide the
  script's own console (`Hide-OwnConsole` pattern) once the window renders. The startup
  `[INFO]`/`[WARN]` lines become the window's log-folder banner (AC24).
- **Mapped drives.** Port RobocopyMigration's `Get-MappedDriveTable`/`Resolve-MappedDrive`
  (map as a parameter, so they are pure). The non-elevated first launch reads the map and passes
  it to the elevated relaunch, because the elevated session usually can't see the user's
  mappings; merge it with what the elevated process finds. Verify and cite the UAC/mapped-drive
  behaviour on Learn.
- **Background work model** (RobocopyMigration's `Start-BgTask`/`Update-BgTasks`):
  - One `RunspacePool(1, 4)`, opened at startup and closed in `finally`. A
    `DispatcherTimer` (200 ms) calls `Update-BgTasks`, which runs each finished task's
    completion callback on the UI thread. Workers return plain `[PSCustomObject]` data and never
    touch controls.
  - Each work block takes `$CorePath` and dot-sources the core when it is non-empty (tests pass
    `$null` because they already loaded it, so Pester mocks stay in effect).
  - Reads (drives, children, folder permissions, files, file permissions, tree count, export)
    may run side by side. Each read carries a request number per pane; a stale result is dropped
    (AC18). Export can be stopped (`PowerShell.Stop()`); reads that are superseded are simply
    ignored.
  - Changes go through `Start-ChangeTask`: one at a time, all change controls disabled, busy line
    "<Action> on <path>... <elapsed>" with an indeterminate progress bar. Browsing stays usable
    during a change. The completion callback always clears the busy state (`finally`). Closing
    the window while a change runs is refused (AC41). Changes have no cancel: stopping takeown
    or a batch midway leaves a half-changed tree.
  - Change work = `Invoke-LoggedPermissionChange -Change { <core function> ... -Confirm:$false
    -WhatIf:$WhatIf } -LogFolder $LogFolder`, then `Get-ChangeResultMessage`. This is the same
    path `Complete-PermissionChange` uses in the current GUI; port that helper and
    `ConvertTo-ChangeResultRow`, plus whatever SQ-014/SQ-015 added (the `partial` status,
    `TreeCounts`, `Skipped (nothing to copy)`, the up-to-date copy row), into PowerShell status
    functions (`Get-ChangeStatus`, AC39). The JS `changeStatusType`/`showChangeResult` rules move
    into `Get-ChangeStatus`.
- **Parity inventory** (main as of efa6afb; the builder re-reads the GUI after SQ-014 and
  SQ-015 merge and adds anything they changed). Endpoint or JS function, then the WPF
  equivalent:
  - `GET /api/drives` (`Get-Drives`): drive tree roots, background (AC14).
  - `GET /api/children` (`Get-Children`, `Get-AccessDeniedMessage`): tree expansion,
    background; 400/403/500 become node error states with the same texts (AC16, AC17). Instead
    of listing every child to decide whether it has subfolders (one extra network call per
    child), every folder shows an expander and loses it when it turns out to be empty, as
    Explorer does on network paths.
  - `GET /api/acl` (`Get-FolderAcl`): folder permissions pane (AC19). The page's "Folder
    Permissions" title shows the folder name; the path header shows the full path (AC22).
  - `GET /api/files`, `GET /api/file-acl`: files grid with checkboxes, select all, expandable
    row details with owner and entries (AC20); diff warning (AC21); "N file(s) selected" action
    bar shown only when something is selected.
  - `POST /api/add-ace`, `/api/remove-ace`, `/api/file-acl/add`, `/api/file-acl/remove`: add and
    remove dialogs ("Add Permission Entry" / "Add Permission to Selected Files", "Remove
    Permission Entry" / "Remove Permission from Selected Files"), status texts "Backing up and
    adding the permission..." etc. kept (AC29-AC31, AC42, AC43). Remove button uses the danger
    style.
  - `POST /api/take-ownership` (single and recursive), `/api/file-acl/take-ownership`: confirm
    texts from the current GUI ("Take ownership of:\n\n<path>?", "Take ownership of <n>
    file(s)?") and SQ-014's whole-tree text, plus the scope count (AC32-AC37). The overflow menu
    labels "Take Ownership" and "Take Ownership — All Files Too" may become buttons/menu items
    with the same words (SQ-014's label if it changed it).
  - `POST /api/replicate`: Copy Permissions To... dialog with the SQ-015 help text (AC38).
  - `GET /api/export`: Save dialog plus background export (AC23).
  - `GET /api/shutdown` and its "Stop the server?" confirm: gone; closing the window ends the
    tool.
  - Theme toggle (`toggleTheme`, localStorage `fpm-theme`): `Set-AppTheme` plus
    `%LOCALAPPDATA%\FolderPermissionManager\settings.json` (AC4, AC5). Dark default, palette and
    style resources copied from RobocopyMigration (blue accent `#5DADE2`).
  - Status bar with role/aria-live: a read-only, selectable status text with colour plus the word
    prefix for warnings (AC39), so long backup paths can be copied.
  - `api()` network-error texts ("Could not reach the Folder Permission Manager server...") no

  - `POST /api/robocopy`, `GET /api/robocopy-preview`, `POST /api/robocopy-files`, the Robocopy
    tab, the mirror type-MIRROR confirm, "Copy Files To...": dropped (D-037).

  the destructive button and Cancel as default, which `MessageBox` can't label.

  support it and the core already does; also handy for the lab test.

  that per-child listing is a large part of the slowness on shares.
- **Remove for files loads the selected files' permissions itself** instead of asking the tech to
