# SQ-021 · FolderPermissionManager: the admin-share route gets the server-side junction check

- status: dropped (merged into SQ-023, 2026-10-19 plan; its ACs are built there)
- size: S
- risk: high (destructive-operations profile in full; read-only-advisory "Advice" for the refusal next step)
- touches: `FolderPermissionManager/FolderPermissionManager-GUI.ps1` (the whole-tree lookup: `Get-ShareTreeRefusal`, `Get-ServerSideLinkRefusal`), `FolderPermissionManager/Tests/FolderPermissionManager-AppChanges.Tests.ps1`, `FolderPermissionManager/README.md`
- depends-on: SQ-018 (the code this item changes exists only on `squad/SQ-018-fpm-wpf-changes`; SQ-018 merges to main first, after its AC55-AC57 revision). Branch from main after that merge.

## Summary (plain English)
Before a whole-tree take ownership on a network share, the WPF app asks the file server where the
share's folder really is and checks every folder on that path for junctions (D-045). That check
is skipped when the tech types the server's administrative share instead, such as
`\\fs01\D$\Shares\Data`. That is exactly the path the app tells the tech to use when the share
lookup fails. After this item the same junction check runs on admin-share paths. A junction
there (for example `D:\Shares` pointing into `C:\Users`) stops the change before the count and
the confirm, as it already does for ordinary shares.

## What users will be able to do
- Whole-tree take ownership on `\\server\X$\folder\...` behaves like the same folder reached
  through an ordinary share. If any folder on the path is a junction or other reparse point, or
  cannot be checked, the change is refused before the count and the confirm. The refusal names
  the folder and says "run the tool on the server itself, or ask a senior admin".
- The same applies when the target only *resolves* to an admin share: a mapped drive or a
  single-target DFS folder that lands on `\\server\X$\...`.
- When the share lookup fails, the app can keep advising the admin-share path, because that
  route is now checked too.
- Nothing changes for local folders, ordinary shares, or the admin-share refusals that already
  exist (`ADMIN$`, a bare `\\server\D$`, `\\server\D$\Windows` and the other D-036 folders, and
  the high-impact roots).

## Acceptance criteria
Each criterion maps to exactly one test, named `AC<n>_...`, in
`FolderPermissionManager/Tests/FolderPermissionManager-AppChanges.Tests.ps1`, unless stated
otherwise. Every server read is mocked at the seam the SQ-018 AC52 tests already mock (the
attribute read behind `Get-ServerSideLinkRefusal`). No test reaches a real share.

1. AC1_AdminShareJunctionRefusesTree: Given a whole-tree take ownership typed as
   `\\fs01\D$\Shares\Data`, where the mocked attribute read reports `\\fs01\D$\Shares` as a
   reparse point, when the lookup runs, then the change is refused before the item count and
   before the confirm. No change task starts. The refusal names `\\fs01\D$\Shares` and ends with
   "run the tool on the server itself, or ask a senior admin".
2. AC2_AdminShareEveryComponentChecked: Given `\\fs01\D$\Shares\Dept\Data` with no reparse
   points, when the lookup runs, then the attribute read is called once for each of
   `\\fs01\D$\Shares`, `\\fs01\D$\Shares\Dept` and `\\fs01\D$\Shares\Dept\Data`. The chosen
   folder itself is included, as in AC52. The change goes on to the count and the confirm.
3. AC3_AdminShareUncheckableComponentRefuses: Given `\\fs01\D$\Shares\Data`, where the mocked
   read of `\\fs01\D$\Shares` fails (access denied, or the folder is not found), when the lookup
   runs, then the change is refused as "could not be checked", fail closed, matching AC52 and
   lead ruling 4.
4. AC4_AdminShareSkipsShareLookup: Given a target on `\\fs01\D$\...`, when the lookup runs,
   then NetShareGetInfo (`Get-RemoteShareLocalPath`) is not called. The server-side path is the
   typed path itself, because `<letter>$` is the root of that drive on the server. A test pins
   that the mock was called 0 times.
5. AC5_AdminShareOddSpellingsStillChecked: Each of the following, typed as a whole-tree target,
   reaches the same component check and is refused when `Shares` is mocked as a reparse point.
   No spelling may fall through a "not an admin share" branch:
   - `\\fs01\d$\Shares\Data` (lower-case letter)
   - `\\fs01\D$\Shares\Data\` (trailing backslash)
   - `\\fs01\D$\\Shares\Data` (doubled backslash)
   - `\\?\UNC\fs01\D$\Shares\Data`
   - `\\fs01\D$\Shares.\Data` (trailing dot)
   - `\\FS01.contoso.local\D$\Shares\Data` (FQDN)

   One `-ForEach` test.
6. AC6_ResolvedToAdminShareChecked: Given a mapped drive `Z:` whose server path is
   `\\fs01\D$\Shares` (mocked `Resolve-NetworkDrivePath`), when a whole-tree take ownership on
   `Z:\Data` is looked up, then the component check runs on `\\fs01\D$\Shares` and
   `\\fs01\D$\Shares\Data`. A reparse point on `Shares` refuses the change, and the refusal shows
   both `Z:\Data` and the real location.
7. AC7_LateRecheckParityWithShares: Given the late re-check that runs just before takeown
   (SQ-018 AC53a), when the target is an admin-share path, then it applies the same server-side
   component check it applies to an ordinary share's server path. If the ordinary-share re-check
   does not repeat AC52 today, both get it. The test flips the mocked attribute of
   `\\fs01\D$\Shares` to a reparse point between the confirm and takeown, and expects a refusal
   with no call to the takeown wrapper (`Invoke-AclTool`, backstop-mocked).
8. AC8_FallbackAdviceRouteIsChecked: a regression test for the exact bug. Given an ordinary
   share `\\fs01\Data` where the mocked NetShareGetInfo fails, then:
   1. `Get-ShareTreeRefusal`'s refusal is taken.
   2. The admin-share path it suggests is fed back into the lookup as the new target.
   3. With `D:\Shares` mocked as a reparse point, the new lookup is refused by the
      server-side junction check.

   If the refusal no longer suggests an admin-share path, the test asserts that its next step
   contains "run the tool on the server itself, or ask a senior admin" and no `$\` path.
9. AC9_ExistingAdminShareRefusalsUnchanged: `\\fs01\ADMIN$\x`, `\\fs01\D$` and
   `\\fs01\D$\Windows\Temp` are still refused by the D-036 text check (`Get-TreeOwnershipRefusal`)
   with today's wording, before any attribute read. The test asserts 0 calls to the attribute
   seam. `\\fs01\D$\Users` is still refused by the high-impact-root check.
10. AC10_ReadmeSaysAdminSharesChecked: the README's whole-tree take ownership section says that
    the junction check on the file server also covers paths typed as `\\server\D$\...`. Test
    file: `FolderPermissionManager-App.Tests.ps1`, or wherever the existing README assertions
    live.

## Out of scope
- The CLI (`FolderPermissionManager.ps1`) and the core. Moving `Get-ShareTreeRefusal` and
  `Get-ServerSideLinkRefusal` into `FolderPermissions.Core.ps1` and calling them from
  `Get-TreeOwnershipTargetRefusal` is SQ-023. The browser GUI is removed after the SQ-018 lab
  test (owner, 2026-10-19), so it gets nothing here.
- `.` and `..` segments in share paths (SQ-024). On an admin share, `ConvertTo-ComparablePath`
  stops `..` at `\\server\X$`, which matches what Windows does there, so this item does not
  widen the SQ-024 gap. The AC5 spellings deliberately include no `..`.
- Copy targets (D-044, SQ-022). The server-side check stays whole-tree only, as in SQ-018.
- Single-item changes (add, remove, take ownership of one folder or files).
- Whether the D-040 allowlist should relax the AC52 "any reparse point" rule, for example for
  mounted volumes. This item keeps AC52's rule as built (see "Risk and safety notes").
- Hidden non-drive shares ending in `$` (`Users$`, `Profiles$`). They are ordinary shares, go
  through NetShareGetInfo, and are already covered by AC52.

## Approach
- **Where the gap is.** Per the SQ-018 reports and AC52, the WPF whole-tree lookup calls
  `Get-ShareTreeRefusal` for a remote target. For a non-admin share, `Get-ShareTreeRefusal`
  asks NetShareGetInfo level 2 for the server folder (`Get-RemoteShareLocalPath`). It maps that
  folder to `\\server\X$\...` and calls `Get-ServerSideLinkRefusal`, which reads every
  component's attributes over the admin share (`Get-AppReparseInfo`, FindFirstFileW). For an
  `X$` share the function returns early, or is never reached, so no component is read.
  - The builder confirms the exact branch on the SQ-018 tip. This spec was written from
    SQ-017.md's revision notes, the run reports and the backlog, not from a checkout of the
    branch.
- **The fix.** Classify the target's resolved server path, after mapped-drive, DFS and final-path
  resolution, the same way `Get-TreeOwnershipRefusal` does: `^\\\\server\\[A-Za-z]\$\\rest` on
  the `ConvertTo-ComparablePath` form. For a match, skip NetShareGetInfo and pass the path
  straight to `Get-ServerSideLinkRefusal`.
  - Classify on the comparable form, never on the typed text (AC5).
  - A path that looks remote but cannot be parsed refuses, as AC52's normalisation already does.
    It must never return `$null` (destructive-operations checklist gap: a "does not apply"
    branch fails closed).
- **Ordering.** The D-036 text check and the high-impact check stay first (AC9). The bare
  `\\server\X$` and `\\server\X$\Windows` never reach a disk read.
- **Late re-check (AC7).** Find the AC53a re-check before takeown and make its server-side step
  take the same admin-share branch. Use one helper for "server path for this target" so the
  lookup and the re-check cannot drift.
- **Advice.** Keep `Get-ShareTreeRefusal`'s existing NetShareGetInfo-failure wording. The
  admin-share route it suggests is checked after this item, which is what the read-only-advisory
  gap ("refusal next steps must not send the tech to a route that skips the check") asks for.
  AC8 pins the round trip.
- **Patterns to follow.**
  - The AC52 tests in `FolderPermissionManager-AppChanges.Tests.ps1`: the same mocks and the same
    backstop for `Invoke-AclTool`/takeown.
  - `Initialize-BackgroundPool -FunctionOverride` for the pool-run lookup, because Pester mocks
    do not reach the pool (SQ-017 traps list).
  - Refusal wording from AC53c.
- **Proposed merge with SQ-023.** SQ-023 moves `Get-ShareTreeRefusal` and
  `Get-ServerSideLinkRefusal` into the core and calls them from
  `Get-TreeOwnershipTargetRefusal`. That is the same function and the same branch this item
  edits.
  - Built as one item, the admin-share branch is written once, in the core, and the CLI gets it
    too (a CLI user can type `\\fs01\D$\...` just as easily).
  - Built separately, SQ-021 changes the GUI copy and SQ-023 moves it, carrying these ACs over.
  - Either way works. The merge saves one round of review on the same lines.
- **Microsoft facts to cite** (root `CLAUDE.md`):
  - `<DriveLetter>$` is the root of that volume on the server, already cited in
    `Get-TreeOwnershipRefusal`
    (https://learn.microsoft.com/troubleshoot/windows-server/networking/remove-administrative-shares).
  - FILE_ATTRIBUTE_REPARSE_POINT
    (https://learn.microsoft.com/windows/win32/fileio/file-attribute-constants).
  - Reuse AC52's citations. No new Win32 API is introduced.

## Decisions
### Confirmed by the owner
- D-036: protected folders and drive roots, including `\\server\X$` and `\\server\X$\Windows`.
- D-040 / D-042: the reparse-point allowlist, for links inside a tree. AC52 deliberately ignores
  it for path components.
- D-045: detect server-side junctions for whole-tree changes on a remote share, and refuse when
  one is found or cannot be checked.
- Owner, 2026-10-19: the browser GUI is removed after the SQ-018 lab test, so no ACs cover it.
### Assumed by the squad
- **Run the check rather than change the advice** (the backlog offered either). D-045 covers
  "whole-tree changes on a remote share", and `\\server\D$` is a remote share whose server path
  is known from the text alone. Admins also type `D$` paths unprompted, so changing the advice
  alone would leave the hole open.
  - Evidence: D-045, and the read-only-advisory checklist gap in
    `squad/reports/2026-10-19-1813.md`.
- **The NetShareGetInfo-failure advice wording stays.** After this item the route it suggests is
  checked, and AC8 proves the round trip. Changing it would be a user-facing wording change with
  no safety gain.
- **AC52's "any reparse point, ignore the allowlist" rule applies unchanged on admin-share
  paths.** Reason: parity with ordinary shares. The SQ-018 assumption "AC52 refuses any reparse
  point on the server-side path, ignoring the D-040 allowlist" stands.
- **Only `<single letter>$` shares get the admin-share branch.** Other `$` shares are ordinary
  shares and go through NetShareGetInfo. Evidence: the `^([A-Za-z])\$$` rule in
  `Get-TreeOwnershipRefusal` (`FolderPermissions.Core.ps1`, around line 843).
- **AC7 parity.** If the late re-check does not repeat the server-side check for ordinary shares
  today, this item adds it for both. Reason: a re-check that re-resolves is a checklist item,
  and splitting the two routes would recreate the gap.
- **Branch code read from the record.** Function names (`Get-ShareTreeRefusal`,
  `Get-ServerSideLinkRefusal`, `Get-RemoteShareLocalPath`, `Get-AppReparseInfo`) come from the
  backlog, SQ-017.md and the 2026-10-19 run report. This spec was written without a checkout of
  `squad/SQ-018-fpm-wpf-changes`. The builder confirms the names and signatures on the merged
  tip before writing tests.

## Risk and safety notes
- **Destructive-operations, "Right target":** the item exists to close a canonicalisation gap
  (server-side junctions on SMB). Fail closed everywhere:
  - an unparseable remote path refuses;
  - an unreadable component refuses;
  - no `$null` "not applicable" branch for odd spellings (AC5).
- **Tests:**
  - backstop mocks of takeown and `Invoke-AclTool`;
  - no real share, no `$env:COMPUTERNAME`;
  - mocks for every machine-state read behind a seam, including pool overrides (the
    system-configuration gap from the same report).
- **Read-only-advisory, Advice:** the refusal's next step ("run the tool on the server itself, or
  ask a senior admin") does not point at any route that skips this check. On the server itself,
  the local final-path and link checks apply.
- **Known usability cost, inherited from D-045/AC52 and not changed here:** file servers that
  mount data volumes into folders (`D:\Mounts\Vol1`, a mount-point reparse point) are refused on
  every remote route, now including `D$`. The tech then has to run the tool on the server. If
  the lab test shows this is common, that is a separate owner decision (allowlisting mount
  points on path components). It is not part of this item.
