# SQ-020 · Whole-tree take ownership: app-execution aliases and Azure File Sync files are plain files (D-042)

- status: ready
- size: S
- risk: high (destructive-operations profile)
- touches: `FolderPermissionManager/FolderPermissions.Core.ps1` (the D-040 allowlist `$script:RedirectFreeReparseTags`), its tests, `FolderPermissionManager/README.md`.
- depends on: SQ-014 merged to main (the allowlist lives there). Branch from main after that merge.

## Summary (plain English)
Whole-tree take ownership refuses any tree that contains a reparse point outside the known-safe list (D-040). Two common types are refused today, though they don't redirect anywhere:
- the app-execution aliases in every profile's `AppData\Local\Microsoft\WindowsApps`;
- Azure File Sync files tiered to the cloud.

Michael chose to treat both as plain files (D-042).

## Acceptance criteria
1. AC1_AllowlistHasAppExecLinkAndStorageSync: `$script:RedirectFreeReparseTags` contains `IO_REPARSE_TAG_APPEXECLINK` = 0x8000001B and `IO_REPARSE_TAG_STORAGE_SYNC` = 0x8000001E, each with a learn.microsoft.com (MS-FSCC 2.1.2.1) citation on its line or the two above. The values are verified on Learn when built.
2. AC2_PinnedTableUpdated: the existing AC20d pin tests (exact names, all values) list the two new entries (24 total). This is the only change to those tests.
3. AC3_AppExecLinkTreeIsNotRefused and AC4_StorageSyncTreeIsNotRefused: a tree containing a reparse point with each tag, whose destination is faked as `\\dc01\NETLOGON`, is not refused because of it, on both the GUI and CLI paths.
4. AC5_OtherTagsStillLinks: DFS (0x8000000A), NFS and an unknown tag are still links (regression guard).
5. AC6_ReadmeNamesThem: the README's "Allowed" paragraph names WindowsApps aliases and Azure File Sync tiered files.

## Out of scope
Any other tag. Option C (refuse links leaving the tree) stays out (D-040).

## Assumed by the squad (run 2026-10-19)
- Lead ruling: the existing AC20c -ForEach row for IO_REPARSE_TAG_APPEXECLINK expected it to refuse the tree as a link, which contradicts D-042. Rather than deleting it, its tag was swapped to IO_REPARSE_TAG_WCI 0x80000018 (Windows Container Isolation, MS-FSCC 2.1.2.1; not allowlisted, not already in that -ForEach). The case's intent is kept: a non-allowlisted tag whose target can't be found refuses the tree. AC20c still has four rows (unknown, DFS, WCI, NFS). Spec auditor, code reviewer and destructive-operations reviewer judged it fair and not a weakening.
- AC2 also gained a count assertion (`$script:AllowedTags.Keys.Count | Should -Be 24`) inside AC20d_AllowlistExistsAsOneOrderedTableOfNameToValue. It tightens the test rather than weakening it.

## Review notes (all reviewers passed; minors for the owner or a later item)
- Record why the two tags can't redirect: neither 0x8000001B nor 0x8000001E has the name-surrogate bit (0x20000000), per https://learn.microsoft.com/windows/win32/fileio/reparse-point-tags. Add a comment next to the entries citing it, and mark the takeown/icacls behaviour claims NOT VERIFIED. The takeown and icacls pages say nothing about reparse points. (destructive-operations, minor)
- The core AC3/AC4 test fakes the destination as `\dc01\NETLOGON` (one backslash); the GUI and CLI tests use `\\dc01\NETLOGON`. The `Links.Count -eq 0` assertion still catches a regression, but the mock should be a real UNC path. (code, spec, destructive-operations; minor)
- README: "tiered files" could use a short gloss ("files whose content is kept in Azure and fetched when opened"), and the edit left a short line mid-paragraph. (UI, minor)
- Follow-up minors:
  - The PS 5.1 allowlist check only covers DEDUP/CLOUD_F/DFS, not the two new entries.
  - An app execution alias probably can't have its owner read by name (Get-Acl likely fails with 1920; not verified), so such items count as Unchecked in the read-back. Unchecked items are left out of the Done/Partly done/Failed decision; consider treating Unchecked > 0 as at most "Partly done".
- Lab test by hand: whole-tree take ownership of a real user profile (WindowsApps aliases) and of an Azure File Sync server endpoint with tiered files.
