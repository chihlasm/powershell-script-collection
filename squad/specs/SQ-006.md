# SQ-006 · Lockout tools recognize Kerberos encryption-type blocks (RC4 enforcement)

- status: ready
- size: M
- risk: medium
- touches: AD-LockoutDiagnostics (Diagnose-ADAccountLockout.ps1, LockoutReference.psd1, the
  status-code fallback copies in Export-ADAuthSourceEvidence.ps1 and Invoke-ADLockoutForensics.ps1,
  README), possibly Invoke-ADLockoutInvestigation.ps1 (SUMMARY.txt), see Q2

## Summary (plain English)
Since the 2026 Kerberos RC4 changes (KB5073381), some sign-in failures look like lockouts but
have nothing to do with the password: the domain controller refused the sign-in because the
account or the device can't use a modern encryption type. The per-account lockout check
(`Diagnose-ADAccountLockout.ps1`) will now look for that on every domain controller and say
"Not a password problem: encryption type blocked", with the next step: reset the password so
the account gets AES keys, or deal with a device that only speaks RC4. Where a domain
controller can't record this evidence, the report says "can't tell" for that DC instead of
"nothing found". The tool stays read-only.

## What users will be able to do
- A helpdesk tech runs the lockout workbench or `Diagnose-ADAccountLockout.ps1 -Identity jdoe`
  for "jdoe can't sign in / keeps locking". If the DCs refused Kerberos tickets for jdoe (or
  for a service jdoe is reaching) because of the encryption type, the report's headline says
  so in plain words, names the account or device, and gives one next step.
- If real lockouts and bad passwords are ALSO present, those stay the headline and the
  encryption-type block is listed as an additional finding, so a real stale-password problem
  is not hidden.
- A new "Encryption-type blocks" section in the report shows, per domain controller, whether
  each kind of evidence could be checked ("Checked" / "Can't tell" with the reason in plain
  English), followed by the matching events.
- A domain controller that is unreachable, unpatched (cannot log the 2026 KDC events), or not
  auditing Kerberos service-ticket failures is named with the reason. The report never says
  "no encryption-type blocks" for a DC it could not check.

## Acceptance criteria
Each maps to one Pester test named `AC<n>_...`, in
`AD-LockoutDiagnostics/Tests/EncryptionTypeBlocks.Tests.ps1` unless stated otherwise.
"Etype" below means Kerberos encryption type.

Reference data
1. AC1: Given `LockoutReference.psd1`, when it is loaded, then it has an `EncryptionTypeBlocks`
   section listing: Kerberos status `0xE` with its documented name (KDC_ERR_ETYPE_NOTSUPP);
   events 4768 and 4769 as the failure events; the KDCSVC error event IDs 203, 204, 208 and
   209, each with a non-empty `Who` (`Account`, `Client` or `Unknown`), `NextStep` and a
   `Reference` URL on `support.microsoft.com` or `learn.microsoft.com`; the KDC event provider
   name; and the audit subcategory GUID for Kerberos Service Ticket Operations.
2. AC2: Given `StatusCodes` in the psd1 now includes `0xE`, when `Get-StatusMeaning` is called
   with `0xE`, `0xe` and `0x0000000E` in Diagnose-ADAccountLockout.ps1, then all three return the
   psd1 meaning. (The existing `SharedReferenceParity.Tests.ps1` fallback tests must keep
   passing, so the fallback tables in Diagnose, Export and Forensics get the same `0xE` entry.)

Parsing (pure functions, synthetic event XML)
3. AC3: Given a synthetic 4769 event XML with `Status` `0xe`, when
   `ConvertFrom-EtypeFailureEvent` parses it, then it returns one row with Time, EventId 4769,
   Account (TargetUserName), Service (ServiceName), ClientAddress (an `::ffff:` prefix removed,
   same rule as `ConvertFrom-BadLogonEvent`), Status `0xE` and DC.
4. AC4: Given 4768/4769 XML with `Status` `0x0`, `0x18` or `0x12`, when parsed, then no etype
   row is returned (only `0xE` counts, in any letter case or zero padding).
5. AC5: Given a synthetic KDCSVC event 204 (System log, KDC provider), when
   `ConvertFrom-KdcsvcEvent` parses it, then the row carries EventId, Time, DC, every account
   name found in its EventData, and `Who`/`NextStep` taken from the psd1 entry for 204.
6. AC6: Given a KDCSVC event with an ID not in 203/204/208/209 (for example warning 201), when
   parsed, then it is not returned as a block.

Matching the investigated account
7. AC7: Given etype rows for `jdoe`, `CONTOSO\jdoe`, `jdoe@contoso.com`, a row whose Service is
   `jdoe`, and a row for `asmith`, when `Select-EtypeEvidenceForAccount -SamAccountName jdoe`
   runs, then the four jdoe rows are kept (case-insensitive) and the asmith row is dropped.

Per-DC gate
8. AC8: Given a DC that threw a non-"no events" error when queried, when `Get-EtypeGate`
   evaluates it, then both features (KDC events, 4768/4769 failures) are "Can't tell" with the
   reason "couldn't reach <DC>: <message>".
9. AC9: Given a reachable DC whose KDC provider metadata does not include event 203, when
   evaluated, then the KDC-events feature is "Can't tell" with a reason naming KB5073381 (the
   DC doesn't have the updates that write these events), and the 4768/4769 feature is
   evaluated on its own.
10. AC10: Given a reachable DC whose Kerberos Service Ticket Operations audit setting is
    `Success` only, `No Auditing`, or could not be read, when evaluated, then the 4768/4769
    feature is "Can't tell" with a plain reason for each case ("not logging failures" /
    "audit policy couldn't be read - needs admin rights on the DC").
11. AC11: Given a reachable, patched DC with failure auditing on, when evaluated, then both
    features are "Checked".

Verdict
12. AC12: Given no lockouts, no bad logons and one etype row for jdoe, when
    `Get-LockoutVerdict` runs, then the first finding starts with "Not a password problem:
    encryption type blocked" and names the account and the next step; no finding says "no
    on-prem lockout or bad-password events" without also stating the block.
13. AC13: Given KDCSVC evidence classified `Who = Account`, when the verdict is built, then the
    next step tells the tech to reset that account's password so it gets AES keys (wording per
    the psd1 entry); given evidence classified `Who = Client`, then the next step names the
    device/address and says it only offers RC4 and must be updated or replaced (exception
    wording per Q3).
14. AC14: Given lockouts and bad-password evidence AND etype rows, when the verdict is built,
    then the existing lockout headline stays first and the etype finding appears later in the
    list.
15. AC15: Given no etype rows and at least one DC with a "Can't tell" feature, when the verdict
    is built, then it includes one finding naming each such DC with its reason, and no finding
    claims encryption-type blocks were ruled out.
16. AC16: Given no etype rows and every DC "Checked", when the verdict is built, then the
    findings are identical to today's output for the same lockout/bad-logon input (a clean
    result stays quiet in the verdict).

Report
17. AC17: Given etype rows and gate rows, when `Write-LockoutReport` renders to `$TestDrive`,
    then the HTML has an "Encryption-type blocks" section with a per-DC table (DC, KDC events,
    4768/4769 failures, reason) and an evidence table; an account named `<script>x</script>`
    appears HTML-encoded.
18. AC18: Given etype rows but no lockouts and no bad logons, when the report renders, then the
    verdict block uses class `bad`, not `warn`.
19. AC19: Given all DCs "Checked" and no rows, when the report renders, then the section says
    "None found on the <n> domain controller(s) checked" (empty state); given a "Can't tell"
    DC, the section lists it first (gap before evidence).

Collection (Get-WinEvent, Invoke-Command mocked)
20. AC20: Given three DCs where the second throws "RPC server is unavailable", when
    `Get-EtypeEvidence` runs, then rows from DC1 and DC3 are returned and DC2's gate row is
    "Can't tell" (one DC never halts the sweep).
21. AC21: Given the mocked `Get-WinEvent`, when the 4768/4769 query runs, then the
    `-FilterHashtable` passed has `LogName = 'Security'`, `Id` 4768 and 4769, the
    audit-failure `Keywords` value and a `StartTime`, and no EventData XPath is used (guards
    the full-log-scan cost measured in Export-ADAuthSourceEvidence.ps1 .NOTES).
22. AC22: Given `Get-WinEvent` throws "No events were found that match the specified selection
    criteria", when collected, then the DC is treated as reachable with zero events, not "Can't
    tell".

Case summary (only if the owner picks Q2 option A)
23. AC23: Given an etype findings CSV in the case folder, when `New-CaseSummary` builds
    SUMMARY.txt, then an "ENCRYPTION-TYPE BLOCKS" block appears directly after FINDINGS with
    the sentence, the next step, and any "can't tell" DCs. Test lives in
    `Invoke-ADLockoutInvestigation.Tests.ps1`.

## Out of scope
- The domain-wide RC4 scan (all accounts, services and devices): parked per the pitch session.
- KDCSVC warning events 201/202/206/207 ("will break when enforced"), NTLM events 4020-4033,
  and NTLMv1 SSO (client-side, not visible from DCs).
- Reading or interpreting `msDS-SupportedEncryptionTypes`, `DefaultDomainSupportedEncTypes` or
  `RC4DefaultDisablementPhase`, and any date or patch-level logic ("enforced since April vs
  July"). The verdict rests only on events the DC actually wrote, which sidesteps Learn's
  out-of-date `0x0` row and KB5073381's inconsistent dates.
- Any change to an account or device. No remediation switches.
- Domain-wide survey runs (no `-Identity`), `Get-LockoutCause.ps1`, `Export-ADAuthSourceEvidence`
  collection, and the shared `AuditSubcategories` list / `Test-ADAuditPolicy.ps1` gate (left
  unchanged, see assumptions).
- AD-UserQuickCheck, unless the owner picks otherwise in Q1.
- The two Word guides (`AD Lockout Investigation - *.docx`): flagged for Michael to update.

## Approach
Follow the existing patterns in `Diagnose-ADAccountLockout.ps1`: pure parse/verdict functions
tested via `-LoadFunctionsOnly`, collection functions with a per-DC try/catch and `continue`,
`Write-Status` console prefixes, `Convert-Esc` for HTML, and `New-DataTable` for tables.

1. **Verify first (root CLAUDE.md).** Before coding, confirm on Learn / the KB and cite in
   comments and `.NOTES` REFERENCES:
   - 4769 and 4768 pages: `0xE` = KDC_ERR_ETYPE_NOTSUPP is a listed failure code; field names
     `TargetUserName`, `ServiceName`, `IpAddress`, `Status`; which subcategory logs each
     (4769 = Kerberos Service Ticket Operations, 4768 = Kerberos Authentication Service).
   - The Kerberos Service Ticket Operations GUID (auditing-constants page).
   - KB5073381: the KDC provider/source name and log (System), the meaning of 203/204/208/209,
     and for each one whose side needs fixing (the account's keys vs the client's supported
     types) and Microsoft's stated next step. Also any EventData field names.
   - The Audit Failure keyword value (`StandardEventKeywords.AuditFailure`, .NET docs on Learn).
   - That `Get-WinEvent -ListProvider -ComputerName` returns the provider's event IDs remotely
     on PS 3.0.
   If KB5073381 does not document an event's EventData fields or whose side it concerns, set
   `Who = 'Unknown'`, show the event message text, link the KB as the next step, and list the
   gap under "NOT VERIFIED" in `.NOTES` (the AD-UserQuickCheck precedent). Do not stop.
2. **LockoutReference.psd1:** add `0xE` to `StatusCodes`; add an `EncryptionTypeBlocks` hashtable
   (status code, events, KDC provider name, KDCSVC block events with `Who`/`NextStep`/
   `Reference`, KSTO GUID). Bump `VerifiedOn`. Add the same `0xE` line to the fallback tables in
   Diagnose, Export-ADAuthSourceEvidence and Invoke-ADLockoutForensics (parity test enforces it).
   Diagnose carries a fallback copy of `EncryptionTypeBlocks` only if the existing pattern needs
   it; if the psd1 is missing, the feature reports "Can't tell: LockoutReference.psd1 not found"
   rather than guessing.
3. **Diagnose-ADAccountLockout.ps1, new functions:** `ConvertFrom-EtypeFailureEvent`,
   `ConvertFrom-KdcsvcEvent`, `Select-EtypeEvidenceForAccount`, `Get-EtypeGate` (pure), and
   `Get-EtypeEvidence` (collection: per DC, (a) `Get-WinEvent -FilterHashtable` on Security for
   4768/4769 with the audit-failure keyword and StartTime, status filtered client-side;
   (b) System log for the KDC provider IDs 203/204/208/209; (c) provider metadata check for
   event 203; (d) Kerberos Service Ticket Operations audit setting via `Invoke-Command`
   `auditpol /get /subcategory:{GUID} /r`, parsed with `ConvertFrom-AuditPolCsv` and
   `Test-SubcategorySetting` by dot-sourcing `Test-ADAuditPolicy.ps1 -LoadFunctionsOnly` from
   beside the script; if that file is absent or the call fails, the feature is "Can't tell").
   Use the same `-DaysBack` window and DC list as `Get-BadLogonEvents`.
4. **Verdict:** extend `Get-LockoutVerdict` with `-EtypeEvidence` and `-EtypeGate` parameters
   (default empty so existing callers and tests are unchanged). Ranking per AC12-AC16.
5. **Report:** new `<h2>Encryption-type blocks</h2>` section after "Where the bad passwords came
   from"; gap table first, then evidence (raw rows behind `<details>`); `verdictClass` rule per
   AC18. Footer gains one sentence on where the evidence comes from.
6. **Q2 = A only:** Diagnose also writes `ADLockoutEtype_<sam>_<stamp>.csv` (only when there is
   a finding or a "can't tell"); `Invoke-ADLockoutInvestigation.ps1` reads it (recursive search,
   like the causes CSV) and passes it to `New-CaseSummary`; the layout map files it under
   `3 - Why This Account`.
7. **README:** a short subsection under Diagnose-ADAccountLockout ("Encryption-type blocks"),
   the extra event IDs in the Event ID Reference table, and the permission note (auditpol needs
   admin on the DC; otherwise that feature says "can't tell").
8. Keep `#Requires -Version 3.0`: no `::new()`, `.Where()`, `-NoNewline`; wrap filtered results
   in `@()` before `.Count`. Keep new text ASCII (no em dashes) so no BOM change is needed.

### Assumed by the squad
- **Home is Diagnose-ADAccountLockout.ps1, not Get-LockoutCause.ps1.** Get-LockoutCause ranks
  per *source device* from the AuthSources CSV, which holds 4625/4771/4776/4740 only; the
  etype evidence is per *account*, and Diagnose already sweeps every DC for this account.
- **Also read 4768 failures with 0xE, not only 4769.** Same filter and cost; a TGT refused for
  the user's own keys is the most direct "user can't sign in" case. Reversible; still must be
  confirmed on the 4768 Learn page (step 1).
- **Errors 203/204/208/209 only; warnings 201/202/206/207 excluded.** Matches the approved slice
  ("errors"); warnings describe future breakage, which belongs to the parked scan.
- **No date or patch-level logic.** Guidance on enforcement dates is inconsistent (card I-06);
  observed events are the only evidence used, so a confident wrong verdict from a date rule
  cannot happen.
- **KDC-events gate = provider metadata check, not a KB/build lookup.** Asking the DC whether
  its KDC provider defines event 203 detects the capability directly and works on any OS,
  including 2012/2012 R2 with or without ESU; a build-number table would be one more fact to
  keep current.
- **4768/4769 gate = auditpol for Kerberos Service Ticket Operations, reusing Test-ADAuditPolicy's
  parser by dot-sourcing it.** Avoids a third copy of the auditpol parser; the companion file
  ships in the same folder and zip (Build-LockoutToolkit). When unreadable (no admin, no
  WinRM), the feature says "can't tell", matching how the investigation gate treats a denied
  audit read. (4768's subcategory, Kerberos Authentication Service, is already gated by
  step 1.)
- **Shared `AuditSubcategories` and `Test-ADAuditPolicy.ps1` unchanged.** Adding a subcategory
  there ripples into the investigation gate, Forensics and three parity tests and changes the
  gate output for every case; the GUID lives in the new `EncryptionTypeBlocks` section instead.
- **System-field filter (Id + audit-failure Keywords + StartTime), status checked client-side.**
  Export-ADAuthSourceEvidence.ps1 .NOTES measured EventData XPath filters forcing full log
  scans (11-52 s per DC); 4769 is one of the busiest events on a DC.
- **Headline only when nothing else explains it (AC12/AC14).** "It suggests, it does not
  conclude" (Get-LockoutCause .DESCRIPTION); a real stale-password lockout must not be hidden.
- **Clean result stays quiet in the verdict, visible in the section (AC16/AC19).** The shared
  stylesheet's stated rule: "A clean result stays quiet".
- **Matching on client OR service account.** A user hitting an RC4-only service shows up with
  the service named; both are the tech's next step for this ticket.

## Risk and safety notes
- **personal-data profile applies** (`AD-LockoutDiagnostics/**`): the new data is account
  names, service names, client IPs and timestamps, all needed for the diagnosis. It stays in
  the existing case folder / `Reports\` (already gitignored), is HTML-encoded (AC17), and test
  fixtures are synthetic. No credentials are touched.
- **Read-only.** No writes to AD or DCs. `Invoke-Command` runs only `auditpol /get`.
- **Permissions:** reading the Security and System logs needs Event Log Readers (or admin) on
  each DC; auditpol needs admin over WinRM. Without them the feature degrades to "can't tell",
  never to "none found".
- **Shifting Microsoft guidance (medium risk):** every ID and meaning is cited; anything
  KB5073381 does not document is marked NOT VERIFIED and worded with a hedge.
- **Owner follow-ups not blocking the build:** try once on a patched test DC; update the two
  Word guides if the new report section should appear in them.
