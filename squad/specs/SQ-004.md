# SQ-004 · "Can this user open this folder?" access evidence

- status: ready
- size: L (proposed split into SQ-004a "evidence and hedged verdict", M, and SQ-004b "what to do about it", M)
- risk: medium
- touches: new tool folder `FolderAccess-Check/`, `ServiceDesk-Toolkit` (README row + build list),
  root `README.md` index, `.gitignore`; reads AD, file-server share security over CIM, and
  folder ACLs over SMB. No writes anywhere.

## Summary (plain English)
A tech types a user name and a network folder path. The tool works out which share permissions
and folder permissions apply to that user, through which of their groups (including nested
groups and the primary group), and whether anything denies them. It gives a careful answer,
PROBABLY YES, PROBABLY NO or CAN'T TELL with the reason, and never a bare YES. The tech is
always sent to Windows' Effective Access tab for the final word. The second part names the
smallest existing group that would grant the access and warns when that group is privileged. It
also spots when the user was added to a group after their last sign-in, so they need to sign out
and back in.

## What users will be able to do
- Run `.\Get-FolderAccessCheck.ps1 -Identity jdoe -Path '\\FS01\Finance\Budgets 2027'` from any
  domain-joined admin workstation with RSAT AD. The first line is the answer:
  `Can Jane Doe open \\FS01\Finance\Budgets 2027?  PROBABLY NO`, followed by the reason, what
  limits it (share permissions or folder permissions), and the next step. The last next step is
  always: "Confirm in the folder's Properties > Security > Advanced > Effective Access for jdoe."
- Below the verdict, sysadmins see the evidence:
  - the share entries and the folder entries, in the order Windows evaluates them;
  - for each entry, whether it matches the user and through which group path (for example
    `FIN-Staff -> FIN-All`, or `Domain Users (primary group) -> FS01\Users`);
  - every Deny that matches the user, marked "applies" or "overridden by an earlier allow".
- CAN'T TELL is a normal outcome. It always gives the reason and what to do instead. Reasons
  include:
  - your account can't read the folder's permissions;
  - the share permissions on FS01 couldn't be read (NAS, WinRM and DCOM both refused);
  - an administrative share path such as `D$`;
  - claims-based conditions on the folder;
  - a local group on the server whose members couldn't be read and that decides the answer;
  - an entry for an account from another domain that decides the answer.
- With `-OutputPath`, an HTML report and a CSV of the evidence rows are saved for the ticket.
- (SQ-004b) The tool says which existing group would grant the access, never Everyone,
  Authenticated Users, Domain Users, a local Users group or a direct per-user entry. It warns
  when that group is privileged elsewhere, and it flags "added to the group after their last
  sign-in: ask them to sign out and back in". It also writes the SQ-001 ticket note. When no
  group grants the access, it points to FolderPermissionManager, which logs the change after
  SQ-008, to add a group rather than the user.

## Acceptance criteria
Every test uses synthetic data (contoso.com, jdoe, made-up SIDs), FakeAD and mocks. The access
level tested is "open and list the folder" (Read) unless Q1 adds `-Access Modify`. See
Decisions.

### Part A: evidence and hedged verdict (SQ-004a)
1. AC1: Given `-Path 'S:\Budgets'` or `'C:\Data'` (not a UNC path), when the tool runs, then it
   prints "Enter the full network path, for example \\FS01\Finance\Budgets 2027", reads nothing
   remotely, and exits with code 2.
2. AC2: Given `\\FS01\Finance\Budgets 2027`, when the path is parsed, then the server is
   `FS01`, the share is `Finance` and the folder is the full UNC path; a share name with a
   trailing `$` that is an administrative share (`C$`, `D$`, `ADMIN$`) yields CAN'T TELL with
   "administrative share: run it again with the folder's real share path".
3. AC3: Given an identity that matches no user, or more than one, when the tool runs, then it
   lists the candidates (or says none matched), reads no share or folder data, and exits with code 2
   (same wording and behavior as AD-UserQuickCheck).
4. AC4 (primary-group regression): Given a user whose `memberOf` is empty and whose
   `primaryGroupID` is 513, a folder that allows Domain Users Read and a share that allows
   Everyone Read, when the tool runs, then the verdict is PROBABLY YES via
   "Domain Users (primary group)", and Domain Users appears exactly once in the user's group
   list. (A memberOf-only lookup would answer PROBABLY NO, and appending the primary group on
   top of a Get-ADGroupMember result would list it twice; both are past bugs.)
5. AC5: Given user -> FIN-Staff -> FIN-All and a folder entry allowing FIN-All Read, when the
   tool runs, then the verdict is PROBABLY YES and the matching entry shows the path
   `FIN-Staff -> FIN-All`.
6. AC6 (the card's example): Given a share allowing Authenticated Users Change and a folder
   with inheritance broken where only FIN-Managers has Modify, and a user in FIN-Staff only,
   when the tool runs, then the verdict is PROBABLY NO, "limited by: folder permissions", with
   the reason "no folder permission entry matches jdoe or their groups".
7. AC7: Given folder entries that allow the user Read but a share that allows only
   FIN-Managers, when the tool runs, then the verdict is PROBABLY NO, "limited by: share
   permissions".
8. AC8: Given an explicit folder Deny Read for FIN-Contractors, the user in FIN-Contractors, and
   an explicit Allow Read for Domain Users after it, when the tool runs, then the verdict is
   PROBABLY NO, and the Deny is named with the group path that matched.
9. AC9: Given an inherited Deny Read for FIN-Contractors and an explicit Allow Read for
   FIN-Staff, with the user in both, when the tool runs, then the verdict is PROBABLY YES, and the
   Deny is listed as "overridden by an earlier allow" (explicit entries are evaluated before
   inherited ones).
10. AC10: Given the only matching folder entry grants Traverse folder only, when the tool runs,
    then the verdict is PROBABLY NO with "jdoe's groups have an entry here, but it doesn't
    allow opening the folder".
11. AC11: Given inherit-only entries (CREATOR OWNER, "Subfolders and files only") that would
    otherwise grant the user, when the tool runs, then those entries are shown as "applies
    below this folder only" and are not counted toward the verdict.
12. AC12: Given a folder entry allowing `BUILTIN\Users` (S-1-5-32-545) Read, and the file
    server's local Users group containing Domain Users, and the user's primary group being
    Domain Users, when the tool runs, then the verdict is PROBABLY YES via
    "Domain Users (primary group) -> FS01\Users".
13. AC13: Given a folder entry for a server-local group whose membership cannot be read, and
    that entry decides the answer (it is the only Allow, or it is a Deny), when the tool runs,
    then the verdict is CAN'T TELL with the reason naming that group and server. When the
    answer is already PROBABLY YES through a domain group and the unreadable entry is an Allow,
    the verdict stays PROBABLY YES and the group is listed under "not checked".
14. AC14: Given `Get-Acl` on the folder throws access denied, when the tool runs, then the
    verdict is CAN'T TELL "your account can't read this folder's permissions", and neither
    PROBABLY YES nor PROBABLY NO is printed.
15. AC15: Given share security cannot be read (CIM over WSMan and over DCOM both fail) and the
    folder entries grant the user, when the tool runs, then the verdict is CAN'T TELL "couldn't
    read the share permissions on FS01" with both error messages in the evidence.
16. AC16: Given share security cannot be read and the folder entries do not grant the user,
    when the tool runs, then the verdict is PROBABLY NO, limited by folder permissions, with
    "share permissions: not read" listed under could-not-check.
17. AC17: Given the folder's SDDL contains a conditional (callback) ACE, when the tool runs,
    then the verdict is CAN'T TELL "this folder uses claims-based conditions; only Effective
    Access can evaluate them".
18. AC18: Given share security whose DACL is null, and separately one whose DACL is empty, when
    the share layer is evaluated, then each follows the semantics documented on Microsoft Learn
    (cited in the code). Expected: a null DACL grants everyone and an empty DACL grants no one.
    The builder confirms this before coding.
19. AC19: Given a folder entry whose SID cannot be resolved (orphaned or from another domain),
    when the tool runs, then the entry is listed as "not checked: unknown account <SID>". The
    verdict is CAN'T TELL only when that entry could change the answer: it is a Deny, or the
    verdict would otherwise be PROBABLY NO.
20. AC20: Given a SID in the user's `tokenGroups` that the upward memberOf walk did not reach,
    when an entry matches that SID, then it counts as a match, shown with the path "nested
    (path not traced)".
21. AC21: Given every fixture in the suite, when the verdict is produced, then the verdict text
    is exactly one of `PROBABLY YES`, `PROBABLY NO`, `CAN'T TELL` (never a bare `YES` or
    `NO`). The next steps always end with the Effective Access instruction naming the user.
22. AC22 (read-only): Given a full run against mocks, when it completes, then `Set-Acl`,
    `Add-ADGroupMember`, `Remove-ADGroupMember`, `Set-ADUser`, `Set-ADGroup`,
    `Set-CimInstance` and `New-Item` outside `-OutputPath` are never called. `Invoke-CimMethod`
    is called only with `GetSecurityDescriptor`.
23. AC23: Given `-OutputPath $TestDrive`, when the tool runs, then it writes
    `FolderAccessCheck_<sam>_<yyyy-MM-dd_HHmmss>.html` and `.csv`. The CSV has one row per
    evidence entry and is written with `-NoTypeInformation -Encoding UTF8`. A folder named
    `<script>alert(1)</script>` appears HTML-encoded in the HTML.
24. AC24: Given each outcome, when the tool exits, then the exit code is 0 for PROBABLY YES, 1
    for PROBABLY NO, 2 for bad input or a user not found or ambiguous, 3 for AD module or
    connectivity failure, and 4 for CAN'T TELL.
25. AC25: Given `Compatibility.Tests.ps1` in the new folder, when the suite runs, then the
    script declares `#Requires -Version 3.0` and uses no 4.0+/5.x feature. It also passes
    `Tests/PSVersionFloor.Tests.ps1` and `Tests/ScriptEncoding.Tests.ps1`.
26. AC26: Given the helper functions copied from Find-PrivilegedAccessPaths
    (`Get-PrivilegedGroupDefinition`, `Get-NameOnlyPrivilegedGroup`,
    `Find-PrivilegedGroupBySid`), when the parity test runs, then each is textually identical
    to the copy in `Find-PrivilegedAccessPaths.ps1`.
27. AC27 (depends on Q2, recommended option): Given a path whose server part is the AD
    domain's DNS or NetBIOS name (a domain-based DFS namespace), when the tool runs, then the
    share layer is CAN'T TELL with "this is a DFS path: run it again with the real server path
    (find it in the folder's Properties > DFS tab)". The folder entries are still read and
    shown, and AC16's rule applies.

### Part B: what to do about it (SQ-004b)
28. AC28: Given PROBABLY NO, a share allowing Authenticated Users Change, and folder entries
    granting Read to FIN-Managers (12 members) and FIN-All (80 members), when the tool runs,
    then the recommendation is "Narrowest existing group that grants this: FIN-Managers".
29. AC29: Given the only entries that would grant access are for Everyone, Authenticated Users,
    Domain Users, Domain Computers, BUILTIN\Users, INTERACTIVE/NETWORK, a server-local group, a
    user account, or the user themself, when the tool runs, then no group is recommended. The
    next step reads: "No existing group grants this. Ask who owns the folder which group should
    have access, then add that group (not the user) with FolderPermissionManager, which logs the
    change."
30. AC30: Given a candidate group that is denied at the folder or not allowed at the share
    layer (and the user's existing groups don't pass that layer either), when recommendations
    are ranked, then that candidate is skipped.
31. AC31: Given candidates FIN-Admins (5 members, nested in Domain Admins) and FIN-Managers (12
    members, not privileged), when the tool runs, then FIN-Managers is recommended. If FIN-Admins
    is the only candidate, it is named with "Warning: FIN-Admins is also in Domain Admins.
    Adding jdoe gives them domain admin rights. Get senior approval first."
32. AC32: Given a candidate group with `adminCount = 1`, when the tool runs, then it carries the
    privileged warning ("protected by AdminSDHolder").
33. AC33: Given the only granting path's newest link (from the replication metadata
    `FirstOriginatingCreateTime` of the member value) is later than the user's newest
    `lastLogon` across all DCs, when the tool runs, then the verdict reads "PROBABLY YES after
    jdoe signs out and back in", with the finding "added to FIN-Staff on <date>, after their last
    sign-in on <date>". The next step reads "Ask them to sign out of Windows and any Citrix/RDS
    session, then sign in again (locking and unlocking is not enough)".
34. AC34: Given one stale granting path and one non-stale granting path, when the tool runs,
    then no stale-token finding is shown.
35. AC35: Given the replication-metadata cmdlet is unavailable or throws, or no DC returns a
    `lastLogon`, when the tool runs, then "when jdoe was added to the group" is listed under
    could-not-check, and no stale-token claim is made.
36. AC36: Given SQ-001's `CaseKit.ps1` is present, when the tool runs with `-TicketNumber`,
    then a ticket note is written. A layer that was not read (CAN'T TELL reason, unreadable share
    or ACL) never appears under "Ruled out".

## Out of scope
- Re-implementing Windows access evaluation fully: no AuthzInitializeRemoteResourceManager, no
  P/Invoke, never a bare YES. Effective Access is the final word.
- Files inside the folder, subfolders, and parent-folder traversal. Bypass traverse checking is
  assumed, as it is granted to Everyone by default.
- Changing anything: no adding users to groups, no ACL edits, no launching FolderPermissionManager.
- Group removal that the user's token still holds (stale grant), integrity labels, ownership
  rights, offline files, ABE as a verdict reason (shown as a note only; see Decisions).
- Evaluating claims or central access policy: detected where visible and reported as CAN'T TELL.
- Users or ACEs from other forests or trusted domains beyond SID matching.
- DFS target resolution through the DFSN module (unless Q2 picks it).
- Long paths over 260 characters: reported as CAN'T TELL with the error.
- A GUI.

## Approach
- **New folder `FolderAccess-Check/`** containing `Get-FolderAccessCheck.ps1`, `README.md` and
  `Tests/` (`Get-FolderAccessCheck.Tests.ps1`, `Compatibility.Tests.ps1`, and `FakeAD/` copied
  and adapted from `AD-UserQuickCheck/Tests/FakeAD`). Naming mirrors
  `AD-UserQuickCheck/Get-ADUserQuickCheck.ps1`.
- **Script shape:** follow `AD-UserQuickCheck/Get-ADUserQuickCheck.ps1`:
  - `#Requires -Version 3.0` and runtime `Import-Module ActiveDirectory` in try/catch;
  - `[CmdletBinding(DefaultParameterSetName='Check')]` with `-LoadFunctionsOnly`;
  - `Write-Status` [PASS]/[WARN]/[FAIL]/[INFO];
  - pure assessment functions separated from collection;
  - `Invoke-*` returns a result object with `ExitCode` and never calls exit.

  Parameters: `-Identity` (pos 0), `-Path` (pos 1, UNC), `-Server`, `-Credential`, `-OutputPath`,
  `-MaxNestingDepth` (ValidateRange 1-50, default 10), `-LoadFunctionsOnly`. Part B adds
  `-TicketNumber` and `-PassThru` in whatever form the SQ-001 spec defines. Q1 may add `-Access`.
- **User resolution:** copy `Resolve-QuickCheckUser`, `ConvertTo-LdapFilterValue` and
  `Get-AdSplat` from AD-UserQuickCheck.
- **User's SID set:**
  - the user SID;
  - `tokenGroups`, a BASE-scope read done once, as in AD-UserQuickCheck lines 657-663;
  - the well-known SIDs every network logon carries (Everyone S-1-1-0, Authenticated Users
    S-1-5-11, NETWORK S-1-5-2, This Organization S-1-5-15), each verified on Learn and cited.

  Paths come from an upward memberOf walk adapted from `Get-UserGroupPath` in
  `Find-PrivilegedAccessPaths/Find-PrivilegedAccessPaths.ps1`, which already adds the primary
  group as its own starting point and is cycle-safe and breadth-first.
- **Share layer:** call `Win32_LogicalShareSecuritySetting` `GetSecurityDescriptor` through
  `Invoke-CimMethod` on a CIM session opened WSMan-first with a DCOM fallback. Copy the session
  pattern from `Citrix-FSLogix-HealthCollector/Get-CitrixFSLogixHealth.ps1` (around line 880).
  - Use one code path for 2008 R2 to 2025, with no SmbShare module needed on the tech's machine.
  - Read `Win32_ComputerSystem.DomainRole` on the same session to tell whether the file server
    is a DC, where BUILTIN groups are domain groups and already sit in `tokenGroups`.
  - Verify the class, the method, the `Win32_ACE` fields (`AceType`, `AccessMask`,
    `Trustee.SIDString`) and the null/empty DACL meaning on Learn.
- **Folder layer:** `Get-Acl -LiteralPath <UNC>`, as FolderPermissionManager reads ACLs, then
  walk the DACL in stored order from the SDDL/raw descriptor rather than the `.Access`
  collection. This is so the walk sees exactly what Windows sees, including conditional ACEs
  (`XA`/`XD`).
  - Skip inherit-only ACEs.
  - Map generic rights to file rights.
  - Walk the DACL the way Windows' access check does for the requested bits. A Deny for a bit not
    yet granted denies it; allows add bits until every requested bit is granted. Cite the Learn
    page on DACL evaluation order.
- **Local groups on the file server:** for each ACE that references a server-local or BUILTIN
  SID on a non-DC server, read that group's members over the same CIM session
  (`Win32_Group` / `Win32_GroupUser` associators, scoped to that group only). Then intersect
  with the user's SID set. One level only, because local groups cannot contain local groups.
- **Requested rights:**
  - Read = list folder / read data, read attributes, read extended attributes, read
    permissions, synchronize, on both layers.
  - Constants come from `FileSystemRights`, cited on Learn.
  - The share's "Read" mask is matched on the same bits.
- **Verdict function** (pure, fixture-tested): `Get-FolderAccessAssessment` takes the user SID
  set and paths, the share evidence (or its read error), the folder evidence (or its read
  error), local-group expansions and the path kind (normal/admin/DFS). It returns Verdict,
  LimitedBy, Reasons, CouldNotCheck, NextSteps and EvidenceRows. Gate rules:
  - Folder unreadable or conditional ACE: CAN'T TELL.
  - Folder NO: PROBABLY NO, whatever the share says.
  - Folder YES and share unreadable/DFS/admin: CAN'T TELL.
  - Both YES: PROBABLY YES.
  - Unresolvable entries make the verdict CAN'T TELL only when they could change it.
- **Privileged check (Part B):** copy `Get-PrivilegedGroupDefinition`,
  `Get-NameOnlyPrivilegedGroup` and `Find-PrivilegedGroupBySid` verbatim, with a parity test as
  in `Find-PrivilegedAccessPaths/Tests/PrivilegedAccess.Tests.ps1` line 135. A candidate is
  privileged if it, or any group it is nested in (walked upward), matches a definition, or if it
  has `adminCount = 1`.
- **Narrowest group (Part B):**
  - Candidates are domain security groups with an Allow at the folder layer that covers the
    requested bits, excluding the broad well-known SIDs and user objects. With the user added,
    a candidate must pass both layers with no Deny.
  - Rank non-privileged candidates first, then by member count (the `member` attribute, direct
    members), then by name.
- **Stale token (Part B):**
  - Use `Get-ADReplicationAttributeMetadata -ShowAllLinkedValues` on each group in the granting
    path, and the `member` value's `FirstOriginatingCreateTime`. For the primary group, use the
    user's `primaryGroupID` `LastOriginatingChangeTime`.
  - Compare the newest link with the newest `lastLogon` across DCs, reusing the per-DC snapshot
    pattern from AD-UserQuickCheck.
  - Verify the parameter names against the real cmdlet with `Get-Command` where RSAT is installed
    (SQUAD.md "Mocks can lie").
- **Output:**
  - Console verdict block first, then the evidence tables.
  - The HTML report uses the dark default; copy `ConvertTo-HtmlSafe` and encode every AD and
    path value.
  - The CSV holds the evidence rows: Layer, Order, Principal, SID, Type (Allow/Deny), Inherited,
    AppliesTo, Rights, MatchesUser, Via, Effect.
- **Packaging:**
  - Add a row to the `ServiceDesk-Toolkit/README.md` table ("I get 'Access denied' on a folder"
    / "Can this user open this folder?" -> FolderAccess-Check, Changes anything? No) plus a
    section.
  - Add an entry to the source list in `Build-ServiceDeskToolkit.ps1` (around line 70).
  - Add the tool to the root `README.md` index.
  - Add a `.gitignore` pattern `FolderAccess-Check/**/FolderAccessCheck_*` in the
    customer-data section.
- **REFERENCES in `.NOTES`:**
  - Win32_LogicalShareSecuritySetting, Win32_SecurityDescriptor and Win32_ACE;
  - Get-Acl;
  - FileSystemRights;
  - DACL evaluation order ("How DACLs control access to an object" and "Order of ACEs in a
    DACL");
  - generic rights mapping for files;
  - well-known SIDs;
  - tokenGroups and primaryGroupID;
  - Get-ADReplicationAttributeMetadata;
  - lastLogon;
  - the AppliesTo/inherit-only flags;
  - conditional ACEs (SDDL `XA`/`XD`).

## Decisions
### Confirmed by the owner
- D-004 split: this spec covers SQ-004 (evidence and hedged verdict, ACs 1-27) and SQ-013 (narrowest group, privileged warning, stale token, ticket note, ACs 28-36).
- D-018 -Access Read by default, Modify optional.
- D-019 domain-based DFS: share layer CAN'T TELL with "re-run with the real server path"; folder permissions still shown.
- None yet. Q1 (access level) and Q2 (DFS paths) are open, and so is the proposed split.

### Assumed by the squad
- **New folder `FolderAccess-Check` with `Get-FolderAccessCheck.ps1`, added to the
  ServiceDesk-Toolkit bundle as "Changes anything? No".** SQUAD.md says new service-desk tools
  go into the bundle, and the naming mirrors AD-UserQuickCheck. It is not added to
  FolderPermissionManager, which is a GUI that changes things, under the destructive risk profile.
- **PowerShell 3.0 floor, with one CIM path (WSMan then DCOM) to `Win32_LogicalShareSecuritySetting`
  for every server version, instead of `Get-SmbShareAccess` plus a fallback.** P-003 and
  SQUAD.md set the 3.0 default for read-only tools. One path means one set of tests and no
  SmbShare module dependency. The DCOM fallback pattern already exists in
  Citrix-FSLogix-HealthCollector.
- **NTFS read via `Get-Acl` over the UNC path, walking the DACL in stored order from the raw
  descriptor.** `.Access` hides conditional ACEs, and order decides Deny vs Allow (P-001).
- **The verdict follows Windows' DACL walk (an explicit Allow can beat an inherited Deny), not
  "any Deny means NO".** A naive rule would give a confident wrong PROBABLY NO (AC9, P-001).
  Every matching Deny is still shown, as the item asks.
- **Group paths come from the upward walk in `Get-UserGroupPath` (primary group as its own
  start), and matching comes from `tokenGroups`.** This reuses the fixed primary-group handling
  (SIGNALS 2026-10-14, Find-PrivilegedAccessPaths), and tokenGroups catches anything the walk
  misses (AC20).
- **The primary-group regression test (AC4) checks both past failure modes: missing (memberOf
  only) and double-counted.** The backlog asks for "a regression test for the past
  primary-group bug". `AD-GroupMembership-Export/Tests/PrimaryGroupMerge.Tests.ps1` is the
  precedent.
- **Server-local groups (BUILTIN\Users and the like) are expanded on the file server.** Default
  file-server ACLs grant BUILTIN\Users, so skipping them would make many answers wrong or CAN'T
  TELL.
- **CAN'T TELL gates:** unreadable folder ACL, unreadable share (when the folder says yes),
  admin share, conditional ACE, and an unresolved entry or local group that decides the answer.
  A folder-layer NO is reported as PROBABLY NO even when the share is unreadable, because access
  needs both layers. These are the card's "CAN'T TELL with the reason" rules made precise.
- **Access-based enumeration (ABE) is a note, not a CAN'T TELL reason.** ABE only hides items
  the user has no read access to, so it doesn't change the access answer (to verify and cite on
  Learn). Making it CAN'T TELL would hide a correct answer.
- **Central access policy is detected only when the SACL is readable (`Get-Acl -Audit` needs
  SeSecurityPrivilege). Otherwise "central access policy: not checked" is listed in the detail
  section, not the verdict.** Dynamic Access Control is rare at SMB clients, and the Effective
  Access next step covers it.
- **"Narrowest" means the fewest direct members (the `member` attribute), with non-privileged
  groups ranked first.** It's cheap and deterministic. Recursive counts on large groups are
  expensive on DCs. Ranking non-privileged first follows the card's "warn if privileged" intent
  without ever hiding the warning.
- **"Privileged elsewhere" means the group, or a group it is nested in, matches the
  well-known privileged SIDs used by Find-PrivilegedAccessPaths, or the group has
  `adminCount = 1`.** This reuses the existing tested definition, with a parity test (AC26).
- **Stale token means the granting path's newest link is newer than the user's newest
  `lastLogon` across all DCs. If either time is unknown, it's could-not-check, never a claim.**
  `lastLogon` is not replicated, so all DCs are read, as in AD-UserQuickCheck (CLAUDE.md

## Risk and safety notes
- **Personal data (`squad/risks/personal-data.md`):**
  - The tool reads group membership, folder names and paths.
  - Output stays under `-OutputPath`, and a `.gitignore` pattern is added in the same change.
  - The HTML encodes every value.
  - Fixtures use contoso.com and synthetic SIDs only.
  - No credential is ever written out. `-Credential` is passed to AD and CIM only.
- **Destructive operations:** not applicable. The tool is read-only, and AC22 proves that no
  write cmdlet runs. It must never call `Set-Acl` or group cmdlets. The recommendation text sends
  changes to ADUC (group membership) or FolderPermissionManager (logged after SQ-008).
- **Trust-breaker area (SIGNALS 2026-10-14, P-001):** the hedged wording, AC21's "no bare
  YES" test and the AC4 regression test exist so this tool can't repeat the access report's
  confident wrong answer.
- **Rights needed:** remote WMI/CIM on the file server needs admin rights there (techs normally
  run as domain admin per SQUAD.md). Without them the share layer is CAN'T TELL, never assumed.
- **Microsoft Learn verification before coding:** every constant listed in REFERENCES. In
  particular:
  - the null vs empty DACL meaning;
  - the well-known SIDs added to a network logon token;
  - the `Win32_ACE` AceType values;
  - the FileSystemRights bits;
  - the `Get-ADReplicationAttributeMetadata` parameter names and output fields.
