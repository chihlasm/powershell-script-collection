# SQ-030 · AD user check: re-enable and expiry steps note who approved it (D-050)

- status: ready
- feature: AD user check
- size: S
- risk: low
- touches: AD-UserQuickCheck (assessment strings in `Get-ADUserQuickCheck.ps1`, its README, its Pester suite)

## Summary (plain English)
When AD-UserQuickCheck finds an account that is turned off or has passed its end date, it tells
the tech to check with the manager and then turn it back on or extend it. The Microsoft 365 check
was tightened (D-050) to also say "note on the ticket who approved it"; the AD check still does
not, so the two tools give different advice for the same situation. This item makes the AD check
say the same thing. It also adds a test that reads every next step the tool can give and fails
if any of them turns something back on, removes or unblocks anything without the right approval
first.

## What users will be able to do
A helpdesk tech who runs `Get-ADUserQuickCheck.ps1` on a disabled or expired account sees a next
step (console, HTML report, ticket note) that tells them to check with the manager, write down on
the ticket who approved it, and only then enable the account or extend/clear its expiry date. The
README tells them the same. Everything else the tool says is unchanged (subject to Q2).

## Acceptance criteria
Tests are named `SQ030_AC<n>_...` because `Get-ADUserQuickCheck.Tests.ps1` already holds
`AC18`-`AC25` from SQ-001 (same idiom as SQ-019's `SQ019_AC<n>_`).

1. **SQ030_AC1_DisabledStepNotesApprover:** Given Facts with `Enabled = $false`, when
   `Get-QuickCheckAssessment` runs, then the `Disabled` reason's `Action` is exactly
   `Check with their manager that the account should be back in use, note on the ticket who approved it, then enable it (Enable-ADAccount or Active Directory Users and Computers).`
   - With Q1 = A, that string is followed by one space and exactly
     `This check does not look at security incidents or Microsoft Entra ID Protection: if this account was disabled during a security incident, escalate to the security lead instead.`
   - With Q1 = B, nothing follows it.
   Level stays `Blocker`, Message unchanged.
2. **SQ030_AC2_ExpiredStepNotesApprover:** Given Facts whose `AccountExpiry.Expired` is true, then
   the `AccountExpired` reason's `Action` is exactly
   `Check with their manager that they should still have access, note on the ticket who approved it, then extend or clear the account expiry date.`
   Level stays `Blocker`, Message unchanged. It carries no security-lead sentence under either Q1
   option.
3. **SQ030_AC3_EveryStepPassesChecker:** A scenario list of hand-built Facts, run through
   `Get-QuickCheckAssessment`, produces every reason code the function can emit: `Disabled`,
   `LockedOut` (all three unlock-time branches), `AccountExpired`, `AccountExpiresSoon`,
   `MustChangePassword`, `PasswordExpired`, `PasswordExpiresSoon`, `WorkstationRestriction`,
   `LogonHours`, `SmartCard`, `BadPasswords` (Info and Warning), `DcUnreachable`, `PdcFallback`,
   `ManyGroups`.
   - The test asserts the set of codes produced equals that list, so a new code added later
     without a scenario fails the test.
   - Every `Action` passes `Test-AdStepNeedsApproval` (see Approach).
   - So does every fixed Next-step line `ConvertTo-UserQuickCheckTicketNote` can add: NotFound,
     Ambiguous, could-not-read (Error), and the YES "No account problem found" line.
4. **SQ030_AC4_CheckerIsNotVacuous:** `Test-AdStepNeedsApproval` rejects each known-bad sample:
   - the old Disabled text (`Check with their manager that the account should be back in use, then enable it (Enable-ADAccount or Active Directory Users and Computers).`);
   - the old expiry text (`Ask their manager whether they should still have access. If so, extend or clear the account expiry date.`);
   - `Enable the account.`;
   - `Check with their manager, then enable it.` (manager phrase without the approver note);
   - `Clear the account expiry date.`;
   - `Remove them from the group.`;
   - `Unlock the account now.` (not the pinned step);
   - `Turn the account back on.`;
   - `Restore the deleted account.`
   It accepts the AC1 and AC2 texts.
5. **SQ030_AC5_RoutineStepsPinned:** (Q2 = A) The checker's exact-string exemption list holds
   exactly two literal strings: today's `LockedOut` Action and today's `PasswordExpired` Action.
   Each matches the reversal pattern only through `unlock` / `reset` respectively. So a new
   unlock or reset step cannot reuse the exemption. (Q2 = B: this AC becomes "the LockedOut and
   PasswordExpired Actions start with `Escalate`", and the list is empty.)
6. **SQ030_AC6_TicketNoteCarriesApprover:** Given the fake-AD scenario for a disabled account
   (`userAccountControl = 514`) and, separately, an expired account, when
   `ConvertTo-UserQuickCheckTicketNote` builds the note, then its Next step section contains
   `note on the ticket who approved it` exactly once, after `Check with their manager`.
7. **SQ030_AC7_ReadmeRowsMatch:** In `AD-UserQuickCheck/README.md`, the "What to do" cell
   (third column) of the "Account is turned off (disabled)" row and of the "Account expired" row
   each contain `Check with their manager` and then `note on the ticket who approved it`, both
   before the first `enable` / `Extend` / `clear`. With Q1 = A the disabled row also contains
   `security lead`.

## Out of scope
- M365-UserQuickCheck and its checker (already done in SQ-019/SQ-027).
- Reading Microsoft Entra ID Protection or any Graph data from AD-UserQuickCheck. The tool is
  on-premises AD only (its `.DESCRIPTION` and README "What it does not check"), has a 3.0 floor,
  and would need Microsoft.Graph (5.1). Q1 is about wording only.
- Any change to verdicts, reason levels, reason codes, which reasons fire, or exit codes.
- The `AccountExpiresSoon` Warning step ("ask their manager to request an extension before
  then"): it changes nothing itself and does not reach the ticket note's Next step.
- Other README rows, and prose outside the reason table (for example "It never unlocks, resets
  or changes anything").
- `dist/` bundles: regenerated by `ServiceDesk-Toolkit/Build-ServiceDeskToolkit.ps1`, never edited.

## Approach
- **`AD-UserQuickCheck/Get-ADUserQuickCheck.ps1`**, `Get-QuickCheckAssessment`, strings only:
  - line 422 (`Disabled` Action) becomes the AC1 text;
  - line 442 (`AccountExpired` Action) becomes the AC2 text;
  - with Q2 = B, lines 435 and 456 gain a leading escalation; with Q2 = A they are untouched.
  - Keep every string ASCII with straight quotes, so encoding and the BOM rule are unaffected
    (`Tests/ScriptEncoding.Tests.ps1`). No new syntax, so the 3.0 floor holds
    (`Tests/PSVersionFloor.Tests.ps1`, `AD-UserQuickCheck/Tests/Compatibility.Tests.ps1`).
  - No Microsoft fact changes, so no new REFERENCES entry.
- **`AD-UserQuickCheck/README.md`**, reason table:
  - line 56 "What to do" becomes: `Check with their manager that it should be back in use, note on the ticket who approved it, then enable it.` plus, with Q1 = A, ` If it was disabled during a security incident, escalate to the security lead instead.`
  - line 58 becomes: `Check with their manager that they should still have access, note on the ticket who approved it, then extend or clear the date.`
- **`AD-UserQuickCheck/Tests/Get-ADUserQuickCheck.Tests.ps1`**: add a `Describe 'SQ-030 next steps need approval'`.
  - Define `Test-AdStepNeedsApproval` in its `BeforeAll`, modelled on SQ-019's
    `Test-M365StepNeedsApproval` (`M365-UserQuickCheck/Tests/M365UserCheck.Core.Tests.ps1:122-152`)
    but self-contained in this tool's suite (folders stay self-contained).
  - Its verb list is the read-only-advisory profile's wide list: `\b(remov\w*|delet\w*|clear\w*|undo\w*|unblock\w*|re-?enable\w*|enable|reset\w*|unlock\w*|restor\w*|take ownership|turn\w* back on|free up space|clean\w* up|change it)\b`, case-insensitive.
  - Escalation phrases: `Escalate`, `Check with the senior engineer`, `Ask the senior engineer`,
    `involve the security lead`, `escalate to the security lead`.
  - Rule: a step with no match passes. A step on the exact-string exemption list (AC5) passes.
    A step whose only matches are `enable` / `re-enable` / `unblock` / `clear` (the last only as
    part of `clear the account expiry date`) passes when `Check with their manager` and
    `note on the ticket who approved` both appear before the first match (D-050). Anything else
    passes only when an escalation phrase appears before the first match.
  - Scenarios for AC3 are built as Facts objects passed straight to `Get-QuickCheckAssessment`
    (pure function, no AD), using the Facts shape from `Get-QuickCheckFacts` (lines 750-767).
    AC6 uses the existing FakeAD `Set-Scenario` pattern (as in the 'disabled -> NO' test).
  - AC7 parses the README reason table by splitting rows on `|` (three columns).
- Pattern to match: M365-UserQuickCheck's D-050 strings (`M365UserCheck.Core.ps1:718`, `:780`,
  `:880`): "Check with their manager that the account should be back in use, note on the ticket
  who approved it, then ...". D-059's caution shape (`M365UserCheck.Core.ps1:219`) for Q1 = A.

## Test plan
- Pester 5 under `pwsh`. Pure assessment tests (AC1-AC5) call `Get-QuickCheckAssessment` with
  hand-built Facts. AC6 uses the existing fake ActiveDirectory module (`Tests/FakeAD`) and
  `-LoadFunctionsOnly`; no real AD, no clipboard (the note builder is called directly, not the
  entry script). AC7 reads the README from the repo.
- Narrow run: `pwsh -NoProfile -File Tests\Invoke-AllTests.ps1 -Path .\AD-UserQuickCheck\Tests`.
  Then both gates: `Tests\Test-ScriptParse.ps1` under `powershell.exe`, and the full
  `Invoke-AllTests.ps1`.
- Edge cases: the three LockedOut branches (unlock time in future / past / duration 0) all
  give the same Action and are all scanned; `Enable-ADAccount` in the Disabled step matches
  `enable` after the approver note (passes); "enabled" in other text does not match `enable\b`;
  the Q1 = A caution contains `escalate` after `enable` and must not break the D-050 rule;
  BadPasswords at both levels; the checker's own negatives (AC4).
- Existing tests that must still pass unchanged: 'disabled -> NO, exit 1' (Action non-empty),
  'account already expired -> NO', `AC18_UserCheckNoteFindings` (pins the PasswordExpired step
  `Reset their password (Set-ADAccountPassword)`: if Q2 = B this assertion changes with it).

What the tests cannot see:
- How a tech reads the new step on a real call: whether "note on the ticket who approved it" is
  followed in practice. Only the owner/team can judge.
- The console and HTML rendering of the longer Disabled step on a real screen (text only, no
  layout change, low risk).
- This is a console tool with no window or start-up path of its own, so the smoke check
  (`smokeCommand`) does not cover it. A real run against a test domain is the owner's to try:
  `.\Get-ADUserQuickCheck.ps1 -Identity <a disabled test user> -NoClipboard`.
- The ServiceDesk-Toolkit bundle in `dist/` keeps the old wording until it is rebuilt.

## Decisions
### Confirmed by the owner
- D-050: re-enabling a plain disabled/blocked account needs the manager check plus "note on the
  ticket who approved it"; deliberate blocks (marker, risky user) still say Escalate. Names
  AD-UserQuickCheck as the follow-up.
- D-060: this approver note for AD-UserQuickCheck is its own item (this one), feature AD user check.
- D-059: the "could not be checked" security-lead caution on manager-path unblock steps. It lists
  SQ-030 under "Applies to", but the backlog text says "only if this tool reads ID Protection",
  and it does not: raised as Q1.
- D-017 / P-004: destructive or reversing steps say Escalate.
- D-066 (2026-11-11): Q1 = A. The D-059-style caution goes on the Disabled step only (wording in D-066). Squad call: unlock and password-reset steps stay plain tier-1 steps, exempted in the checker by exact string (Q2 = A, same precedent as SQ-019).

### Assumed by the squad
- **AD-UserQuickCheck has no "deliberate block" reason to keep on Escalate.** It reads only
  on-premises AD (`Get-QuickCheckFacts`, lines 635-639). The M365-SyncedUserFixes block marker
  (`msDS-cloudExtensionAttribute10 = BlockCloudSignIn`) blocks Microsoft 365 sign-in only
  (`M365-SyncedUserFixes/README.md:72`) and does not stop AD sign-in, so it is not in this
  tool's scope. A disabled AD account is the D-050 "plain disabled" case, exactly as the M365
  tool already treats an AD-disabled account (`M365UserCheck.Core.ps1:718`). "Keep deliberate
  blocks on Escalate" is satisfied by the checker: any step that undoes something other than a
  plain enable/expiry must carry an escalation.
- **The expiry step uses the same D-050 path as re-enabling.** The backlog asks for it, and an
  expired account is a plain block set by date, not a security block. Its wording changes from
  "Ask their manager whether ... If so," to "Check with their manager that ..." to match the
  M365 phrasing exactly, so one checker phrase covers both tools.
- **"clear" is allowed under the manager rule only as "clear the account expiry date".**
  Clearing the date means "never expires" (`accountExpires` 0 / 0x7FFFFFFFFFFFFFFF, already
  cited in `.NOTES`). It is a re-enable, not a delete. Any other "clear" still needs an escalation.
- **The checker lives in this tool's test file**, not shared with M365-UserQuickCheck: folders
  stay self-contained (SQUAD.md), and the AD list of steps is different (unlock, reset).
- **The checker uses the profile's wide verb list** (unlock, restore, take ownership, turn back
  on, free up space, clean up), which SQ-019 left as a follow-up for the M365 checker. Here it
  costs nothing, because no AD step uses those words except the two routine steps in Q2.
- **README is checked for its two changed rows only**, not a full checker scan of every cell:
  the README's "Unlock it." and "Reset it" cells are shortened forms that the exact-string
  exemption cannot match, and the tool output (AC3) is the authority.
- **The Q1 = A caution goes on the Disabled step only.** Accounts are disabled, not expired,
  during a security incident, and the expiry step stays one sentence.

## Risk and safety notes
- **Read-only-advisory profile applies.** This item is that profile's Advice rule made testable
  for AD-UserQuickCheck: every reason code and action string enumerated, the wide verb list, the
  step that reaches the ticket note (Blocker) carries the approval itself (AC6).
- **Profile tension, raised as Q2.** The profile's verb list includes "unlock" and "reset", and
  says steps that undo a deliberate block (including "lockout policy") say Escalate. The tool's
  LockedOut step ("Unlock it (Unlock-ADAccount)...") and PasswordExpired step ("Reset their
  password (Set-ADAccountPassword)...") are plain tier-1 instructions today. SQ-019 exempted the
  M365 password steps by exact string as routine tier-1 work; the same is recommended here, but
  a reviewer applying the profile literally could flag the unlock step as a major and stop the
  build, so it is asked now.
- **Risky-user rule, raised as Q1.** The profile says a risky or compromised user always
  escalates to the security lead before any re-enable. This tool cannot see ID Protection, so it
  cannot know; Q1 decides whether the step says so.
- No code path, read, write or module change; the static read-only guarantees are untouched.
- Personal data: no new fields in the ticket note or CSV.
- **Pre-mortem: what could stop the build?**
  1. Q1 unanswered: AC1 and AC7 have two forms. Asked now.
  2. Q2 unanswered: AC5, and whether lines 435/456 and `AC18` change. Asked now.
  3. An existing test pins the old text: checked, none pins the Disabled or AccountExpired
     Action strings; `AC18` pins the PasswordExpired step (only matters under Q2 = B).
  4. A reason code the scenario list misses: AC3 asserts set equality against the 14 codes
     found by reading `Get-QuickCheckAssessment` (lines 419-517).
