# SQ-024 · FolderPermissionManager: a typed `..` in a share path makes the checks look at a different folder

- status: ready
- size: M
- risk: high (destructive-operations profile, "Right target, right object")
- touches: `FolderPermissionManager/FolderPermissions.Core.ps1` (one new text-only helper),
  `FolderPermissionManager/FolderPermissionManager-GUI.ps1` (Get-ChangeTarget,
  Resolve-ChangeTargetSet, Get-ShareTreeRefusal, Get-ServerSideLinkRefusal, Open-TypedPath),
  `FolderPermissionManager/FolderPermissionManager.ps1` (CLI `-Path`), their tests,
  `FolderPermissionManager/README.md`.
- depends-on: SQ-018 (the WPF change code lives only on `squad/SQ-018-fpm-wpf-changes` until it
  merges; branch from main after that merge).
- found-in: SQ-018 (destructive-operations re-review of fix round 1, major).

## Summary (plain English)
If a tech types a path with `..` in it, for example `\\fs01\AppShare\..\..\..\Data`, the safety
checks and the actual change can end up looking at two different folders. Windows never lets
`..` climb above the share, so the change lands inside the share's own folder (on the server
that can be `C:\ProgramData\App\Share\Data`, a protected place). The checks work the path out
differently and inspect `C:\Data` on the server instead, which looks harmless. After this
item, the tool refuses any typed path that has a `.` or `..` folder name in it, with a plain
message telling the tech to type the folder's full path. This applies in the window (the
"Go to" box, every change, and Copy permissions targets) and in the command-line script.

## What users will be able to do
- When a tech types or pastes a path with a `.` or `..` folder name in the window, as a target
  for any change or in the Copy permissions box, the change is refused before anything is
  looked up, asked or changed. The message names the path and says what to do: "`<path>` has a
  folder name made only of dots ('.' or '..') in it. Windows does not read those the way this
  tool checks them ('..' never goes above the share or the drive), so the tool cannot be sure
  which folder this is. Type the folder's full path without them, for example D:\Shares\HR or
  \\fs01\Data\HR. Nothing was changed."
- Typing such a path in the "Go to" box does not open it. The status line says why, and the
  tree stays as it was (owner question Q1; default is the recommended option).
- On the command line, `-Path 'D:\Shares\..\Windows'` or `-Path '\\fs01\AppShare\..\Data'`
  stops with `[FAIL]` and that message, exit code 1, before anything is counted, asked or saved.
  `-AllowSystemFolder` and `-Force` do not get past it. Relative paths still work as before
  (`.\HR`, `..\HR`): they are resolved against the PowerShell location into a full path first.
- Everything else works as before. Ordinary names that only contain dots (`.hidden`, `HR.v2`,
  `a..b`) are not affected.

## Out of scope
- Normalising or correcting the typed path, or suggesting the "real" one in the message
  (decided against, see Decisions).
- Changing `ConvertTo-ComparablePath` or any D-036 / high-impact text check. Their own tests
  (`AC16d_*` in `FolderPermissions.Tree.Tests.ps1`, including `System32\..\System32` and
  `Windows.\System32`) stay as they are.
- Segments that end in a dot or space but are not made only of dots (`Data.`, `a..`, `x `).
  `ConvertTo-ComparablePath` trims every trailing dot and space from every segment, but Windows
  removes only a single trailing period mid-path and trims all trailing dots and spaces at the
  end of the path. That is a smaller mismatch of the same kind, and it is proposed as a
  follow-up (see Risk notes), not built here.
- Moving the share and server-side checks into the core (SQ-023), the admin-share advice
  (SQ-021), and the copy refusals in the core (SQ-022).
- `FolderPermissionManager-WebGUI.ps1`: the owner removes it after the SQ-018 lab test
  (2026-10-19). No ACs for it.
- Reading or viewing (the permission panes): nothing there changes anything.

## Approach
1. **Core helper (PowerShell 3.0 safe)** in `FolderPermissions.Core.ps1`, next to
   `ConvertTo-ComparablePath`: `Get-DotSegmentRefusal -Path` returns the dot-segment text or
   `$null`. A segment is a dot segment when, after splitting on `\` and `/` and skipping empty
   segments (a trailing or doubled separator), it consists only of `.` characters (one or more).
   The `\\?\` / `\\.\` prefix's `?` / `.` segment is the device prefix: skip the first segment
   after a leading `\\?\` or `\\.\` (the GUI refuses device paths anyway; the CLI then still
   catches `\\?\C:\Data\..\Windows`). No `::new()`, no `.Where()`; `@()` around anything counted.
   Comment block cites the Learn page (see Risk notes) and states why the tool refuses instead of
   normalising. Core functions reach the WPF pool automatically (`Get-CoreFunctionNames`), so no
   `$script:WorkHelperFunctions` edit is needed for it.
2. **Get-ChangeTarget** (GUI): right after the "not a full path" check and before the stream
   check, `Get-DotSegmentRefusal -Path $display`; when it refuses, return
   `& $refuse $text $display $false`. This is before `Resolve-MappedDrive`,
   `Test-ThisComputerName`, DFS and the share lookup, so nothing is resolved from a dot path.
   Add the rule to the function's comment-based help ("Refused: ... a path with a '.' or '..'
   folder name").
3. **Resolve-ChangeTargetSet**: in the file-prefix branch, next to the `':'` check on `$rest`,
   refuse with `Get-DotSegmentRefusal -Path $p` when it returns text.
4. **Get-ShareTreeRefusal**: before building `$serverPath`, refuse (return the dot-segment text
   for `-Path`) when `-Rest` has a dot segment, so the function is safe on its own when SQ-023
   moves it to the core. Change the comment above `ConvertTo-ComparablePath -Path $serverPath`:
   that call now only folds a trailing or doubled `\`.
5. **Get-ServerSideLinkRefusal**: refuse a `-ServerPath` that has a dot segment before
   `ConvertTo-ComparablePath` (fail closed, same `$next` tail). Fix the comment that says
   "`.` or `..` segments do not skip the check": it must say they are refused, because Windows
   stops `..` at `\\server\share` on the client while the server path would climb above the
   share's folder.
6. **Open-TypedPath** (Q1, recommended option): after the trim, when `Get-DotSegmentRefusal`
   refuses, `Set-Status -Kind Warning` with "`<path>` has a folder name made only of dots ('.' or
   '..') in it, so it was not opened. Type the folder's full path without them, or browse to it."
   and return without touching the tree.
7. **CLI** (`Invoke-FolderPermissionCli`): before `Resolve-AclTargetPath`, when the trimmed
   `-Path` is rooted (`[System.IO.Path]::IsPathRooted`) and `Get-DotSegmentRefusal` refuses,
   print `[FAIL] <text>` (no `Get-CliRefusalNextStep`: the next step is in the text) and return 1.
   After `Resolve-AclTargetPath`, check the resolved path again: a relative input that still
   resolves to a path with a dot segment is refused the same way. If
   `GetUnresolvedProviderPathFromPSPath` turns out not to collapse `..\HR` (AC11 shows it), make
   `Resolve-AclTargetPath` collapse relative input with `[System.IO.Path]::GetFullPath` (the
   documented Win32 normalisation) rather than refusing it; do not change how rooted input is
   resolved. Both checks run before the `Test-Path` existence check, so the tech sees the
   dot-segment reason, and before `-AllowSystemFolder` is considered.
8. **Docs**: README "what is refused" list and the CLI `.PARAMETER Path` help; `.NOTES`
   REFERENCES in the core and the CLI gain the file-path-formats page.
9. Existing patterns to follow: `Test-UncSharePath` (GUI) already refuses `.`/`..` segments in a
   drive map value rather than normalising them (SQ-017 fix rounds); refusals follow the
   `& $refuse` / `New-ChangeTarget -Ok $false` shape; CLI refusals print `[FAIL] ... Nothing was
   changed.` and return 1 (the D-036 branch).

### Assumed by the squad
- **Refuse, do not normalise.** Technical choice delegated to the squad by the planner. Reasons:
  (1) fail closed is the destructive-operations rule ("a guard that cannot resolve the path fails
  closed"); (2) normalising correctly needs a second copy of Windows' rules, and there are at least
  three places where a copy would disagree: `..` stops at `\\server\share` for a UNC path but at
  `H:\` for a mapped drive (Windows normalises `H:\..\Data` to `H:\Data`, while mapping first gives
  `\\fs01\Data\Dept\..\Data`, which climbs to `\\fs01\Data\Data`); `...` is a real folder name to
  Windows but `ConvertTo-ComparablePath` drops it; and the server-side mapping builds a path on a
  different root (`\\server\X$`); (3) the same tool already refuses `.`/`..` in drive map values
  (`Test-UncSharePath`); (4) a typed `..` in an admin path is almost never deliberate, and the fix
  for the tech is to type the full path.
- **Dot-only segments, including `...`.** Windows treats `...` as a valid name, but
  `ConvertTo-ComparablePath` trims it away, so it causes the same check/target mismatch. Refusing
  it costs nothing in practice. Names that merely contain dots are allowed.
- **Every entry point.** Every WPF change (add, remove, take ownership of a folder, its files or the
  whole tree, Copy source and targets, and SQ-025's Change Permission when it lands) goes through
  `Get-ChangeTarget` / `Resolve-ChangeTargetSet`, so one check there covers them all. Local and
  mapped-drive paths are refused too, for one rule the tech can learn, even though a local `..` is
  handled consistently today.
- **The CLI keeps relative input.** `.\HR` is documented in `-Path` help and pinned by an existing
  test (`FolderPermissionManager.Cli.Tests.ps1`, `-Path ('.\' + ... + '\')`); `..\HR` is the same
  kind of input, resolved against the PowerShell location by `Resolve-AclTargetPath`. Only rooted
  input with dot segments, or a resolved path that still has one, is refused.
- **`-AllowSystemFolder` does not bypass it.** That switch overrides D-036 (protected folders); the
  dot rule is about not knowing which folder is meant, so no override exists.
- **Defence in depth in `Get-ShareTreeRefusal` and `Get-ServerSideLinkRefusal`**, so the functions
  stay safe on their own once SQ-023 moves them to the core and calls them from the CLI path.
- **The helper lives in the core**, because the CLI (3.0) and the GUI both need it and SQ-023 will
  call it from `Get-TreeOwnershipTargetRefusal`.
- **Message wording** is the squad's proposal (shown in full above). It follows the tool's style:
  it names the path, says why in plain words, gives an example, and ends "Nothing was changed."

## Risk and safety notes
- Destructive-operations profile, "Right target, right object": "Paths are canonicalised before any
  protected-path or scope check ... and a guard that cannot resolve the path fails closed." Today the
  check and the action use two different canonical forms. This item makes the action's target and
  the checked path the same by refusing the inputs where they can differ.
- No new write path. The change only adds refusals before existing lookups. Backstop mocks of
  icacls, takeown and Set-Acl stay in place in every suite touched.
- **Microsoft Learn verification (must be done by the builder before coding).** This planning
  session had no web or Learn tool, so the following is recalled, not fetched. The builder must
  fetch https://learn.microsoft.com/dotnet/standard/io/file-path-formats, quote it verbatim next to
  `Get-DotSegmentRefusal`, and add it to `.NOTES` REFERENCES in the core and the CLI. The sections
  that matter, under "Path normalization":
  - "Evaluate relative components": a single-period segment is removed, a double-period segment
    removes itself and its parent, "Parent directories are only removed if they aren't past the
    root of the path", and the root is "the drive (`C:\`) for DOS paths, the server/share for UNCs
    (`\\Server\Share`)". This is the `\\server\share` stop, and the `H:\` stop for a mapped drive.
  - "Trim characters": "A segment of three or more periods is not normalized and is actually a
    valid file/directory name" (the `...` case), and only a single trailing period is removed from
    a segment mid-path.
  - "Skip normalization": `\\?\` paths are passed through without normalisation.
  If the page says anything different, stop and flag it. Do not adjust the ACs silently.
- Pre-mortem: what could stop the build and leave it waiting for the owner?
  - Q1 (Go box) is the only user-facing choice not decided by the backlog text. It is asked now,
    and the spec defaults to the recommended option.
  - `GetUnresolvedProviderPathFromPSPath` may not collapse `..` in relative input. Approach step 7
    already says what to do (collapse relative input with `GetFullPath`), so this needs no owner.
  - An existing test that feeds a dot path through `Get-ChangeTarget` or the CLI and expects
    acceptance. None was found (searched the SQ-017/SQ-018 diffs and the main-branch tests). The
    `Get-InstanceMutexName` test with `Other\..\Logs` is about `-LogFolder`, which this item does
    not touch.
  - Merge order with SQ-021 and SQ-023, which edit the same two functions: see the proposed
    sequencing below. It is a planning note, not an owner question.
- Proposed sequencing (no merge): build SQ-024 before SQ-023 and SQ-021. SQ-023 then moves the
  already-fixed `Get-ShareTreeRefusal` and `Get-ServerSideLinkRefusal` into the core and should
  call `Get-DotSegmentRefusal` at the top of `Get-TreeOwnershipTargetRefusal`. SQ-022 does not
  conflict (Copy targets are covered here through `Get-ChangeTarget`).
- Follow-up candidate (not built): segments that end in a dot or space (`Data.`, `a..`) are
  trimmed differently by `ConvertTo-ComparablePath` and by Windows. That is a narrower mismatch of
  the same kind. `Test-UncSharePath`'s rule ("a name ending in . or space is refused") could be
  applied to typed change targets too.
