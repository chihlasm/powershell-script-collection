# SQ-009 · LocalAdminManager: log every add and remove

- status: ready
- size: M
- risk: high
- touches: LocalAdminManager/LocalAdminManager.ps1, LocalAdminManager/README.md,
  LocalAdminManager/Tests (new), root README.md (LocalAdminManager section), .gitignore

## Summary (plain English)
LocalAdminManager adds or removes a person or group from a computer's local Administrators
group, but it keeps no record. After this change, every add or remove is written to a daily
change-log CSV: who ran it, when, from which machine, on which computer, and the full member
list before and after. That makes every change provable and reversible.

While checking the code, the squad found that the tool cannot work today: it passes
`-ComputerName` to `Add-LocalGroupMember`/`Remove-LocalGroupMember`, and those cmdlets have no
such parameter. Every run, local or remote, ends in "Failed to add ...". The tool caught the
error and still said "Operation completed." The before/after lists need a working way to read the
group on the target, so this item also fixes how the tool reaches the target computer
(owner question Q1).

## What users will be able to do
- Run `LocalAdminManager.ps1 -Action Add|Remove -Member DOMAIN\Name [-ComputerName PC01]` and
  have the change actually happen, locally or on a remote computer.
- See the scope before anything changes: `[WARN] This will add CONTOSO\JSmith to the local
  Administrators group on PC01 (currently 4 members).`, followed by a confirmation prompt.
  `-Force` skips the prompt and `-WhatIf` shows what would happen without changing anything.
- Read a clear result line, e.g. `[PASS] Added CONTOSO\JSmith to Administrators on PC01. Logged to
  ...\Logs\Changes_2026-10-17.csv`, or `[FAIL] ...` with the reason. The script exits with code 1
  on failure, so batch files can detect it.
- Open `LocalAdminManager\Logs\Changes_<yyyy-MM-dd>.csv` (or `-LogFolder`) and see one row per
  attempt, including failures and "no change" outcomes, with the before and after member lists.
- Run it on a non-English Windows (where the group is called, for example, "Administratoren"),
  because the group is found by its fixed SID, not its English name.

## Acceptance criteria
Each maps to exactly one Pester test named `AC<n>_...`. The script is loaded with
`-LoadFunctionsOnly`, and the read/write/transport wrappers are mocked (see Test plan).

1. AC1: Given a target whose Administrators group holds A and B, when `Add` of C succeeds, then
   the returned entry has Action `Add administrator`, Target `<ComputerName>\<group name>`,
   ItemType `Local group`, Detail `C`, BackupFile empty, OldValue `A; B`,
   NewValue `A; B; C` (re-read from the target after the change, not computed), Result `Done`,
   Error empty, Time in `yyyy-MM-dd HH:mm:ss`, Technician `$env:USERDOMAIN\$env:USERNAME`, and
   Computer `$env:COMPUTERNAME` (the machine the tool ran on, as in M365-SyncedUserFixes).
2. AC2: Given the group holds A, B and C, when `Remove` of C succeeds, then OldValue is
   `A; B; C`, NewValue is `A; B` and Result is `Done`.
3. AC3: Given C is already a member, when `Add` of C runs, then the add wrapper is not called
   and Result is `No change (already a member)`, with OldValue equal to NewValue.
4. AC4: Given C is not a member, when `Remove` of C runs, then the remove wrapper is not called
   and Result is `No change (not a member)`.
5. AC5: Given the add/remove wrapper throws "Access is denied", when the change runs, then the
   function does not throw. Result is `Failed`, Error holds the message, OldValue holds the
   list read before, and NewValue holds the list re-read afterwards (empty if that re-read also
   fails).
6. AC6: Given reading the group on the target throws (computer unreachable), when the change
   runs, then no add/remove is attempted, Result is `Failed`, and Error names the computer and
   the reason.
7. AC7: Given `-WhatIf`, when the change runs, then no add/remove wrapper is called, no change
   log file is created, and Result is `Skipped (WhatIf)`.
8. AC8: The script's `[CmdletBinding()]` declares `SupportsShouldProcess` and
   `ConfirmImpact = 'High'`, so a run without `-Force` prompts (checked through the script AST).
9. AC9: Given `-Force`, when the main body runs with mocked wrappers, then the change is made
   with no confirmation prompt (`$ConfirmPreference` is `None` for the change call).
10. AC10: Given a target whose built-in Administrators group is named `Administratoren`, when
    the group is located, then it is resolved from SID `S-1-5-32-544` and the localized name is
    used. The string `"Administrators"` is never hardcoded as the group to change (regression
    test for the hardcoded English name).
11. AC11: Given `-ComputerName` is the local machine (`$env:COMPUTERNAME`, `localhost`, `.`,
    or empty), when the tool reads or changes the group, then it runs in-process and
    `Invoke-Command` is not called.
12. AC12: Given `-ComputerName PC01`, when the tool reads or changes the group, then it calls
    `Invoke-Command -ComputerName PC01` (transport per Q1; this AC changes if Q1 picks option B
    or C).
13. AC13: Given two runs on the same day, when the change log is written, then both rows are
    in one `Changes_<yyyy-MM-dd>.csv` with a single header row, and the columns are, in order:
    `Time, Technician, Computer, Action, Target, ItemType, Detail, OldValue, NewValue, Result,
    Error, BackupFile`. This is the format pinned in SQ-008's "Change-log format" section, which
    wins over anything else in this spec. Action values are `Add administrator` and
    `Remove administrator`.
14. AC14: Given the log folder cannot be created or written, when the tool is about to make a
    change, then no add/remove is attempted, a `[FAIL]` line names the folder, and the script
    exits 1 (fail closed, per Q2; this AC changes if Q2 picks "warn and continue").
15. AC15: Given members whose names cannot be resolved (orphaned SIDs), when the member list
    is formatted, then the SID string appears in their place, and the list is sorted
    case-insensitively and joined with `; `.
16. AC16: Given a successful change, when the run ends, then the console shows a `[PASS]` line
    with the log path and the exit code is 0. Given a `Failed` result, it shows `[FAIL]` and
    the exit code is 1.
17. AC17: `LocalAdminManager.ps1` declares `#Requires -Version 3.0` and uses no feature above
    3.0 (the tool's `Compatibility.Tests.ps1`, modelled on
    `AD-GroupMembership-Export/Tests/Compatibility.Tests.ps1`, together with
    `Tests/PSVersionFloor.Tests.ps1`).

## Out of scope
- Restoring a previous member list from the log (an "undo" command). The log has enough data to
  undo by hand. A restore command would be a new destructive operation and needs its own item.
- Guard rails against removing the built-in Administrator account (RID 500) or Domain Admins.
  Worth a follow-up item; not part of "log every change".
- Multiple members or computers in one run, and a GUI.
- Groups other than the built-in Administrators group.
- Adding LocalAdminManager to the ServiceDesk-Toolkit bundle (it is not in it today).
- Checking that the member exists in AD beyond what the add itself reports.

## Approach
Restructure `LocalAdminManager/LocalAdminManager.ps1`. It stays a single file, following the
`-LoadFunctionsOnly` pattern of `AD-LockoutDiagnostics/Set-DCSecurityLogRetention.ps1` (also a
change tool with `SupportsShouldProcess`, `ConfirmImpact = 'High'` and `Write-Status`):

- `param()`: keep `-Action`, `-Member`, `-ComputerName`. Add `-LogFolder` (default
  `Join-Path $PSScriptRoot 'Logs'`, not the current directory; same reason as
  `M365-SyncedUserFixes/Start-M365SyncedUserFixes.ps1` line 86), `-Force`, and
  `-LoadFunctionsOnly`. Use `[CmdletBinding(SupportsShouldProcess, ConfirmImpact = 'High')]`.
- `Write-Status` (PASS/WARN/FAIL/INFO colours), copied from Set-DCSecurityLogRetention.
- `Test-IsLocalComputer -ComputerName` (pure).
- `Invoke-OnTarget -ComputerName -ScriptBlock -ArgumentList`: runs `& $ScriptBlock` locally, or
  `Invoke-Command -ComputerName ... -ErrorAction Stop` remotely (option A of Q1). This is the
  only function that touches the transport.
- The script block that runs on the target finds the group by SID `S-1-5-32-544`. It translates
  the SID with `System.Security.Principal.SecurityIdentifier` to get the local name, then uses
  the ADSI `WinNT://<computer>/<localized name>,group` object. It returns members as
  `{ Name, Sid }` (from each member's `objectSid`; ADsPath when the SID cannot be translated) and
  performs `Add`/`Remove` with `WinNT://DOMAIN/Name`. The repo already handles localized
  built-in groups by SID (`Find-PrivilegedAccessPaths/Tests/PrivilegedAccess.Tests.ps1`).
- Thin wrappers that tests mock: `Get-LocalAdminMember -ComputerName`,
  `Add-LocalAdminMember` and `Remove-LocalAdminMember -ComputerName -Member`.
- `Format-MemberList` (pure): sort, then join with `; `.
- `Set-LocalAdminMembership` (`SupportsShouldProcess`): modelled directly on
  `Set-SyncedUserMarker` (`M365-SyncedUserFixes/SyncedUserFixes.Core.ps1` lines 1311-1375). It
  builds an `[ordered]` entry, reads before, decides on no-change, calls
  `$PSCmdlet.ShouldProcess("$Group on $ComputerName", "Add $Member")`, writes, re-reads, and
  never throws.
- `Write-LocalAdminChangeLog -Entries -LogFolder`: a copy of `Write-SyncedUserChangeLog`
  (same file name pattern `Changes_<yyyy-MM-dd>.csv`, append with a single header, UTF8,
  returns the path or `$null`).
- `Test-LogFolderWritable -LogFolder`: creates the folder if needed and does a create/delete
  probe of a temp file. Called before any change (Q2).
- Main body: elevation check (keep the existing `Test-Administrator`), log-folder check, read
  the current members, print the `[WARN]` scope line, `if ($Force) { $ConfirmPreference = 'None' }`,
  call `Set-LocalAdminMembership`, write the log, print the result, then `exit 0/1`. Under
  `-WhatIf` no log is written (AC7).
- Add `.NOTES` REFERENCES. Update the help (`.PARAMETER LogFolder/Force`, a `-WhatIf` example)
  and `LocalAdminManager/README.md`: requirements (WinRM on remote targets if Q1=A), the log
  location and columns, `-Force` in the batch examples, and removal of the wrong "Windows 10 /
  Server 2016 cmdlets" note. Update the root `README.md` LocalAdminManager section with the new
  parameters.
- Add `LocalAdminManager/Logs/` to `.gitignore` under the client-data block, next to
  `M365-SyncedUserFixes/Logs/`.
- Before coding, verify on Microsoft Learn and cite in comments and REFERENCES:
  - that `Add-LocalGroupMember`/`Remove-LocalGroupMember` have no `-ComputerName` (the root cause;
    https://learn.microsoft.com/powershell/module/microsoft.powershell.localaccounts/add-localgroupmember);
  - well-known SID `S-1-5-32-544`
    (https://learn.microsoft.com/windows-server/identity/ad-ds/manage/understand-security-identifiers);
  - the IADsGroup `Add`/`Remove`/`Members` methods
    (https://learn.microsoft.com/windows/win32/api/iads/nn-iads-iadsgroup);
  - the `Invoke-Command` parameters.

  Also check the real `Invoke-Command` names with `Get-Command -Syntax` (read-only).
- Save as UTF-8 with BOM if any non-ASCII character is used. Otherwise keep the file ASCII.
- No plan in `docs/plans` covers this tool.

  domain (`Name` resolves to `WinNT://<target>/Name`), a case-different duplicate

  case-insensitive name fallback).

## Decisions
### Confirmed by the owner
- D-005 remote targets via Invoke-Command running the ADSI script block.
- D-029 fail closed when the change log cannot be written.
- D-030 change-log columns follow SQ-008's pinned format.
- (none yet; Q1 and Q2 pending)

### Assumed by the squad
- Log format: the M365-SyncedUserFixes change log (`Changes_<yyyy-MM-dd>.csv`, appended,
  single header, `Time`/`Technician`/`Computer`/`Action`/.../`OldValue`/`NewValue`/`Result`/`Error`).
  Reason: the backlog item says "same format as SQ-008", and SQ-008 says "M365-SyncedUserFixes
  format" (`SyncedUserFixes.Core.ps1` lines 1334-1347, 1396-1420). `Computer` keeps its M365
  meaning (where the tool ran). The changed machine goes in an added `TargetComputer` column, and
  `Group` holds the localized group name. SQ-008 should use the same column names where they
  apply.
- Old and new lists go in `OldValue`/`NewValue` as `; `-joined sorted names, not in extra
  columns. Reason: they stay readable in Excel and match the M365 columns.
- NewValue is re-read from the target after the change, not computed. Reason: the risk profile
  wants evidence of what actually happened.
- `-LogFolder` (default `Logs` next to the script) rather than `-OutputPath`. Reason: M365
  precedent for change logs, and an elevated prompt's current directory is System32.
- Confirmation prompt, `-WhatIf` and `-Force` are added. Reason: required by
  `squad/risks/destructive-operations.md` and the root CLAUDE.md `-Force` convention. Nothing
  breaks for existing batch callers, because the tool has never succeeded (see Summary). README
  batch examples gain `-Force`.
- `-WhatIf` writes no log. Reason: a dry run changes nothing. File cmdlets would inherit
  `$WhatIfPreference` anyway.
- "No change" outcomes and failures are logged as rows. Reason: M365 logs every attempt, and an
  auditor needs to see the failures too.
- Membership is matched by SID, with a case-insensitive name fallback. Reason: names differ in
  case and format between input and ADSI.
- The group is found by SID `S-1-5-32-544`, not the name "Administrators". Reason: the name is
  localized. The repo already resolves built-ins by SID (Find-PrivilegedAccessPaths).
- ADSI (`WinNT://`) runs inside the target script block instead of the LocalAccounts cmdlets.
  Reason: the cmdlets need PS 5.1 on the target and `Get-LocalGroupMember` is known to fail on
  groups holding orphaned SIDs, which would block the "before" read. ADSI works on PS 3.0 and
  handles orphaned SIDs. The builder confirms the LocalAccounts failure mode before citing it,
  or drops the claim.
- `#Requires -Version 3.0` with a Compatibility test. Reason: the root CLAUDE.md default.
  Admin rights are checked by the existing `Test-Administrator` function, which avoids the 4.0
  `#Requires -RunAsAdministrator`.
- Keep the existing elevation check as it is (it is required even for remote targets). Reason:
  out of scope, and it is not a safety regression.
- Exit code 1 on any failed result. Reason: batch callers in the README need to detect failure.
  Today the script exits 0 even when the change failed.
- No split. Reason: the transport fix is the minimum needed to record a before/after list, and
  the whole item is under a day in one file.

## Risk and safety notes
- Destructive-operations profile applies in full (privileged group membership on client
  machines). Covered:
  - scope printed with `[WARN]` before acting (target, group, current member count, member);
  - `SupportsShouldProcess` with `ShouldProcess` per target and `-WhatIf` tested (AC7);
  - confirmation unless `-Force` (AC8, AC9);
  - old and new values logged with a timestamp (AC1, AC2, AC13);
  - partial failure handled (AC5, AC6);
  - the "zero items" edge (empty group) tested.
- Every write path (`Add-LocalAdminMember`, `Remove-LocalAdminMember`, `Invoke-Command`, ADSI) is
  mocked. A test that could touch a real Administrators group is a blocker.
- Member lists are usernames from client environments. The log stays local under
  `LocalAdminManager/Logs/`, which is gitignored.
- Behaviour change worth flagging in the PR: the tool goes from always failing to actually
  changing membership. Remote targets newly need whatever transport Q1 picks.
