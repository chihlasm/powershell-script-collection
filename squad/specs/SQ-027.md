# SQ-027 · M365 user check: a blocked risky user must escalate to the security lead, not the manager path

- status: review
- feature: M365 user check
- size: S
- risk: medium
- touches: `M365-UserQuickCheck/M365UserCheck.Core.ps1` (`Get-M365UserAssessment` step choice,
  one new step constant, one small helper), `M365-UserQuickCheck/Get-M365UserQuickCheck.ps1`
  (`ConvertTo-M365UserCheckTicketNote`, only if Q2 = A),
  `M365-UserQuickCheck/Tests/M365UserCheck.Core.Tests.ps1`,
  `M365-UserQuickCheck/Tests/Get-M365UserQuickCheck.Tests.ps1`, `M365-UserQuickCheck/README.md`

## Summary (plain English)
Today, when Microsoft's ID Protection flags a user as risky or compromised and an admin has
blocked them, the M365 user check shows two steps that conflict: "involve the security lead" (a
warning) and "check with their manager, then unblock sign-in". Only the second one reaches the
ticket note, so a tier 1 tech could unblock a compromised account. After this change, every step
for a risky user that would unblock, re-enable or reset the password tells the tech to escalate
to the security lead instead, and that is the step that goes in the ticket note. In the same
change, a synced account blocked on purpose (it carries the block marker) no longer gets "enable
it in AD" from the sign-in error step next to the "check with the senior engineer" step.

## What users will be able to do
- A tier 1 tech checks a user whom ID Protection flags (risk level medium or high, or risk state
  atRisk or confirmedCompromised) and who is blocked. The answer is still NO. "Why not" and the
  ticket note's "Next step" say to escalate to the security lead, and that they must not unblock
  sign-in, enable the account or reset the password until the security lead agrees. The manager
  step is not shown anywhere in the report for that user.
- The same applies when the user's latest sign-in failed with 50057 (account disabled), 50055
  (password expired) or 50126 (wrong password), and when AD has the account disabled while
  Microsoft 365 still lets them in. Each of these steps would otherwise turn the account back on
  or reset its password.
- A synced user blocked on purpose with M365-SyncedUserFixes (block marker on the AD account)
  whose latest sign-in failed with 50057 gets one consistent step: "Check with the senior
  engineer who blocked it...". The 50057 step no longer says "enable it in AD".
- Users who are not flagged as risky see exactly the steps they see today (D-050).
- (Q1 = A) When ID Protection could not be checked (no Entra ID P2, or a role that cannot read
  it), the manager step for a blocked account ends with one sentence. It says the risky-user
  check did not run, and that if the account was blocked during a security incident, the tech
  escalates to the security lead instead.
- (Q2 = A) A risky user who is not blocked and whose sign-in works keeps the YES verdict, but the
  ticket note's "Next step" carries the security-lead step instead of "No Microsoft 365 account
  problem found".

## Acceptance criteria
Tests go in a new `Describe 'SQ-027 a risky user always escalates to the security lead'` in
`M365-UserQuickCheck/Tests/M365UserCheck.Core.Tests.ps1`. AC9 and AC10 go in
`Get-M365UserQuickCheck.Tests.ps1`. Tests are named `SQ027_AC<n>_...`, because both files
already hold SQ-002's `AC1`-`AC29`. The new Describe gets its own copies of the `New-AdUser` /
`New-AdGate` / `New-HybridFacts` fixtures, as the SQ-019 Describe does: a Describe's `BeforeAll`
is not visible to sibling Describes.

"Risky" in these ACs means the RiskGate is `Available` and `RiskyUser` matches the existing
predicate: `riskLevel` high or medium, or `riskState` atRisk or confirmedCompromised.
"The security-lead step" means the new constant `$script:M365RiskyUserStep`. Its text must:
- start with `Escalate to the security lead`;
- say not to unblock sign-in, enable the account or reset the password until the security lead
  agrees;
- not contain `manager`.

## Out of scope
- AD-UserQuickCheck's manager step without the approver note (`Get-ADUserQuickCheck.ps1:422`)
  and its "extend or clear the account expiry date" step (`:442`). It is a different tool and
  feature, it reads no ID Protection data, and D-050 already says it follows separately. This is
  raised as Q3: a separate item is recommended.
- Widening the SQ-019 checker's verb list (unlock, restore, take ownership, "turn back on", free
  up space, clean up). It is a recorded SQ-019 follow-up. Widening it here would also force a
  rewording of StaleTenantSync's "(enabling, unlocking, a new password)" status text.
- Changing any verdict, level or reason code. RiskyUser stays a Warning, and a risky user who can
  sign in stays YES.
- The 50053, 53003, 530035, NoLicence, LicenceError, UPN/SID mismatch and AdEnabledMismatch
  (Probable) steps for risky users. None of them unblocks, enables or resets anything.
- The risky-user predicate itself (which levels/states count). It is unchanged and already
  cited in the core's `.NOTES`.
- Conditional Access policy names and `failureReason` in the note (separate SQ-019 follow-up).
- `dist/` bundles.

## Approach
- **`M365UserCheck.Core.ps1`**
  - Add a small pure helper `Test-M365RiskyUser -RiskGate -RiskyUser` that returns `$true` only
    when the gate is `Available` and the record matches the existing predicate (`:879-883`).
    The RiskyUser reason block calls it, so the warning and the step override can never disagree.
  - Add `$script:M365RiskyUserStep` next to `$script:M365NoSignInHistoryStep` (ASCII only).
    Proposed text:
    `Escalate to the security lead: Microsoft Entra ID Protection flags this user as a possible compromised account. Do not unblock sign-in, enable the account or reset the password until the security lead agrees.`
  - In `Get-M365UserAssessment`, compute `$isRisky` once, before the "Account blocked" section.
    Leave the RiskyUser reason where it is, so the order of reasons within a level does not
    change.
  - SignInBlocked: if `$isRisky`, the action is the security-lead step. Otherwise the existing
    branches run unchanged.
  - Sign-in failure: after `$step = Get-M365SignInNextStep ...`, decide the action in this order:
    1. if `$isRisky` and the code is 50055, 50057 or 50126, use the security-lead step;
    2. if the code is 50057 and SignInBlocked fired, use the SignInBlocked action (AC7);
    3. otherwise use the mapped step.

    `Get-M365SignInNextStep` itself is unchanged, so the SQ-019 password-step exemption and the
    "Action equals the mapped step" behaviour for non-risky users stay exact.
  - AdDisabledCloudEnabled is added inside `Get-M365OnPremisesAssessment`, which does not know
    about risk. Pass `-IsRisky` (a switch, default off) into it from `Get-M365UserAssessment`.
    When it is set, use the security-lead step for that Action. Also return it as
    `BlockedAction` for every branch, or override `BlockedAction` in the caller, whichever keeps
    the diff smaller. The ACs only see the outcome.
  - (Q1 = A) Add `$script:M365RiskNotCheckedSentence`, for example
    `ID Protection could not be checked: if this account was blocked during a security incident, escalate to the security lead instead.`
    Append it to the manager-path actions (`:680`, `:688`, `:831`, and 50057 cloud/synced) only
    when the RiskGate exists and is `NotLicensed`, `NotAllowed` or `Failed` (a 403 can't tell missing P2 from a missing role). Not for `NotChecked` with no cloud
    user: SignInBlocked cannot fire without a user.
- **`Get-M365UserQuickCheck.ps1`** (Q2 = A only): in `ConvertTo-M365UserCheckTicketNote`, add
  the RiskyUser reason's `Action` to `$next` after the Blocker/Probable actions. The YES
  fallback step is then skipped because `$next.Count` is no longer 0. The kit's
  `New-TicketNote` already de-duplicates identical steps (`CaseKit.ps1:172-175`), so a
  SignInBlocked and a 50057 reason with the same action show once.
- **README:** rows at lines 98, 105 and 122 as in AC11.
- Patterns to match:
  - the existing fixed-step constants (`$script:M365NoSignInHistoryStep`,
    `$script:M365AddressCheckStep`);
  - the existing D-017 phrasing "Escalate to a senior engineer: ..." (`ProvisioningError`);
  - the SQ-019 checker in the test file's top `BeforeAll` (`Test-M365StepNeedsApproval`,
    `$script:ReversalPattern`);
  - the SQ-019 Describe's fixture copies and `Get-BlockedAction`.
- No new Microsoft facts. The risk levels and states are the ones already cited at `:122-124`
  (riskyUser resource). Error codes 50055/50057/50126 keep their existing citations.
- Version floor and encoding: no new syntax, ASCII strings only (`Tests/PSVersionFloor.Tests.ps1`,
  `Tests/ScriptEncoding.Tests.ps1`).

## Decisions
### Confirmed by the owner
- D-050: the manager check plus "note on the ticket who approved it" is only for a plain blocked
  account. Deliberate blocks (marker, risky user) still say Escalate. This item makes "risky
  user" true in code.
- D-017: a reversing step says Escalate plus the reason, and tier 1 never sees it as a plain
  instruction.
- D-001: about half of the tenants lack P1, and fewer have P2. An unavailable risk gate is
  normal, which is why Q1 matters.
- D-059 (Q1 = A): the manager-path steps carry the "ID Protection could not be checked" caution
  when the risk gate is NotLicensed or Failed. AC6 is in. (Squad, 2026-10-20 run: NotAllowed added too,
  because a 403 means "no P2 or a role that cannot read it", which line 37 names; see Assumed.)
- Q2 = A, settled by the read-only-advisory checklist (2026-10-20: the next steps that reach the
  ticket note must carry the escalation themselves) and P-004: the RiskyUser action goes into the
  note's next steps. AC10 is in.
- D-060 (Q3 = A): AD-UserQuickCheck's approver note is a separate item, SQ-030. Out of scope here.

### Assumed by the squad
- **"Risky" reuses the existing predicate unchanged** (`M365UserCheck.Core.ps1:883`), through one
  helper, so the warning and the step override cannot drift apart. The backlog and the
  read-only-advisory profile name atRisk/confirmedCompromised, and the existing predicate also
  counts medium/high levels. Narrowing it would be a separate change.
- **Password-reset steps (50055/50126) escalate for a risky user too.** The read-only-advisory
  profile (2026-10-20) says a risky user "always escalates to the security lead before any
  unblock, re-enable or password-reset step". This is answered by the profile, so it is not asked.
- **AdDisabledCloudEnabled (a Warning) is included.** The profile says one report never gives
  conflicting next steps for the same account. That step offers "enable the AD account" next to
  RiskyUser's escalation.
- **One shared security-lead step for every overridden reason.** It is the same advice, and
  identical strings collapse to one line in the note (`CaseKit.ps1:174`).
- **The marker/50057 fix generalises to "50057 follows SignInBlocked when SignInBlocked
  fired".** 50057 means the account is disabled, which is the condition SignInBlocked reports.
  Reusing its action removes every 50057-versus-SignInBlocked conflict at once (marker, no-AD,
  AdEnabledMismatch), not only the marker case. When SignInBlocked did not fire (the account
  has since been enabled), the mapped 50057 step stays.
- **`Get-M365SignInNextStep` is not changed.** The override sits in the assessment, so the SQ-019
  exact-string exemption of the four password steps stays valid.
- **The verb-list widening stays a separate follow-up** (see Out of scope). It would force a
  status-text rewording that this item does not need.

- **Added during the build (2026-10-20 run):**
  - **NotAllowed counts as "could not be checked"** (lead decision in fix round 1): the
    read-only-advisory review found a 403 on riskyUsers is graded `NotAllowed`, which means "no P2
    or a role that cannot read it", exactly the case the user-facing rule names. D-059's state list
    named only NotLicensed/Failed; the caution is a safe-side addition. Michael can narrow it back.
  - `Test-M365RiskyUser` (gate `Available` + the existing level/state rule) is the single predicate
    behind both the RiskyUser warning and the step override.
  - The caller (`Get-M365UserAssessment`) does the risky-user override for the marker and AD-enabled
    cases; `Get-M365OnPremisesAssessment` gained `-IsRisky` / `-RiskNotChecked` for the AD-disabled ones.
  - Test changes: AC8 narrowed to unblock/enable/re-enable/reset/"change it" actions (unchanged
    Escalate steps contain "removing", out of scope); `SQ019_AC9_ReadmeStepsMatch` anchor loosened to
    allow the new leading sentence (AC11 pins it); counts corrected (AC2 8 -> 7, AC8 >40 -> exactly 38,
    verified by code and spec reviewers).

## Risk and safety notes
- **Read-only-advisory applies in full.** This item implements three of its rules for this tool:
  - "risky user always escalates to the security lead" (AC1-AC4);
  - "the steps that reach the ticket note carry the escalation themselves" (AC9, and AC10 if
    Q2 = A);
  - "one report never gives conflicting next steps" (AC7, AC8).

  The code still only reads, and the static read-only guard tests are untouched.
- **Personal-data:** no new fields reach the note or CSV. The RiskyUser Message (level and
  state) already goes in the note today. The new step is fixed wording, with no client data.
- **Pre-mortem (what could stop the build?)**
  1. Q1, Q2 and Q3 unanswered. AC6 and AC10 are written for option A and dropped with option B,
     so the build can proceed with either answer. Q3 does not touch this item's code.
  2. An existing test pins the old text for a risky scenario. Checked: only `AC16_*` and the
     D017 scenario use a risky fixture, and none of them is blocked or has a failing sign-in.
     The entry-script suite has no risky fixture.
  3. `SQ019_AC9`'s README checker rejects a new README cell. AC11's sentence puts "escalate"
     before any reversal word, so rule (b) passes.
  4. The Q2 change makes a YES verdict show a non-trivial next step. The verdict and exit code
     do not change, and AC10 pins both.
