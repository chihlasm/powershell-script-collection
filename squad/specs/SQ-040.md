## Summary (plain English)
When Microsoft's ID Protection flags a user as risky and their latest sign-in was stopped by
Conditional Access (53003) or security defaults (530035), the M365 user check today tells the tech
to "ask the client's admin whether it should apply to this user". For a risky user that policy is
often the one that is holding a compromised account out; excluding them from it lets the attacker
back in. After this change those steps say "escalate to the security lead" for a risky user, the
security-lead step is the first next step in the ticket note, and the step names changing or
excluding a Conditional Access policy as something not to do until the security lead agrees.
Depending on the owner's answers, the 53003 step for every user also says what to do when the
blocking policy is risk-based (Q1), and a risky user no longer gets "help them add Microsoft
Authenticator" (Q2).

## What users will be able to do
- A tier 1 tech checks a user ID Protection flags (risk level medium or high, or state atRisk or
  confirmedCompromised) whose latest sign-in failed with 53003 or 530035. The answer is still NO
  and "Why not" still shows the code, Microsoft's reason, the blocking policy name (when visible)
  and the lookup link. The "What to do" line is the security-lead step, which says not to unblock,
  enable, reset the password, or change or exclude them from a Conditional Access policy or
  security defaults until the security lead agrees. "Ask the client's admin whether it should
  apply to this user" is not shown anywhere for that user.
- The ticket note for any user ID Protection flags starts its "Next step" list with the
  "involve the security lead" step, ahead of every other step, so a tech reading top-down sees
  the escalation first. Users who are not flagged keep today's order.
- (Q1 = A) For every user, the 53003 step starts by saying: if the policy that blocked it is
  based on user risk or sign-in risk (its Conditions show User risk or Sign-in risk), escalate to
  the security lead and do not change the policy or exclude them from it. This covers a risky
  sign-in blocked for a user who is not (yet) flagged, and tenants where ID Protection could not be
  read.
- (Q2 = A) A user ID Protection flags who has no MFA method still gets the "No MFA method
  registered" warning, but its "What to do" is the security-lead step instead of "Help them add
  Microsoft Authenticator", because registering a method on an attacker's device would hand them
  the account.
- Users who are not flagged see exactly today's steps (apart from the Q1 = A sentence on 53003).

## Decisions
### Confirmed by the owner
- D-050 / D-017: a risky user escalates to the security lead instead of any step that undoes a
  deliberate block. A Conditional Access block on a risky user is such a block.
- D-059: the "could not be checked" caution applies to the manager-path steps; 53003/530035 are not
  manager-path steps, so they do not get the sentence (AC4). Q1 = A covers the unchecked-risk case
  for 53003 with its own sentence instead.
- D-001: many tenants lack P1/P2; risk-based CA needs P2, which is why the user-facing hint in Q1
  is conditional ("if the policy is based on user or sign-in risk").
- D-067 (2026-11-11): Q1 = A, the conditional risk-policy sentence on the 53003 step for everyone (AC5). D-068: Q2 = A, the risky user's NoMfaMethod step escalates (AC6). Depends on SQ-039.

### Assumed by the squad
- **Both 53003 and 530035 escalate for a risky user, whatever produced the block.** The backlog
  proposes it and the read-only-advisory profile's rule is about the user, not the policy type.
  It also makes the behaviour independent of the Learn answer on which code a risk policy returns.
- **The RiskyUser step goes first in the note for a risky user.** The read-only-advisory checklist
  gap (report 2026-10-20-0837: "when an escalation applies to the account, it is the first next
  step") and the SQ-027 review minor both say so; the backlog says "or put first". Doing both
  (override and order) costs one line.
- **One shared, longer security-lead step rather than a CA-specific one.** Identical steps
  de-duplicate in the note (`CaseKit.ps1:174`) and SQ-027's AC1-AC4 compare to the constant, so one
  edit keeps every risky path consistent.
- **The policy-reversal and MFA-registration patterns live in the new Describe, not in the shared
  SQ-019 checker** (see Out of scope: `:657` false positive, non-risky 530035 rewording).
- **No new error codes are mapped**; unmapped codes already give no step (`Get-M365SignInNextStep`
  default), so they cannot carry a reversal.
- **Learn could not be reached during planning** (no web or Learn tool in the planner's session).
  The facts above about 530032/53004/53011 and risk-policy codes are recollection, marked as such;
  step 0 verifies them and nothing in the ACs depends on them.
