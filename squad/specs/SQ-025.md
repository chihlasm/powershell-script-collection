# SQ-025 · FolderPermissionManager WPF app: change an existing permission in place

- status: review
- size: M
- risk: high (destructive-operations profile in full)
- touches: `FolderPermissionManager/FolderPermissionManager-GUI.ps1` (button, double-click, dialog
  mode, confirm spec, read-back, dry-run result), `FolderPermissionManager/FolderPermissions.Core.ps1`
  (one new change function plus pure helpers), `FolderPermissionManager/README.md`, new tests in
  `FolderPermissionManager/Tests/`. The CLI `FolderPermissionManager.ps1` and the browser
  `FolderPermissionManager-WebGUI.ps1` are not touched.
- depends on: SQ-018 including its pending revision (AC47-AC57 in `squad/specs/SQ-017.md`). Build
  from main after SQ-018 merges; if SQ-018 is done but not merged when the run starts, stack on

## Summary (plain English)
Today, turning `chihlas`'s Allow into a Deny means adding a second entry and typing the account
name again. With this item the tech selects the entry in the permissions list and presses
**Change Permission** (or double-clicks it): a dialog opens with the account already filled in,
and they only pick the new level or Allow/Deny. The old entry is swapped for the new one in a
single write, after the usual backup and log line, so a failure can never leave the account with
no entry at all. A Deny gets the same red "are you sure" step as adding a Deny. Inherited entries
can't be changed here; the dialog says which folder above they come from.

## What users will be able to do
- In the folder permissions list, select an entry and press **Change Permission** (next to Add
  and Remove), or double-click the entry.
- For an entry set directly on this folder (not inherited), a dialog "Change Permission Entry"
  opens showing:
  - the path and its real location (as the Add dialog does);
  - the account, read-only (a deleted account shows as its SID with "Windows can't look up this
    account from here (it may be deleted, or local to the server)");
  - "Applies to", read-only, in Explorer's words (for example "This folder, subfolders and files");
    it is kept as it is;
  - the permission level, preselected. When the entry holds a non-standard mix of rights, the
    list starts with "Keep current (DeleteSubdirectoriesAndFiles, Modify)", preselected, so the
    tech can flip Allow/Deny without losing the exact rights;
  - Allow/Deny, preselected;
  - when the account has other entries set directly on this folder, a note that only the chosen
    entry changes (Q-A).
- Choosing Deny turns the submit button red, labelled "Change to Deny", never the default
  button, and a confirm dialog with the real location, the old and new entry and the Deny warning
  opens before anything changes. If the tech's own account or one of their groups gets the Deny,
  the confirm says they may lose access themselves. (Which other changes also get the confirm is
  Q-B.)
- Pressing Change with nothing changed keeps the dialog open: "Nothing to change yet: choose a
  different permission level or Allow/Deny."
- For an inherited entry, the dialog opens read-only: "<account> gets Allow Modify here from
  <folder above>. To change it, open that folder." with a Close button only.
- For files: with exactly one file selected, **Change Permission** in the files bar opens the
  same dialog with a picker of that file's own (not inherited) entries (Q-C).
- After the change: the same status line, backup and log as Add/Remove, a read-back check, and
  under `-WhatIf` a dry-run result naming the account, old and new entry and location.

   entries ..."; with none, no note. Inherited entries are not counted.
8. **AC8_NothingToChange**: Given the dialog with the level and type as they were, when Change is

9. **AC9_InheritedEntrySource**: Given a `$TestDrive` folder `P` with an explicit Allow

### The change itself (core)
10. **AC10_OneWriteReplacesEntry**: Given a `$TestDrive` folder whose ACL (from SDDL) has the AC1
    explicit entries and `Set-Acl` mocked to capture `-AclObject`, when
    `Set-FolderPermissionEntry` changes the Allow Modify (CI,OI) entry of `S-1-5-32-545` to Deny
    Modify, then `Set-Acl` is called exactly once; the captured ACL has no explicit Allow Modify
    (CI,OI) for that SID, has an explicit Deny Modify (CI,OI) for that SID, and every other entry
    (the Deny Write, the inherited Allow Read, other accounts) is unchanged; the row is `Done` with
    Action `Change permission`.
11. **AC11_KeepsAppliesTo**: Given entries with flags None/None, OI/InheritOnly and
    CI/NoPropagateInherit, when each is changed to another level, then the new entry has exactly
    the old entry's inheritance and propagation flags (not the app's default CI,OI); and on a file,
    None/None.
12. **AC12_OnlyTheChosenEntry** (Q-A): Given two explicit Allow entries for the same SID (Modify
    CI,OI and Write None/None), when the Modify one is changed to Read, then the Write entry is
    still there unchanged.
13. **AC13_KeepCurrentRights**: Given an entry with rights "DeleteSubdirectoriesAndFiles, Modify"
    changed with level `Current` from Allow to Deny, then the new Deny entry has the same rights
    mask (Synchronize left to Windows as the core does today); and a GENERIC_ALL entry kept as
    `Current` is written as its mapped file rights (`ConvertTo-SpecificFileRight`).
14. **AC14_EntryGoneNothingWritten**: Given the folder's ACL no longer holds the exact entry when
    the change runs (re-read in the work, matched by SID, type, rights mask and flags), then
    `Set-Acl` is not called, the row's Result is `Skipped (entry not found)`, and the status is a
    warning: "The permission entry changed since it was shown (someone else may have changed it).
    Nothing was changed. Press Refresh and try again."
15. **AC15_FailedWriteKeepsOldEntry**: Given `Set-Acl` mocked to throw, then the row is `Failed`,
    its OldValue equals its NewValue (the permissions read back after the failure), the status
    starts with SQ-018's failure wording and names the backup file, and the error says nothing was
    changed.
16. **AC16_NonCanonicalRefused**: Given an ACL whose `AreAccessRulesCanonical` is false (built
    with a Deny after an Allow via raw SDDL), then `Set-Acl` is not called, the row is `Failed`, and
    the error is "The permissions on <path> are not in the order Windows expects, so the tool will
    not edit them. Nothing was changed. Ask a senior admin to check them in Explorer (Advanced
    Security Settings)."
17. **AC17_BackupLogStartedFirst**: Given a successful change, then the backup CSV and a
    `Started` log row are written before `Set-Acl`, and the Done log row has the D-030 columns with
    Action `Change permission`, Detail "From Allow Modify to Deny Modify for BUILTIN\Users (applies
    to: This folder, subfolders and files)" and the SDDL before and after; given the backup can't be
    written, `Set-Acl` is not called and the row is `Failed` with the core's backup text.
18. **AC18_ActsOnSid**: Given an entry whose SID cannot be translated to a name
    (`S-1-5-21-1-2-3-1234`), then the dialog shows the SID with "Windows can't look up this account
    from here (it may be deleted, or local to the server)", and the change's new rule and the
    removed rule both carry that SID; and for a translatable account the core never translates the
    name again (the rule is built from the SID).

## Approach
- **Code to read first** (on `squad/SQ-018-fpm-wpf-changes`, or main once merged; this planner
  could not read the branch, so names come from the SQ-018 spec and review notes):
  `Show-PermissionDialog`, `Open-AddPermission`, `Open-RemovePermission`, `Invoke-AddPermission`,
  `Set-PermissionSubmitStyle` (AC47 danger style), the confirm dialog (`Get-ConfirmSpec`,
  `Set-ConfirmDialog`), `Start-ChangeTask`, target resolution (`Resolve-ChangeTargetSet`, real
  location, D-043, remembered mappings), `Get-PermissionIdentityCheck` / `ConvertTo-IdentitySid`,
  the read-back by SID, the AC57 dry-run result, `Get-ChangeStatus`, refresh plan (AC40). Reuse each;
  add a `ChangePermission` case rather than a parallel path.
- **Core (`FolderPermissions.Core.ps1`, 3.0 floor: no `::new()`, `.Where()`, classes):**
  - `Set-FolderPermissionEntry` with `[CmdletBinding(SupportsShouldProcess)]`, parameters `-Path
    [string[]]`, `-Sid`, `-Type` (old), `-RightsValue` (old mask), `-InheritanceFlags`,
    `-PropagationFlags`, `-NewRights` (`FullControl|Modify|ReadAndExecute|Read|Write|Current`),
    `-NewType` (`Allow|Deny`), `-LogFolder`. It runs through `Invoke-SingleItemAclChange` (backup,
    ShouldProcess per item, one row per item, Action `Change permission`, ActionSlug
    `ChangePermission`). Change block: `Get-Acl`; refuse non-canonical (`AreAccessRulesCanonical`);
    find the exact explicit rule with `GetAccessRules($true, $false, [SecurityIdentifier])`
    (`Find-ExplicitAccessRule`, pure); none -> return `Result = 'Skipped (entry not found)'`
    without writing (the block's existing Result outcome); `RemoveAccessRuleSpecific(<that rule
    object>)`; check in memory that it is gone; `AddAccessRule(<new rule: same SID object, new
    rights, same flags, new type>)`; one `Set-Acl -LiteralPath -AclObject -ErrorAction Stop`.
  - Why this pair and not `SetAccessRule`/`ResetAccessRule`: `SetAccessRule` replaces every rule of
    the same account and the same Allow/Deny type (so it would drop sibling entries and, for
    Allow -> Deny, leave the Allow in place); `ResetAccessRule` drops every rule of the account of
    both types. `RemoveAccessRuleSpecific` removes only the rule that matches exactly (account,
    rights, flags, type). `AddAccessRule` merges into an existing rule with the same account, type
    and flags, which AC23's "at least the chosen rights" read-back allows for. **The builder
    verifies each of these on Learn and cites them** (URLs in Risk notes); if Learn says otherwise,
    follow Learn and record it.
  - Single write: both edits are made on the in-memory ACL object; `Set-Acl` writes the DACL once.
    The core already notes "NOT VERIFIED: which Win32 call Set-Acl uses"; the guarantee pinned by
    tests is "exactly one `Set-Acl`, and a throw leaves the before-state" (AC10, AC15). Keep
    `Set-Acl` (consistent with Add/Remove/Copy and their mocks) rather than switching to
    `SetAccessControl`.
  - `Format-AppliesTo` and `Find-InheritanceSource` (walks up with `Get-Acl -LiteralPath` on each
    parent until it finds an explicit inheritable rule that `Test-InheritedCopyOfRule` matches, or
    reaches the drive or share root; stops on an unreadable parent). Both pure apart from that read,
    so the CLI could use them later.
  - `Get-ChangeResultMessage`: add the `Change permission` case (AC24).
- **App (`FolderPermissionManager-GUI.ps1`, 5.1):**
  - `ConvertTo-AclViewModel` rows gain `Sid`, `RightsValue`, `InheritanceFlags`, `PropagationFlags`,
    `AppliesTo` (additive; the CSV export is unchanged).
  - New `ChangePermissionBtn` between Add and Remove, `Btn` style, label "Change Permission" with a
    pencil glyph (`&#x270E;`) plus text, in `Get-ChangeControlNames` so it is disabled during a
    change; files bar gets `ChangeFilePermissionBtn`.
  - `FolderAclGrid.MouseDoubleClick` -> resolve the row under the mouse
    (`ItemsControl.ContainerFromElement`) -> `Invoke-AclRowDoubleClick`.
  - The Change dialog reuses `Get-PermissionDialogXaml` with a mode: a read-only account field
    (`PermAccountText`), an `PermAppliesToText` line, an entry picker for files
    (`PermEntryCombo`), a note line, and Close-only for inherited mode. Existing Add/Remove dialog
    behaviour unchanged. Inline errors in `PermDialogError` as SQ-018 AC56 does.
  - Self-deny: `[System.Security.Principal.WindowsIdentity]::GetCurrent()` `.User` and `.Groups`,
    injected as a parameter so tests never read the real token.
- **Docs:** README section "Change a permission"; `.NOTES` REFERENCES in both scripts gain the new

### Assumed by the squad
- **"Applies to" is kept from the original entry**, never reset to the app's default CI,OI.
  Changing level or Allow/Deny must not silently widen a "This folder only" entry to the whole
  tree, or narrow a tree-wide one. Shown read-only so the tech sees it. (Editing it is out of scope.)
- **One row = one entry = one ACE as .NET reads it** (`GetAccessRules`, as the grid already shows).
  The match at write time is exact (SID, type, rights mask, flags), so a stale view never changes
  the wrong thing (AC14). Evidence: `ConvertTo-AclViewModel` in the app; destructive-operations
  "the old value logged is the same read the safety decision used".
- **Non-standard rights get "Keep current (<rights>)"** preselected rather than snapping to the
  nearest level: flipping Allow/Deny then keeps the exact rights. Generic rights are written as
  their mapped file rights, which is what Windows gives children anyway (`ConvertTo-SpecificFileRight`,
  `Test-InheritedCopyOfRule` in the core).
- **Act on the SID, not the name** (risk profile "right object"; SQ-018 remove lesson). A deleted
  account's entry can be changed too, because the SID is used directly.
- **`RemoveAccessRuleSpecific` + `AddAccessRule` + one `Set-Acl`** (see Approach), consistent with
  the core's existing `Set-Acl` use and its mocks.
- **Non-canonical ACLs are refused** before any write (AC16): .NET will not edit them reliably and
  Explorer offers to reorder them; better a plain refusal than a surprise reorder.
- **Inherited source by walking up the folders** with `Get-Acl` and the core's
  `Test-InheritedCopyOfRule`, in the background, rather than P/Invoke `GetInheritanceSourceW`:
  simpler, testable in `$TestDrive`, and the app already reads parents. Above a share root the
  tool can't see, and says so.
- **New core function, not app-only logic**: SQUAD.md "logic separated from collection and UI"; the
  core holds every other change, and the 3.0 floor is kept.
- **CLI and browser GUI get no change command** (out of scope; the backlog asks for the WPF app).
- **Self-deny warning in the confirm** (AC21), squad-drafted text, owner can adjust at review:
  Deny for Administrators on a folder the tech doesn't own can lock the tool out of reading back.

## Owner questions
- **Q-A** When an account has more than one entry set directly on a folder (Windows sometimes
  splits one permission into two, or someone added "special" rights), what does Change replace?
  - A (recommended): only the entry that was selected; the dialog says how many other entries the
    account has there. Least surprise: exactly the row clicked changes, nothing else is removed.
  - B: every entry of that account with the same Allow/Deny is replaced by the one new entry (as
    Remove already removes all of a type). One clean entry afterwards, but it silently drops
    special entries the tech never saw in the dialog. (AC7, AC12 change.)
- **Q-B** Besides changing to Deny, which changes get the red "are you sure" step?
  - A (recommended): any change that takes access away (to Deny, or an Allow lowered, e.g. Modify
    -> Read) and any change on a drive or share root; changes that only give more access stay one
    click. Matches Remove being destructive and D-044's root rule.
  - B: only changes to Deny, plus roots (the backlog's literal wording). Lowering Modify to Read is
    one click with no second check.
  - C: every Change asks first. Safest, but an extra click on harmless changes like Read -> Modify.
- **Q-C** How does Change work for files?
  - A (recommended): one selected file at a time; the dialog has a picker of that file's own
    entries. Simple and exact; several files need several changes.
  - B: with several files selected, change the same entry (same account, Allow/Deny and level) on
    every selected file that has it; files without it are skipped and listed. Faster for batches,
    more to test, and the "Partly done" cases come back. (Adds about four ACs.)
